# Регламент ротации секретов

**Триггер**: плановая ротация, подозрение на компрометацию credentials или требование политики безопасности

**Предусловия**:

- Новые секреты сгенерированы безопасно
- Подготовлено хранилище секретов (secret manager или защищённый env-файл)
- Запланировано окно обслуживания (если недостижим zero-downtime)

**Ориентировочная длительность**: 30-60 минут на тип секрета

---

## Инвентарь секретов

Production-секреты HarmoFin, требующие возможности ротации:

| Секрет                                    | Используется         | Влияние ротации                 | Возможен zero-downtime                |
| ------------------------------------------ | --------------------- | -------------------------------- | -------------------------------------- |
| `DATABASE_URL`                            | API, worker, migrate  | Высокое — рестарт всех сервисов | Нет — требуется рестарт сервисов        |
| `SESSION_HASH_SECRET`                     | API                   | Высокое — сессии инвалидируются | Нет — пользователи заходят заново       |
| `SMTP credentials`                        | API                   | Среднее — только отправка почты | Да — новое соединение использует новые credentials |
| `ERROR_REPORTING_ENDPOINT` DSN            | API, worker           | Низкое — только observability   | Да — новые ошибки используют новый DSN  |
| `OTEL_EXPORTER_OTLP_ENDPOINT` credentials | API, worker           | Низкое — только observability   | Да — новые трейсы используют новые credentials |
| `GitHub registry token`                   | Деплой                | Низкое — только pull образов    | Да — только workflow деплоя             |
| `SSH private key`                         | Деплой                | Низкое — только деплой          | Да — только workflow деплоя             |

---

## Общая процедура ротации

### 1. Сгенерировать новый секрет

```bash
# Сгенерировать новый секрет безопасно
# НЕ включать в Git реальные команды генерации с выводом

# Примеры паттернов (адаптировать под тип секрета):
# - Пароль базы данных: консоль провайдера или CLI
# - SESSION_HASH_SECRET: openssl rand -base64 32
# - SSH-ключ: ssh-keygen -t ed25519
```

**Новый секрет сгенерирован**: `[timestamp]`  
**Сгенерировал**: `[имя]`

- [ ] Новый секрет сгенерирован с достаточной энтропией
- [ ] Новый секрет записан в secret manager или защищённое хранилище
- [ ] Старый секрет сохранён до завершения ротации

### 2. Обновить секрет в secret manager

```bash
# Обновить секрет в GitHub Environment secrets (для credentials деплоя)
# ИЛИ обновить env-файл на production-хосте (для runtime-секретов)

# Для GitHub secrets:
# - Перейти в Settings репозитория → Environments → production/staging
# - Обновить значение секрета
# - Проверить, что имя секрета совпадает с конфигурацией приложения

# Для runtime-секретов:
# - SSH на production-хост
# - Отредактировать .env.production с новым секретом
# - Сохранить права доступа к файлу (600)
# - Не коммитить в Git
```

- [ ] Новый секрет сохранён в secret manager или env-файле
- [ ] Секрет доступен нужным сервисам
- [ ] Права доступа к файлу корректны (если env-файл)

### 3. Перезапустить затронутые сервисы

```bash
# Для runtime-секретов (DATABASE_URL, SESSION_HASH_SECRET, SMTP):
ssh production-user@production-host
cd /app/production
docker compose -f infra/compose/production.yml restart api worker

# Для секретов деплоя: рестарт не нужен, следующий деплой использует новый секрет
```

**Время рестарта сервисов**: `[YYYY-MM-DD HH:MM UTC]`

- [ ] Сервисы перезапущены с новым секретом
- [ ] Health-проверки проходят
- [ ] Нет ошибок аутентификации/соединения

### 4. Проверить работу нового секрета

```bash
# Проверить работоспособность сервиса с новым секретом
curl -f https://production-domain/api/v1/health/ready

# Для DATABASE_URL: health-проверка включает связность с базой данных
# Для SESSION_HASH_SECRET: проверить сценарий входа
# Для SMTP: следить за логами отправки почты
# Для observability: проверить появление логов/метрик/трейсов
```

- [ ] Сервисы подключаются с новым секретом
- [ ] В логах нет ошибок, связанных с секретом
- [ ] Функциональность проверена

### 5. Отозвать старый секрет

**⚠️ ВНИМАНИЕ**: не отзывать старый секрет, пока не проверена работа нового

```bash
# Отозвать старый секрет у провайдера или в secret manager
# Для базы данных: обновить пароль пользователя у провайдера
# Для GitHub secrets: старое значение перезаписано, отдельный отзыв не нужен
# Для SSH-ключей: удалить старый публичный ключ из authorized_keys
```

**Старый секрет отозван**: `[YYYY-MM-DD HH:MM UTC]`

- [ ] Старый секрет отозван у источника
- [ ] Сервисы всё ещё здоровы после отзыва
- [ ] Старый секрет невозможно использовать

## Специфичные процедуры ротации

### Ротация DATABASE_URL

**Влияние**: высокое — требуется рестарт сервисов, прерывает запросы в процессе

**Рекомендуемое окно**: период низкого трафика, рекомендуется уведомление пользователей

```bash
# 1. Сгенерировать новый пароль базы данных через консоль провайдера
# 2. Протестировать новый DATABASE_URL с хоста приложения
psql "postgresql://user:NEW_PASSWORD@host/database" -c "SELECT 1;"
# 3. Обновить .env.production новым DATABASE_URL
# 4. Перезапустить api, worker, убедиться, что migrate использует новый URL при следующем запуске
docker compose -f infra/compose/production.yml restart api worker
# 5. Проверить прохождение health-проверок
curl -f https://production-domain/api/v1/health/ready
# 6. Отозвать старый пароль базы данных через консоль провайдера
```

**Влияние на пользователей**: запросы в процессе падают, активные сессии прерываются

### Ротация SESSION_HASH_SECRET

**Влияние**: высокое — инвалидирует все пользовательские сессии, требуется повторный вход

**Рекомендуемое окно**: период низкого трафика, требуется уведомление пользователей

```bash
# 1. Сгенерировать новый SESSION_HASH_SECRET
openssl rand -base64 32
# 2. Обновить .env.production
# 3. Перезапустить API
docker compose -f infra/compose/production.yml restart api
# 4. Уведомить пользователей об инвалидации сессий
```

**Влияние на пользователей**: все пользователи выходят из системы, требуется повторный вход

### Ротация SMTP credentials

**Влияние**: среднее — только отправка почты, без влияния на пользователей

```bash
# 1. Сгенерировать новые SMTP credentials через консоль провайдера
# 2. Обновить .env.production новыми SMTP_USER и SMTP_PASSWORD
# 3. Перезапустить API (или дождаться zero-downtime: новые соединения используют новые credentials)
docker compose -f infra/compose/production.yml restart api
# 4. Протестировать отправку почты (запустить сброс пароля или уведомление)
# 5. Отозвать старые SMTP credentials через консоль провайдера
```

**Влияние на пользователей**: нет (только фоновая отправка почты)

### Ротация credentials observability

**Влияние**: низкое — только observability, без влияния на пользователей

```bash
# 1. Сгенерировать новый DSN или API-ключ через консоль провайдера observability
# 2. Обновить .env.production новым ERROR_REPORTING_ENDPOINT или OTEL_EXPORTER_OTLP_ENDPOINT
# 3. Перезапустить затронутые сервисы
docker compose -f infra/compose/production.yml restart api worker
# 4. Проверить появление логов/метрик/трейсов/ошибок в бэкенде
# 5. Отозвать старые credentials через консоль провайдера
```

**Влияние на пользователей**: нет

### Ротация GitHub-credentials деплоя

**Влияние**: низкое — только деплой, без влияния на production runtime

**SSH private key**:

```bash
# 1. Сгенерировать новую пару SSH-ключей
ssh-keygen -t ed25519 -f production_deploy_new
# 2. Добавить новый публичный ключ в authorized_keys production-хоста
# 3. Обновить GitHub Environment secret PRODUCTION_SSH_PRIVATE_KEY
# 4. Протестировать деплой с новым ключом (не на production или на staging)
# 5. Удалить старый публичный ключ из authorized_keys
```

**Registry token**:

```bash
# 1. Сгенерировать новый GitHub PAT или использовать GITHUB_TOKEN (предпочтительно)
# 2. Обновить GitHub Environment secret (если не используется GITHUB_TOKEN)
# 3. Протестировать pull образа с новым токеном
# 4. Отозвать старый PAT через настройки GitHub
```

**Влияние на пользователей**: нет (только workflow деплоя)

## Экстренная ротация (подозрение на компрометацию)

**Триггер**: утечка credentials, несанкционированный доступ, инцидент безопасности

### Немедленные действия

1. **Оценить влияние**
   - [ ] Определить, какие секреты скомпрометированы
   - [ ] Оценить радиус поражения (что может получить атакующий)
   - [ ] Уведомить incident commander и команду безопасности

2. **Немедленно ротировать скомпрометированный секрет**
   - [ ] Сгенерировать новый секрет
   - [ ] Обновить production (принять влияние на пользователей при необходимости)
   - [ ] Отозвать старый секрет у источника
   - [ ] Следить за попытками несанкционированного доступа

3. **Проверить логи доступа**
   - [ ] Просмотреть логи доступа к базе данных
   - [ ] Просмотреть логи доступа к API
   - [ ] Просмотреть audit-логи провайдера
   - [ ] Определить любую несанкционированную активность

4. **После инцидента**
   - [ ] Задокументировать хронологию компрометации
   - [ ] Определить источник утечки и предотвратить повторение
   - [ ] Обновить процедуры обращения с секретами
   - [ ] Рассмотреть ротацию дополнительных секретов из осторожности

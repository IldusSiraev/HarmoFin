# Secret Rotation Runbook

**Trigger**: Scheduled rotation, suspected credential compromise, or security policy requirement

**Prerequisites**:

- New secrets generated securely
- Secret storage prepared (secret manager or secure environment file)
- Maintenance window scheduled (if zero-downtime not achievable)

**Estimated duration**: 30-60 minutes per secret type

---

## Secret inventory

HarmoFin production secrets requiring rotation capability:

| Secret                                    | Used by              | Rotation impact              | Zero-downtime possible                    |
| ----------------------------------------- | -------------------- | ---------------------------- | ----------------------------------------- |
| `DATABASE_URL`                            | API, worker, migrate | High - all services restart  | No - requires service restart             |
| `SESSION_HASH_SECRET`                     | API                  | High - invalidates sessions  | No - users re-authenticate                |
| `SMTP credentials`                        | API                  | Medium - email delivery only | Yes - new connection uses new credentials |
| `ERROR_REPORTING_ENDPOINT` DSN            | API, worker          | Low - observability only     | Yes - new errors use new DSN              |
| `OTEL_EXPORTER_OTLP_ENDPOINT` credentials | API, worker          | Low - observability only     | Yes - new traces use new credentials      |
| `GitHub registry token`                   | Deployment           | Low - image pull only        | Yes - deployment workflow only            |
| `SSH private key`                         | Deployment           | Low - deployment only        | Yes - deployment workflow only            |

## Specific rotation procedures

### DATABASE_URL rotation

**Impact**: High - requires service restart, breaks in-flight requests

**Recommended window**: Low-traffic period, user notification advised

```bash
# 1. Generate new database password via provider console
# 2. Test new DATABASE_URL from application host
psql "postgresql://user:NEW_PASSWORD@host/database" -c "SELECT 1;"
# 3. Update .env.production with new DATABASE_URL
# 4. Restart api, worker, ensure migrate uses new URL on next run
docker compose -f infra/compose/production.yml restart api worker
# 5. Verify health checks pass
curl -f https://production-domain/api/v1/health/ready
# 6. Revoke old database password via provider console
```

**User impact**: In-flight requests fail, active sessions interrupted

### SESSION_HASH_SECRET rotation

**Impact**: High - invalidates all user sessions, requires re-authentication

**Recommended window**: Low-traffic period, user notification required

```bash
# 1. Generate new SESSION_HASH_SECRET
openssl rand -base64 32
# 2. Update .env.production
# 3. Restart API
docker compose -f infra/compose/production.yml restart api
# 4. Notify users of session invalidation
```

**User impact**: All users signed out, must re-authenticate

### SMTP credentials rotation

**Impact**: Medium - email delivery only, no user-facing impact

```bash
# 1. Generate new SMTP credentials via provider console
# 2. Update .env.production with new SMTP_USER and SMTP_PASSWORD
# 3. Restart API (or wait for zero-downtime: new connections use new credentials)
docker compose -f infra/compose/production.yml restart api
# 4. Test email delivery (trigger password reset or notification)
# 5. Revoke old SMTP credentials via provider console
```

**User impact**: None (background email delivery only)

### Observability credentials rotation

**Impact**: Low - observability only, no user-facing impact

```bash
# 1. Generate new DSN or API key via observability provider console
# 2. Update .env.production with new ERROR_REPORTING_ENDPOINT or OTEL_EXPORTER_OTLP_ENDPOINT
# 3. Restart affected services
docker compose -f infra/compose/production.yml restart api worker
# 4. Verify logs/metrics/traces/errors appearing in backend
# 5. Revoke old credentials via provider console
```

**User impact**: None

### GitHub deployment credentials rotation

**Impact**: Low - deployment only, no production runtime impact

**SSH private key**:

```bash
# 1. Generate new SSH key pair
ssh-keygen -t ed25519 -f production_deploy_new
# 2. Add new public key to production host authorized_keys
# 3. Update GitHub Environment secret PRODUCTION_SSH_PRIVATE_KEY
# 4. Test deployment with new key (non-production test or staging)
# 5. Remove old public key from authorized_keys
```

**Registry token**:

```bash
# 1. Generate new GitHub PAT or use GITHUB_TOKEN (preferred)
# 2. Update GitHub Environment secret (if not using GITHUB_TOKEN)
# 3. Test image pull with new token
# 4. Revoke old PAT via GitHub settings
```

**User impact**: None (deployment workflow only)

## Emergency rotation (suspected compromise)

**Trigger**: Credential leak, unauthorized access, security incident

### Immediate actions

1. **Assess impact**
   - [ ] Identify which secret(s) compromised
   - [ ] Assess blast radius (what can attacker access)
   - [ ] Notify incident commander and security team

2. **Rotate compromised secret immediately**
   - [ ] Generate new secret
   - [ ] Update production (accept user impact if necessary)
   - [ ] Revoke old secret at source
   - [ ] Monitor for unauthorized access attempts

3. **Audit access logs**
   - [ ] Review database access logs
   - [ ] Review API access logs
   - [ ] Review provider audit logs
   - [ ] Identify any unauthorized activity

4. **Post-incident**
   - [ ] Document compromise timeline
   - [ ] Identify leak source and prevent recurrence
   - [ ] Update secret handling procedures
   - [ ] Consider rotating additional secrets out of caution

# HarmoFin: план реализации Envelope Plan v2.2 — индекс

> **Для исполнителя в любой сессии:** выполняйте ОДНУ задачу с кодом и тестом через субагентов, затем сообщайте результат и останавливайтесь. Перед началом прочитайте этот индекс, [журнал передачи](2026-09-29-envelope-v2.2-progress.md), указанную в задаче секцию [спецификации v2.2](../specs/2026-09-29%20HarmoFin_Envelope_Plan_Model_v2.2.md) и только свою задачу из файла этапа. Используйте порядок работы ниже; worktree не создавать. Для реализации используйте TDD; не переходите к следующей задаче самостоятельно. Чекбоксы в файлах этапов отражают выполненные шаги, но Git-коммит и результаты команд — главный источник состояния.

**Цель:** Заменить физическую семантику конвертов v1 моделью назначений v2.2, сохранить реальные деньги и историю, выпустить безопасный лимит расходов и быстрый интерфейс.

**Архитектура:** Расширяем PostgreSQL и API без изменения поведения бюджетов v1; новые серверные сервисы считают назначения, платежи и предложения отдельно от фактических счетов. После завершения API/web/worker, проверки миграции и ручного допуска переводим текущий бюджет в версию 2, создаём новые бюджеты сразу в версии 2 и удаляем мёртвый код отдельным этапом. `/api/v1` не меняет смысл; модельно-зависимые записи v1 для бюджета 2 блокируются, а `/api/v2` работает только с бюджетом 2.

**Технологический стек:** Node.js 24.20.0, pnpm 11.24.0, TypeScript strict, Nuxt 4/Vue 3, NestJS/Fastify, Prisma/PostgreSQL 18, Vitest, OpenAPI, Playwright в CI.

**Спецификация:** [2026-09-29 HarmoFin_Envelope_Plan_Model_v2.2.md](../specs/2026-09-29%20HarmoFin_Envelope_Plan_Model_v2.2.md). Существующий v1-код — исторический источник существующих имён и контрактов; продуктовые решения берите из v2.2.

## Глобальные ограничения

- Все суммы хранятся как integer minor units (`BIGINT`/`bigint`), основная валюта `RUB`, `scale = 2`; ввод API — десятичная строка, ответы — строковые minor units. **Примеры в прозе указаны в рублях: 65 000 ₽ = `6_500_000n` / ответ `"6500000"`.** Не использовать `number`/float для денег.
- В расчётах только `CONFIRMED`; черновик, отмена, логическое удаление не меняют деньги и назначения. Банковские переводы сохраняют сумму счетов.
- Каждая пользовательская таблица и выборка фильтруются по `budget_id`; проверять authenticated user → active workspace membership → budget → role → linked object → state. В v2 OWNER подтверждает назначения/переназначения/цели, меняет правила, архивирует и применяет шаблон; OWNER|EDITOR записывают реальные факты и оплачивают планы; VIEWER только читает. Ссылки между объектами одного бюджета подтверждаются составными FK/серверными проверками.
- Финансовые мутации v2: единый порядок блокировок в PostgreSQL transaction: budget row `FOR UPDATE`, затем advisory idempotency lock, затем account/income/envelope/occurrence rows по ID. Все v2 writers используют этот порядок (включая expense, update, account starting balance), иначе назначение параллельно с расходом может превысить наличные деньги. `Idempotency-Key`, аудит, логическое удаление; конкуренция проверяется интеграционными тестами.
- OpenAPI описывает request/response/error для каждого нового endpoint; `/api/v1` не ломать без согласованного переключения. HTTP-контроллеры не вычисляют деньги и не обращаются к Prisma.
- UI и пользовательские документы — на русском; код, API и схема БД — на английском. Следовать [Calm Fintech](../specs/2026-09-17-calm-fintech-visual-guidelines.md), сохранять keyboard/focus/contrast/labels и обе темы.
- В v2.2 не входят банковский импорт, интеграции, кредиты/долги, мультивалютная конвертация, совместный UI, AI, биллинг, Telegram. Изменение дня/границы цикла для используемого бюджета поддержано с будущего периода; смена timezone после подтверждённых фактов требует отдельного решения о перекладке календарных дат и в этом плане безопасно отклоняется (T02). Это ограничение продукта нужно явно отразить в настройках/справке.
- `identity/logo_description.png` и неотслеживаемый `envelope_plan_2.1_anwers.md` не трогать/не добавлять. Никаких production-секретов/данных в тестах, Git или логах.
- Работать в новой ветке в текущем checkout; worktree не создавать. Локально НЕ запускать Playwright: браузерные тесты запускаются в CI. Коммиты после локальных unit/integration/typecheck; после исправления E2E/CI сбоя остановиться до отдельного подтверждения владельца перед коммитом.

### Работа с субагентами без worktree

1. Ведущий агент выбирает **одну** следующую задачу по журналу и зависимостям. В текущем checkout создаёт или использует выделенную ветку; не создаёт worktree, изолированную копию или отдельную ветку для субагента.
2. Передаёт свежему субагенту-исполнителю ID задачи, путь к её файлу, ссылки на индекс и спецификацию, точные границы файлов, TDD/команды и запреты на production, локальный Playwright и чужие файлы. Субагент меняет код **в том же checkout**; одновременно может быть только один пишущий агент. Ведущий не редактирует эти файлы параллельно.
3. После завершения исполнителя ведущий запускает отдельного субагента для **читающего** review: соответствие задаче и спецификации, финансовые инварианты, изоляция бюджетов, тесты и отсутствие побочных изменений. Review не исправляет код, не коммитит и не запускает опасные операции. Замечания исправляет исполнитель в том же checkout; затем ведущий повторно проверяет затронутые места. Для особенно небольших задач review остаётся отдельным коротким проходом.
4. Ведущий проверяет diff, запускает предусмотренные локальные тесты/проверки и фиксирует фактические результаты. Коммит только по файлам текущей задачи после зелёных проверок и закрытия замечаний; исключение для E2E/CI исправлений — ждать подтверждения владельца. Обновляет журнал, сообщает результат и **останавливается** до следующего запроса. Субагенты не начинают соседнюю задачу сами.
5. Для миграции/выпуска субагенты готовят и проверяют код или read-only preview. Реальный cutover, production deploy и деструктивные команды не поручать субагенту и не выполнять без отдельного явного допуска владельца и проверок из этапа 7.

## Согласованные контракты данных

Рассматривать имена ниже как контракт между задачами. Если проекту нужен иной вариант, изменить индекс и зависимые задачи **до реализации**. Датой назначения/переноса служит дата подтверждения в timezone бюджета, не дата дохода или целевого периода: текущие деньги можно назначить будущему периоду уже сегодня. Для дат до миграции v2-баланс назначений не реконструировать по старым фактам: показывать их как исторические v1 записи, не как v2 «Можно потратить».

1. `Budget.planModelVersion: number` (`1|2`, начальный DB default `1`) и `Budget.planModelActivatedOn: Date|null` (null для бюджета1; дата cutover/создания бюджета2 в timezone бюджета); `Transaction.accountingModelVersion: number` (`1|2`, default `1`). `planModelActivatedOn` запрещает повторную генерацию исторических неподтверждённых obligations до cutover: существующие открытые occurrences сохраняются, пропущенные в старой истории решает владелец отдельно. Все старые транзакции имеют модель 1; новые v2 — 2. В новых виртуальных остатках мигрированного бюджета учитывать начальные назначения при переключении и расходы с `accountingModelVersion=2`, **не** повторно вычитать старые расходы. Балансы счетов продолжают учитывать обе эпохи. Редактирование старого факта после cutover требует отдельного явного согласования начального назначения.
2. `EnvelopePeriod(id, budgetId, envelopeId, startsOn, endsOn, targetMinor?, targetStatus)`: конкретный период; уникально `(budgetId,envelopeId,startsOn)` и `(id,budgetId,envelopeId)` для FK ledger. `targetStatus=UNSET|DRAFT|CONFIRMED`, target nullable только у UNSET. Сохранённое правило формирует DRAFT цели периода; она становится CONFIRMED лишь после явного действия владельца (отдельно или вместе с назначением дохода). Только CONFIRMED target участвует в `period_funding_gap`; UNSET/DRAFT не выдаются за лимит. Для `MANDATORY_EXPENSES` и `SAVINGS_GOAL` period ID назначения отсутствует — остаток сквозной. Старый `period_slot` только шаблон/роль, не идентификатор конкретного периода. `BudgetCycleRevision(budgetId,effectiveOn,cycleStartDay,periodBoundaryOffset,timezone)` хранит future-only смену границ; `settingsAt(date)` выбирает действующую версию, не переписывает сохранённые интервалы.
3. `EnvelopeFundingRule(envelopeId,budgetId,type,priority,fixedMinor?,percentBasisPoints?)`: один активный тип из `MANUAL|SUM_OF_PLANS|FIXED_PER_PERIOD|SUGGESTED_FIXED|PERCENT_OF_INCOME`. `SUGGESTED_FIXED` не защищает ещё не назначенный взнос. Суммы правил не проводят операций.
4. `EnvelopeAssignment(id,budgetId,envelopeId,periodId?,sourceKind,sourceIncomeTransactionId?,effectiveOn,amountMinor,status)`: `sourceKind=INCOME|OPENING|FREE`. `effectiveOn` — дата фактического подтверждения назначения в timezone бюджета (миграционное OPENING — дата cutover), не редактируется задним числом; `createdAt` отдельно хранит UTC-аудит. Положительные целые суммы; источник INCOME требует подтверждённый доход бюджета, первоначальные назначения этого дохода в сумме ≤ доходу. `OPENING`/`FREE` берут только реально свободные деньги. После явного освобождения деньги становятся общебюджетным `FREE`, исходный доход сохраняется в аудите.
5. `EnvelopeMovement(id,budgetId,sourceEnvelopeId,sourcePeriodId?,destinationEnvelopeId?,destinationPeriodId?,effectiveOn,amountMinor,status)`: `effectiveOn` — дата подтверждения в timezone бюджета; ненулевой source; nullable destination означает освобождение в `FREE`. Назначение из свободного хранится как `EnvelopeAssignment(sourceKind=FREE)`, не дублируется движением. Два периода одного конверта могут быть разными сторонами. Расход не является движением.
6. `PlanPayment(id,budgetId,occurrenceId,transactionId)`: один реальный расход связан максимум с одним occurrence; occurrence может иметь несколько `PlanPayment`. В v2 старый `PlanOccurrence.transactionId` не используется как единственный платёж; для v1 остаётся прежним. `unpaid = max(0, expected − Σ confirmed linked expenses)` для открытых occurrences, закрытый/пропущенный = 0.
7. `Transfer.mode=LEGACY_PARTS|ACCOUNT_ONLY`; для `ACCOUNT_ONLY` заполнены новые `sourceAccountId`/`destinationAccountId`, `parts=[]`, сумма положительна; для `LEGACY_PARTS` действуют нынешние части, подтверждённые старые движения продолжают входить в баланс счёта. Ни одно новое прямое движение не меняет остатки назначений.
8. `calculateSpendable({cash,current,mandatory,mandatoryDue,otherBalances})` возвращает `spendableNow`, `mandatoryProtected`, `mandatoryGap`, `freeToAssign`, `unbackedAssignments`; формулы из §4/§8 спецификации. `mandatoryDue` — просроченные, текущий и ближайший следующий периоды; будущий доход не включать. Расход периода меняет `current`, но не `period_funded`; перенос из него меняет оба.
9. Предложения `POST /api/v2/budgets/:budgetId/funding/preview` принимают источник `INCOME|OPENING|FREE` и optional редактируемые `overrides`, возвращают серверный остаток/ошибки и draft целей; `/funding/confirm` передаёт те же lines, `confirmPeriodTargets` и `previewHash` от актуальных серверных данных, draft-целей и строк. Confirm под блокировкой пересчитывает суммы и отказывает `409 PREVIEW_STALE`, если состояние/строки изменились. Никаких тихих автоматических назначений.
10. `GET /api/v2/budgets/:budgetId/reference-template/preview`, `POST /api/v2/budgets/:budgetId/reference-template/apply` — создают только выбранные категории/конверты/правила; существующие и архивные ключи не затирают; `FREE_MONEY` не создают.

## Проверки и безопасные стопы

- Для HTTP/integration fixture брать устройство теста из [reference-data.integration.test.ts](../../../apps/api/test/reference-data.integration.test.ts): `createApiApp`, `server.inject`, отдельные owner/чужой бюджет, `afterAll` cleanup. Для новых v2 тестовых бюджетов ставить `planModelVersion=2` и `planModelActivatedOn` явно; после M04 регистрация делает это сама. Не копировать реальные данные владельца и не отключать проверки сессии/CSRF.
- Unit: `pnpm --filter @harmofin/api exec vitest run src/common/finance/v2-money.domain.test.ts --config vitest.config.ts` — пример реального целевого файла из F05; для остальных задач команда с точным путём указана в шаге 2.
- Integration (только отдельная локальная тестовая БД): `pnpm --filter @harmofin/api exec vitest run --config vitest.integration.config.ts test/v2-foundation.integration.test.ts` — пример из F01. Подготовить отдельную БД `harmofin_v22_test` в локальном Compose Postgres, а не использовать рабочую `harmofin`. Перед любым `pnpm db:migrate` явно задать `DATABASE_URL` в текущем shell на эту БД; проверить hostname/database через `node -e 'const u=new URL(process.env.DATABASE_URL); console.log(u.hostname,u.pathname)'`, убедиться, что вывод указывает **именно на disposable DB**, затем `pnpm db:generate` и `pnpm db:migrate`. Если URL не подтверждён или БД содержит нужные данные — остановиться; никогда не брать `.env` на веру. Тесты в некоторых файлах имеют встроенный fallback на `harmofin`: отсутствие явного `DATABASE_URL` недопустимо.
- Gates после каждой задачи: её целевой тест + `pnpm typecheck`; после этапа: `pnpm lint`, `pnpm test`, `pnpm build`, интеграционные тесты на disposable PostgreSQL. `pnpm format:check` перед коммитом планов/крупных этапов.
- Playwright: тесты писать в задаче и прогонять **только в CI**, локально не запускать. Сбой CI/E2E фиксировать отдельно; без подтверждения владельца не коммитить исправление.
- До cutover `Budget.planModelVersion=1` для действующих бюджетов; для тестовых бюджетов2 обязательно `planModelActivatedOn` в timezone бюджета. Никакие новые v2-эндпоинты не становятся маршрутом старого UI. Смена версии — ручная gate после полного backup и rehearsal. Никогда не применять destructive `migrate dev`/rollback к production.
- Не использовать `git add .`: коммитить только файлы своей задачи. Если проверки красные, сообщить точную ошибку и остановиться. Коммиты до пользовательского review за пределы локальной ветки не публиковать.

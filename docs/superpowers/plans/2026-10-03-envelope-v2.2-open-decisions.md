# HarmoFin Envelope Plan v2.2 — открытые решения и бэклог

Состояние на 2026-10-03: этапы 01–08 завершены по коду, перенос действующего бюджета на v2 **отменён** (владелец начинает учёт с чистого листа через `docs/runbooks/budget-reset.md`). Ветка `feat/envelope-v22-foundation` локальная, не опубликована. Подробная история — в [журнале передачи](2026-09-29-envelope-v2.2-progress.md). Здесь только то, что требует решения или ещё не сделано.

## 1. Интерфейс

1. **Остальные Drawer → диалоги.** Окно «Базовый шаблон» уже диалог (U01). Остались на боковой панели `UiDrawer`: `AccountDrawer` (детали счёта), `PeriodDecisionCard` (перенос остатка), `EnvelopeMovePanel` (перемещение между конвертами), `EnvelopePlanDrawer` (план и правило конверта), `FundingReviewSheet` (проверка пополнения), `RuleSettingsSheet` (правило пополнения), `IncomeRecordSheet` (запись дохода), `ObligationPaySheet` (оплата обязательного), `OperationDrawer` (операция), «Фильтры» в `OperationsToolbar`. Предложение: быстрые действия (оплата, доход, перенос, пополнение, правило) — в диалоги; детали счёта и операции — оставить панелью. Решение за владельцем.
2. **Понятность первого запуска** — отдельная работа по итогам прохождения «глазами нового пользователя» (см. `docs/ux/newcomer-walkthrough.md`).
3. Нет пользовательского UI создания и редактирования **v2-планов обязательств** (в v2 `plans.vue` скрыты календарь, «Создать план», форма; API `createObligationPlan` есть). Онбординг предлагает «добавить плановые платежи», но формы нет.
   - **Сделано (2026-10-04):** форма «Создать план» для обязательных платежей и плановых доходов на странице «Планы» (`PlanCreateDialog`). Остаются: правка и остановка плана, календарь (UX-17).
4. Подсказки «До нужной суммы» / «Весь остаток» в панели назначения не подключены (нужны серверные подсказки, иначе арифметика в JS).
5. Расход по умолчанию создаётся «Без назначения» (нет серверной подсказки предложенного конверта).
6. `UiStatus` показывает статус текстом и цветом, без иконки (общий компонент).
7. Окно шаблона: поле «второй период начинается M-го числа» вместо «длительность первого периода, дней»; блокировка цикла сообщается только после ответа 409 (нужен флаг `cycleLocked` в preview).
8. Не проверено глазами в браузере: компоновка подсказок внутри прокручиваемого диалога, нижняя панель на мобильном, тёмная тема, остальные 6 мест, где используется общий `Modal.vue` (после U01 у него новая фокус-ловушка и стек).
9. **Контраст границ полей ввода** (UX-06): токены `--hf-color-border` / `--hf-color-border-strong` дают около 1.2–1.5:1, ниже 3:1 (WCAG 1.4.11). В окне шаблона границы уже усилены до `border-strong`; общий токен границы управляющих элементов (`Input`, `Select`, `DatePicker`, чекбоксы) с контрастом ≥3:1 в обеих темах — отдельная задача с проверкой в браузере.
10. **Подтверждённая цель периода нигде не видна** (UX-10): дашборд отдаёт только `suggestedTarget` (пока цель не подтверждена), в `EnvelopePlanResponse` нет данных цели периода. Нужен additive-DTO: `period.targetMinor` и `targetStatus` в дашборде и цель периода в строке периодного конверта; тогда можно показать «План периода 65 000 ₽ · назначено 0 ₽» и «Подтверждён: 65 000 ₽» в шаге чек-листа. Пока карточка «Можно потратить» только объясняет нулевой остаток текстом.
11. **Строки предложения назначения без дат периода** (UX-11): в панели «Назначить деньги» строка периодного конверта подписана только именем. Нужен additive-DTO: границы периода (`periodStart`, `periodEnd`) и признак «идёт сейчас» в строках предпросмотра, чтобы показать «Второй период · 25 сент – 9 окт · идёт сейчас». Подсказки «До нужной суммы» / «Весь остаток» скрыты, пока их не отдаёт сервер (§1.4).
12. **Нет постоянного входа в назначение кроме главной** (UX-13): строка «Свободно для назначения» с кнопкой есть только на главной; кнопка «Назначить деньги» на страницах «Счета» и «Конверты» не добавлена.
13. **Отмена ошибочного назначения из интерфейса** (UX-14, вариант 3): на сервере есть `DELETE /assignments/:id` и правка суммы, но история конверта отдаётся без `id` записей и в вебе нет кнопки «Отменить назначение». Нужен additive `id` в истории и действие с подтверждением.

## 2. Пробелы API (additive, из gate-06b и последующих ревью)

- Dashboard DTO: нет `period.envelopeId` и `nextPeriodId` (поэтому «В следующий период» выключено и e2e-сценарий переноса остатка в текущий период помечен `test.fixme`), нет `asOf`, единой суммы «защищено», просроченных и «свободно для назначения» как действий.
- `EnvelopePlanResponse`: периоды конверта теперь отдаются (`periods[{periodId, startsOn, endsOn, fundedMinor, spentMinor, balanceMinor, current}]`, UX-14; панель переноса и назначения передаёт `sourcePeriodId`, `destinationPeriodId`, `periodId`). Остаётся: нет `targetStatus` периода, нет `status=archived` в списке, `targetAmountMinor` — десятичные рубли, остальное minor units. Архив периодного конверта с деньгами в нескольких периодах требует нескольких переносов (по одному на период).
- Перенос и назначение принимают любой `destinationPeriodId`/`periodId` конверта (в том числе прошлого или будущего периода): панель всегда шлёт текущий период, но прямой вызов API может наполнить не текущий; при желании ужесточить проверкой «период получателя — текущий» (замечание финансового ревью UX-14). Ответы `POST /assignments`, `PATCH`/`DELETE /assignments/:id` и `POST /movements` теперь описаны собственными схемами (`AssignmentResultResponse`, `MovementResultResponse`).
- Worker `MATERIALIZE_PLAN_OCCURRENCES` для моделей v2 создаёт возникновения только плановых расходов (`planType: 'EXPENSE'`, `apps/worker/src/plan-occurrence.handler.ts`), плановых доходов он не создаёт: повторяющийся плановый доход получает возникновения при создании (до сегодня + 60) и в других сервисных путях, но не по расписанию. Проверить и, если нужно, добавить доходы в worker (отдельная задача; найдено при UX-18).
- Нет GET текущего правила пополнения и текущего предложения по категории дохода.
- История конверта без `id`, источника дохода, направления переноса.
- Журнал операций v2: нет поиска, сортировки по сумме, фильтра периода и `planId`; CSV-экспорт без фильтров; нет перевода DRAFT → CONFIRMED; ответ lifecycle без `accountingModelVersion` и `planOccurrenceIds`.
- Аудит операции доступен только через v1-маршрут `GET /api/v1/budgets/:id/transactions/:id/audit` (оставлен намеренно).
- Не реализовано уведомление «проверьте новое предложение» (план этапа 05).
- 422-коды шаблона не перечислены единым списком в OpenAPI (добавлен `TEMPLATE_SLOT_OCCUPIED`).

## 3. Остатки legacy (не критично, без DROP)

- `PlanModelPolicy`, ответ 409 `MODEL_VERSION_MISMATCH`, колонки `plan_model_version` / `plan_model_activated_on`, DB default и CHECK, фильтр `planModelVersion=2` в worker, ветки `=== 2` в `accounts`, `mandatory-due`, `v2-occurrence-materializer`, `regular-plan.repository`, поле `planModelVersion` в `/me` и dashboard. Убирать вместе с contract-миграцией.
- В `FinancialBalanceRepository` остался SQL по `transfer_parts`; legacy-таблицы остаются в схеме (`docs/runbooks/legacy-schema.md`). Отдельный будущий план contract-миграции с DROP — только после backup.
- Нет проверки `accountingModelVersion` при правке, удалении и восстановлении операций v2 (после очистки v1-строк нет).
- `GET/POST /api/v1/workspaces` оставлен сознательно (под будущие роли); enum `PLAN_UPCOMING` и устаревшие типы уведомлений в Prisma, DTO и web-типе.
- Устаревшие комментарии: `report-v2.repository.ts`, `transfers.vue`, `DirectTransferCard.vue`.
- `IncomeAllocationRepository` удалён; 2 migration-теста схемы (`plans-notifications-migration`, `reference-data.migration`) создают бюджеты с `planModelVersion: 1`.
- Тест `budget-reset-script` падает, пока в рабочей копии изменён `docs/runbooks/budget-reset.sql` (локальные email и `commit_changes`): после очистки выполнить `git restore docs/runbooks/budget-reset.sql`.

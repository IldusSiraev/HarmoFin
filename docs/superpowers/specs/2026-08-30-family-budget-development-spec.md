## 1. Назначение документа

Документ фиксирует техническое решение для разработки веб-приложения семейного бюджета (v1) и задает правила, по которым приложение должно развиваться в универсальный семейный продукт и SaaS.

Документ отвечает на вопросы:

- какой стек используется на фронтенде, бэкенде и в хранении данных;
- как разделить приложение на модули;
- как фронтенд взаимодействует с API;
- где и как хранятся денежные данные;
- как организовать локальную разработку, staging и production;
- как выполнять миграции, резервирование и откат;
- как обеспечить безопасность и наблюдаемость;
- как подготовить систему к совместным бюджетам, Telegram и ИИ без преждевременного усложнения v1.

Все функциональные требования, бизнес-правила и критерии приемки берутся из функционального ТЗ. При противоречии функциональное ТЗ имеет приоритет по поведению продукта, а эта спецификация — по способу реализации.

## 2. Архитектурные решения

### 2.1. Общая архитектура

Используется веб-приложение с разделением на:

```text
Браузер
   │
   ▼
Web-приложение Nuxt/Vue
   │ HTTPS + REST/OpenAPI
   ▼
API NestJS/Fastify
   ├── PostgreSQL
   ├── Worker фоновых задач
   └── Object Storage для будущих файлов и экспортов
```

Стиль приложения — **модульный монолит**.

Модульный монолит означает:

- один продукт и единая доменная модель;
- четко разделенные модули внутри API;
- единая транзакционная база данных;
- отдельные процессы для web, API и worker;
- возможность позднее вынести тяжелые или независимо масштабируемые части без переписывания предметной области.

Микросервисы, Kubernetes и распределенная транзакционная модель не используются в v1.

### 2.2. Главный источник истины

PostgreSQL является единственным источником истины для:

- пользователей;
- рабочих пространств;
- бюджетов;
- счетов;
- конвертов;
- категорий;
- операций;
- распределений;
- переводов;
- регулярных планов;
- уведомлений;
- аудита.

Фронтенд не является источником финансовых расчетов. Любые балансы, доступные лимиты, статусы дефицита и агрегаты рассчитываются или подтверждаются API.

### 2.3. Границы v1

В v1 реализуются:

- ручной ввод операций;
- счета банков, карты и наличные;
- начальные балансы;
- конверты;
- категории;
- распределение доходов;
- переводы, разбитые на части;
- настраиваемый финансовый цикл;
- регулярные планы;
- внутренние уведомления;
- дашборд и базовая аналитика;
- редактирование, логическое удаление и журнал изменений;
- регистрация по email и паролю;
- адаптивный интерфейс;
- экспорт.

В v1 не входят:

- импорт CSV/XLSX;
- банковские API;
- Telegram;
- email и push-уведомления;
- совместная работа нескольких пользователей в интерфейсе;
- полноценная мультивалютность;
- кредитные счета;
- ИИ-анализ;
- биллинг SaaS.

Технические границы будущих функций предусматриваются в контрактах и модели данных, но код и интерфейс этих функций не должны необоснованно увеличивать объем v1.

## 3. Рекомендованный технологический стек

### 3.1. Сводная таблица

| Область | Решение |
|---|---|
| Frontend framework | Nuxt 4.x |
| UI framework | Vue 3.5+ |
| Язык | TypeScript в strict mode |
| Сборка | Nuxt/Vite toolchain |
| Состояние интерфейса | Pinia |
| Серверное состояние | TanStack Query for Vue |
| Формы | vee-validate + Zod |
| UI-компоненты | PrimeVue + Tailwind CSS |
| Графики | ECharts |
| Backend framework | NestJS 11.x |
| HTTP-движок | Fastify через Nest adapter |
| API | REST + OpenAPI |
| База данных | PostgreSQL 18.x |
| ORM | Prisma, дополненный контролируемым SQL |
| Аутентификация | Argon2id + серверные сессии + Secure HttpOnly cookies |
| Фоновые задачи | PostgreSQL-backed jobs + отдельный worker |
| Файлы | S3-compatible Object Storage |
| Контейнеры | Docker |
| Локальная оркестрация | Docker Compose |
| CI/CD | GitHub Actions или эквивалентный pipeline |
| Ошибки | Sentry или совместимый сервис |
| Трассировка и метрики | OpenTelemetry + Prometheus-совместимый backend |
| E2E-тесты | Playwright |
| Unit/integration-тесты | Vitest, Jest/Supertest или единая согласованная комбинация |

Точные patch-версии фиксируются lock-файлами. Обновление major-версий выполняется отдельным изменением с миграционным планом и тестами.

### 3.2. Версии runtime

Для production использовать активную LTS-версию Node.js, рекомендованно **Node.js 24 LTS**.

Минимальные правила:

- версия Node.js едина для local, CI, staging и production;
- версия задается в `.nvmrc`/`mise.toml`/эквиваленте и Docker image;
- бэкенд не запускается на Current-версии Node.js без отдельного решения;
- локальная разработка не должна зависеть от глобально установленной версии.

Nuxt 4 должен использоваться с поддерживаемой версией Node.js 22 или новее; Node.js 24 LTS является основным вариантом.

NestJS 11 используется с Node.js 24 LTS.

### 3.3. Почему выбран TypeScript end-to-end

Выбор единого языка обусловлен тем, что:

- один продуктовый домен используется фронтендом и API;
- схемы OpenAPI и валидации проще синхронизировать;
- быстрее разрабатывать v1 небольшой командой;
- проще переиспользовать безопасные типы и DTO;
- проще внедрять единые правила форматирования, lint и review;
- легче привлекать разработчиков для будущего SaaS-продукта.

Это не означает, что бизнес-логика должна копироваться в общий frontend/backend-пакет. Общими могут быть только контракты, типы и схемы, не содержащие серверных секретов и доступа к БД.

## 4. Frontend

### 4.1. Nuxt и Vue

Основой frontend является Nuxt 4.x на Vue 3.5+.

Стратегия рендеринга:

- публичные страницы и будущий лендинг — SSR или prerender;
- закрытые страницы бюджета — клиентский режим либо гибридный режим;
- пользовательские финансовые данные не должны попадать в публичный HTML или поисковые индексы;
- route middleware проверяет наличие действующей сессии;
- серверная проверка прав остается обязательной независимо от middleware.

Основные страницы v1:

```text
/login
/register
/forgot-password
/reset-password
/app
/app/operations
/app/accounts
/app/envelopes
/app/plans
/app/analytics
/app/notifications
/app/settings
```

Маршруты должны быть логически привязаны к текущему бюджету, но идентификатор бюджета не должен быть единственным механизмом авторизации.

### 4.2. Управление состоянием

Используются два уровня состояния.

#### Pinia

Pinia применяется для состояния интерфейса:

- выбранный бюджет;
- состояние бокового меню;
- локальные фильтры;
- состояние модальных окон;
- настройки отображения;
- временный черновик многошаговой формы.

#### TanStack Query for Vue

TanStack Query применяется для серверного состояния:

- список операций;
- счета;
- конверты;
- планы;
- уведомления;
- отчеты;
- текущая сводка.

После мутации должны инвалидироваться только связанные query-ключи. Нельзя вручную поддерживать десятки копий одного баланса в разных Pinia-store.

### 4.3. Компоненты и дизайн-система

Tailwind CSS используется для layout, отступов, responsive-правил и дизайн-токенов.

PrimeVue используется для:

- таблиц;
- полей форм;
- select/autocomplete;
- date picker;
- диалогов;
- toast-сообщений;
- pagination;
- tabs;
- меню и уведомлений.

Компоненты должны быть обернуты в локальный слой приложения там, где нужно зафиксировать:

- русский текст;
- единый формат денег и дат;
- доступность;
- правила ошибок;
- визуальные статусы;
- будущую замену UI-библиотеки.

Не следует напрямую использовать библиотечные компоненты во всех страницах без локальных соглашений.

### 4.4. Формы

Для форм используются:

- vee-validate для состояния формы;
- Zod для декларативных схем;
- серверная повторная валидация обязательна;
- денежные поля принимают строковое десятичное значение и преобразуются безопасно;
- суммы не передаются и не вычисляются как JavaScript `number`, если это может привести к потере точности;
- ошибки API отображаются у соответствующих полей.

Формы операций должны поддерживать режимы:

- доход;
- расход;
- перевод;
- распределение дохода;
- создание операции из плана.

При изменении типа операции форма должна очищать несовместимые поля и предупреждать пользователя о потере введенных значений.

### 4.5. Форматирование денег и дат

В интерфейсе:

- деньги отображаются в локали `ru-RU`;
- дата отображается как `ДД.ММ.ГГГГ`;
- часовой пояс берется из бюджета;
- сумма не должна форматироваться через неявные локальные преобразования;
- отрицательные значения отображаются со знаком минус и статусом;
- валюта всегда отображается рядом с суммой там, где контекст недостаточно очевиден.

### 4.6. Аналитика и визуализация

Для аналитики используется ECharts или совместимая библиотека с управляемой доступностью.

Форма визуализации выбирается по задаче:

- ключевые значения — stat cards, не графики;
- динамика доходов и расходов — линейный график;
- план/факт — столбцы или компактные progress-индикаторы;
- расходы по категориям — горизонтальные столбцы с ограничением числа видимых серий;
- накопительные цели — progress-индикатор и числовые значения;
- счета и конверты — таблица или карточки, если график не добавляет понимания.

Обязательные требования:

- любой график имеет табличное представление;
- для двух и более серий присутствует легенда;
- идентичность не кодируется только цветом;
- статусы используют цвет вместе с текстом и иконкой;
- не использовать двойные оси;
- не использовать rainbow-палитры;
- фильтры размещаются до области графиков;
- hover tooltip содержит дату/серию/значение;
- графики пригодны для клавиатурной навигации настолько, насколько позволяет библиотека;
- на мобильном экране графики не должны требовать горизонтальной прокрутки всей страницы.

### 4.7. Frontend-структура

Рекомендуемая структура:

```text
apps/web/
├── app/
│   ├── components/
│   │   ├── common/
│   │   ├── dashboard/
│   │   ├── operations/
│   │   ├── accounts/
│   │   ├── envelopes/
│   │   ├── plans/
│   │   └── analytics/
│   ├── composables/
│   ├── layouts/
│   ├── middleware/
│   ├── pages/
│   ├── plugins/
│   ├── stores/
│   └── utils/
├── public/
├── assets/
├── nuxt.config.ts
└── package.json
```

Границы:

- `pages` отвечают за маршрут и композицию;
- `components` отвечают за отображение и пользовательские действия;
- `composables` содержат переиспользуемую UI-логику и query hooks;
- `stores` не содержат серверных расчетов;
- `utils` не содержат доступа к API, если это не явно обозначенный API client;
- API client генерируется или строится из OpenAPI-контракта.

## 5. Backend

### 5.1. NestJS и Fastify

API реализуется на NestJS 11.x с Fastify adapter.

NestJS используется для:

- модулей и dependency injection;
- guards и проверки доступа;
- pipes и валидации;
- interceptors;
- lifecycle hooks;
- интеграционных тестов;
- единообразной структуры API.

Fastify используется как HTTP-движок. Код не должен зависеть от Express-специфичных объектов без обоснованной необходимости.

### 5.2. Модули API

```text
apps/api/src/
├── main.ts
├── app.module.ts
├── config/
├── common/
│   ├── errors/
│   ├── guards/
│   ├── interceptors/
│   ├── pagination/
│   ├── money/
│   ├── dates/
│   └── request-context/
├── auth/
├── workspaces/
├── budgets/
├── accounts/
├── envelopes/
├── categories/
├── transactions/
├── allocations/
├── transfers/
├── plans/
├── notifications/
├── reports/
├── audit/
└── exports/
```

Каждый предметный модуль по возможности содержит:

```text
module/
├── module.ts
├── controller.ts
├── service.ts
├── repository.ts
├── dto/
├── domain/
├── policies/
└── tests/
```

Контроллеры не должны содержать финансовые расчеты. Контроллеры:

- принимают запрос;
- вызывают application service;
- возвращают DTO;
- не обращаются к Prisma напрямую.

Репозитории отвечают за доступ к данным. Domain/application services отвечают за правила и транзакционные сценарии.

### 5.3. API-стиль

Используется REST API с JSON.

Базовый префикс:

```text
/api/v1
```

Примеры ресурсов:

```text
GET    /api/v1/me
GET    /api/v1/budgets
GET    /api/v1/budgets/{budgetId}/summary
GET    /api/v1/budgets/{budgetId}/transactions
POST   /api/v1/budgets/{budgetId}/transactions
PATCH  /api/v1/budgets/{budgetId}/transactions/{transactionId}
DELETE /api/v1/budgets/{budgetId}/transactions/{transactionId}
POST   /api/v1/budgets/{budgetId}/transfers
POST   /api/v1/budgets/{budgetId}/allocations
GET    /api/v1/budgets/{budgetId}/reports/expenses
GET    /api/v1/budgets/{budgetId}/notifications
```

Требования:

- каждый endpoint документируется в OpenAPI;
- request и response схемы версионируются;
- breaking changes не вносятся в `/api/v1` без миграционного плана;
- списки имеют pagination, сортировку и ограниченные фильтры;
- mutation endpoints поддерживают idempotency key там, где повторная отправка может создать финансовый дубль;
- ошибки возвращаются в формате Problem Details либо согласованном эквиваленте;
- API не возвращает лишние поля модели данных.

### 5.4. Контракт API

OpenAPI является контрактом между frontend и backend.

Pipeline должен проверять:

- корректность OpenAPI-документа;
- отсутствие несовместимых изменений;
- соответствие DTO и фактического ответа;
- генерацию или проверку frontend client;
- наличие описаний ошибок и кодов ответа.

Общие frontend/backend-пакеты могут содержать:

- идентификаторы типов;
- enum значений;
- Zod-схемы, безопасные для клиента;
- сгенерированные API-типы.

Они не должны содержать:

- Prisma client;
- секреты;
- SQL;
- серверные repository;
- правила, требующие доверенной среды.

### 5.5. Ошибки API

Минимальный набор HTTP-ответов:

- `400` — некорректный запрос;
- `401` — пользователь не авторизован;
- `403` — нет прав;
- `404` — объект не найден или недоступен;
- `409` — конфликт состояния, например несоответствие частей перевода;
- `422` — бизнес-валидация;
- `429` — превышение rate limit;
- `500` — внутренняя ошибка.

Сообщение ошибки должно содержать:

- машинный код;
- понятное сообщение;
- идентификатор запроса;
- список ошибок полей для форм — если применимо.

Внешнему пользователю нельзя показывать stack trace, SQL, секреты и внутренние пути.

## 6. База данных и финансовая точность

### 6.1. PostgreSQL

Основная СУБД — PostgreSQL 18.x.

PostgreSQL 17 допускается только как временный fallback, если выбранный managed-провайдер еще не предлагает PostgreSQL 18. Версия должна быть зафиксирована в инфраструктурном решении, а перенос на PostgreSQL 18 — отдельная задача.

Production-база должна быть managed-сервисом либо иметь эквивалентные возможности:

- автоматические резервные копии;
- point-in-time recovery;
- шифрование;
- мониторинг;
- ограничение сетевого доступа;
- документированное восстановление.

### 6.2. Денежные значения

Запрещено использовать `float`, `double` и JavaScript floating-point arithmetic как источник истины для денег.

Рекомендуемая модель:

```text
amount_minor BIGINT
currency     CHAR(3)
scale        SMALLINT
```

Для RUB:

- валюта `RUB`;
- scale `2`;
- 1 000 ₽ хранится как 100000 минимальных единиц.

На границе API сумма принимается как десятичная строка, например `"106000.00"`, затем валидируется и преобразуется в минимальные единицы. В ответе можно отдавать и минимальные единицы, и безопасное форматированное представление по контракту.

Все операции сложения, вычитания и сравнения выполняются:

- в базе через `BIGINT`;
- в backend через integer/decimal-safe код;
- в транзакции;
- с проверкой переполнения.

### 6.3. Основные таблицы

Минимальный набор таблиц:

```text
users
sessions
workspaces
workspace_memberships
budgets
accounts
envelopes
categories
transactions
transaction_metadata
income_allocations
transfers
transfer_parts
recurring_plans
plan_occurrences
notifications
audit_events
exports
background_jobs
```

Некоторые таблицы будущих функций можно создать позже, но ключи бюджета и рабочего пространства должны быть предусмотрены сразу.

### 6.4. Общие поля сущностей

Для всех изменяемых бизнес-сущностей использовать:

- `id`;
- `budget_id` или `workspace_id`, если применимо;
- `created_at`;
- `updated_at`;
- `created_by`, если применимо;
- `updated_by`, если применимо;
- `archived_at` либо `deleted_at`, если используется soft delete.

Временные значения хранятся в UTC. Отображение выполняется в часовом поясе бюджета.

### 6.5. Идентификаторы

Идентификаторы внешних сущностей должны быть непрозрачными для пользователя. Рекомендуется UUIDv7, генерируемый приложением или поддерживаемой библиотекой.

Нельзя использовать последовательный integer ID как единственный внешний идентификатор финансовых объектов.

### 6.6. Изоляция бюджета

Каждая таблица, содержащая пользовательские финансовые данные, должна иметь путь к `budget_id` либо безопасную связь через сущность, принадлежащую бюджету.

Доступ проверяется в application service и repository query.

Запросы должны включать ограничение по бюджету в самом запросе, а не фильтровать чужие строки после получения данных.

Обязательны:

- составные уникальные индексы с `budget_id`;
- внешние ключи;
- check constraints для положительных сумм и допустимых статусов;
- индексы по часто используемым фильтрам;
- запрет удаления родительской сущности, если это нарушает аудит или историю.

### 6.7. Статусы операций

Рекомендуемые статусы:

```text
DRAFT
CONFIRMED
CANCELLED
DELETED
```

В расчетах участвуют только `CONFIRMED`.

Логическое удаление записывает:

- дату удаления;
- пользователя;
- причину — если введена;
- audit event.

### 6.8. Транзакционные сценарии

Следующие действия выполняются в одной транзакции БД:

- создание дохода и связанных начальных данных, если они создаются одним подтверждением;
- создание расхода;
- создание распределения дохода;
- создание перевода и всех его частей;
- изменение операции с пересчетом зависимостей;
- логическое удаление операции;
- восстановление операции;
- подтверждение операции из регулярного плана.

Если любой шаг не выполнен, все изменения откатываются.

### 6.9. Финансовые инварианты

Бэкенд обязан проверять:

1. Сумма операции положительна.
2. Валюта операции совпадает с валютой счета в v1.
3. Доход существует до создания распределения.
4. Сумма распределений не превышает доход.
5. Сумма частей перевода равна общей сумме перевода.
6. Исходный и целевой счет перевода различаются.
7. Архивированный счет нельзя выбрать для новой операции.
8. В расчеты попадают только подтвержденные операции.
9. Доход `Шабашка` при включенном правиле предлагается распределять в `Ремонт`.
10. Общий баланс счетов при переводе не изменяется.
11. Обычный перевод не изменяет общий баланс конвертов.
12. Все связанные сущности принадлежат одному бюджету.
13. Запрос повторной отправки не создает вторую операцию.

### 6.10. Расчетные представления и кеш

Для v1 сначала использовать SQL-агрегации и индексы. Не материализовать все балансы вручную без необходимости.

Если производительность потребует кеша:

- кеш не является источником истины;
- у каждого значения есть понятная стратегия инвалидирования;
- после мутаций расчет можно восстановить из PostgreSQL;
- ошибочный или устаревший кеш не должен приводить к сохранению неверной операции.

## 7. Авторизация и безопасность реализации

### 7.1. Сессии

Для web v1 использовать серверные сессии:

- cookie `HttpOnly`;
- `Secure` в production;
- `SameSite=Lax` либо более строгая политика при совместимости;
- срок бездействия сессии — 30 дней; абсолютный срок — 90 дней; значения можно изменить после threat modeling без изменения финансовой модели;
- ротация идентификатора после входа;
- отзыв сессии при выходе и смене пароля;
- возможность завершить все сессии.

Не хранить auth-токены в `localStorage`.

Для будущих мобильных клиентов и Telegram можно добавить отдельный token/OAuth flow, не меняя web-сессию.

### 7.2. Пароли

- Argon2id;
- минимальная длина — 10 символов;
- rate limit входа и восстановления;
- временные одноразовые токены восстановления;
- токены восстановления не хранятся в открытом виде;
- пароль никогда не попадает в логи, audit или ответы API.

### 7.3. Авторизация объектов

До выполнения любого действия проверять:

```text
authenticated user
→ workspace membership
→ budget access
→ role permission
→ object belongs to budget
→ operation allowed for object state
```

Проверки должны быть централизованы в guards/policies/application services. Нельзя дублировать их только в контроллерах или интерфейсе.

### 7.4. Защита API

- schema validation всех входных данных;
- ограничение размера запроса;
- rate limiting для auth и дорогостоящих отчетов;
- защита от CSRF для cookie-based mutations;
- security headers;
- CORS только для явно разрешенных origins;
- отсутствие подробных ошибок в production;
- request ID и безопасное трассирование;
- проверка content type;
- запрет неожиданных полей через DTO validation;
- идемпотентность критических mutation endpoints.

### 7.5. Секреты

Секреты нельзя хранить в Git, Dockerfile или клиентском bundle.

Секреты должны поступать через:

- secret manager облачного провайдера;
- защищенные secrets CI/CD;
- локальный `.env` вне Git.

Разные среды используют разные:

- ключи cookie;
- credentials БД;
- ключи мониторинга;
- ключи почтового сервиса — если будет нужен reset email;
- ключи object storage.

### 7.6. Персональные данные

Приложение должно собирать только данные, необходимые для работы.

Не хранить:

- полные номера банковских карт;
- CVV;
- банковские пароли;
- логины интернет-банка;
- секретные платежные реквизиты.

До публичного запуска необходимо провести отдельную юридическую проверку требований к обработке персональных данных и выбрать регион хранения с учетом целевой аудитории. Техническая спецификация не является юридическим заключением.

## 8. Фоновые задачи и уведомления

### 8.1. Worker

Фоновые задачи выполняются отдельным процессом `worker`.

Worker отвечает за:

- создание уведомлений по регулярным планам;
- проверку просроченных планов;
- уведомления о нераспределенном доходе;
- подготовку тяжелых отчетов — если потребуется;
- генерацию экспортов;
- очистку истекших технических данных.

### 8.2. Хранение задач

Для v1 использовать устойчивое хранилище задач на PostgreSQL. Состояние задачи не должно храниться только в памяти процесса.

У задачи должны быть:

- идентификатор;
- тип;
- payload с версией схемы;
- статус;
- количество попыток;
- время следующей попытки;
- время блокировки;
- время выполнения;
- ошибка без секретных данных;
- idempotency key.

Должна быть защита от параллельного выполнения одной задачи несколькими worker-инстансами.

Redis не добавляется в v1 без подтвержденной потребности. Если позже потребуется Redis/BullMQ или другой брокер, он должен быть введен отдельным архитектурным решением.

### 8.3. Повторные попытки

Для временных ошибок использовать ограниченное число retry с backoff.

Не повторять автоматически операции, которые могут привести к повторному финансовому движению, без idempotency.

После исчерпания попыток задача переводится в состояние, видимое в мониторинге.

### 8.4. Планировщик

Планировщик должен быть устойчивым к:

- рестарту API;
- рестарту worker;
- задержке выполнения;
- запуску нескольких реплик;
- переходу через полночь и часовые пояса;
- повторному выполнению после сбоя.

Уведомление о регулярном плане должно быть уникальным для конкретного возникновения плана и типа уведомления.

## 9. Экспорт и объектное хранилище

Экспорт относится к v1, но сложные или большие файлы не должны формироваться в HTTP-запросе без ограничений.

Рекомендуемый flow:

```text
Пользователь запрашивает экспорт
→ API создает export job
→ worker формирует файл
→ файл сохраняется в S3-compatible storage
→ пользователь получает уведомление
→ API выдает временную подписанную ссылку
```

Требования:

- ссылка имеет срок действия;
- доступ к файлу проверяет пользователя и бюджет;
- файлы не публикуются в открытом доступе;
- экспорт не содержит данные другого бюджета;
- старые временные файлы удаляются по политике хранения;
- ошибки экспорта видны пользователю и в мониторинге.

Если экспорт v1 мал по объему, допустимо начать с синхронного ответа, но API-контракт не должен препятствовать переходу на фоновые задачи.

## 12. Тестирование

### 12.1. Unit-тесты

Обязательно тестировать без HTTP и реальной сети:

- расчет начала цикла;
- расчет периода;

- изоляцию бюджетов;

### 12.4. E2E-тесты

5. добавление фактического дохода 99 000 ₽;
6. добавление дохода 106 000 ₽;
7. распределение дохода по конвертам;
8. добавление шабашки и направление в ремонт;
9. добавление расхода;
10. создание перевода из нескольких частей;
11. создание операции из плана;
12. просмотр дашборда;
13. просмотр аналитики;
14. редактирование операции;
15. удаление и восстановление;
16. просмотр аудита;
17. выход и восстановление пароля.

### 12.5. Нагрузочные проверки

До production проверить:

- типичный список операций;
- отчет за несколько циклов;
- параллельное добавление операций;
- повторные запросы summary;
- одновременную обработку worker-задач;
- восстановление после недоступности БД.

Целевые показатели из функционального ТЗ:

- главная страница — до 3 секунд при нормальном соединении;
- результат mutation — до 1 секунды после ответа сервера;
- фильтрация типичного журнала — до 2 секунд.

## 13. CI/CD

### 13.1. Pull Request pipeline

Каждый Pull Request должен запускать:

1. установку по lock-файлу;
2. проверку форматирования;
3. ESLint;
4. TypeScript typecheck;
5. unit-тесты;
6. интеграционные тесты;
7. проверку Prisma schema и миграций;
8. OpenAPI lint и breaking-change check;
9. сборку web, api и worker;
10. сборку Docker image;
11. базовое сканирование зависимостей и образов;
12. E2E smoke-тесты — минимум для ветки staging.

### 13.2. Staging deploy

После прохождения pipeline:

- собираются неизменяемые образы с commit SHA;
- выкатывается staging;
- применяются только staging secrets;
- запускаются миграции в контролируемом шаге;
- выполняются health-check и smoke-тесты;
- результат публикуется в PR.

### 13.3. Production deploy

Production deploy выполняется после:

- прохождения всех обязательных проверок;
- ручного approval для v1;
- проверки совместимости миграции;
- наличия резервной копии перед потенциально опасной миграцией;
- подтверждения smoke-теста staging.

После деплоя:

- проверяется готовность web, API и worker;
- проверяется подключение к БД;
- проверяется создание тестового безопасного health-запроса;
- отслеживаются ошибки и latency;
- при критическом ухудшении выполняется rollback образа либо заранее подготовленный план отката миграции.

### 13.4. Миграции

Миграции базы данных:

- хранятся в Git;
- применяются отдельно от запуска приложения, если это требуется выбранным runtime;
- backward-compatible для rolling/перезапуска;
- не удаляют и не переименовывают данные без отдельного этапа;
- для крупных изменений используют expand/contract-подход;
- проверяются на staging-копии схемы.

Нельзя автоматически откатывать production migration деструктивной командой.

## 14. Рекомендуемая стратегия деплоя

### 14.1. Основной вариант v1

Рекомендуется:

- один cloud/VPS host для приложений;
- Docker Compose для web, API, worker и reverse proxy;
- managed PostgreSQL отдельно от host приложений;
- S3-compatible object storage отдельно;
- DNS и TLS через cloud provider/CDN/reverse proxy;
- CI/CD с автоматическим deploy staging и ручным deploy production.

### 14.2. Production-топология

```text
Internet
   │
   ▼
DNS + CDN/WAF + TLS
   │
   ▼
Reverse proxy / ingress
   ├── web container (Nuxt)
   ├── api container (NestJS/Fastify)
   └── health endpoints
          │
          ├── managed PostgreSQL 18
          ├── object storage
          └── worker container
```

Для небольшого v1 web, API и worker могут жить на одном host, но это должны быть отдельные контейнеры с отдельными health-check и restart policy.

PostgreSQL не следует размещать единственной копией на том же host, что и приложение.

### 14.3. Reverse proxy

Reverse proxy должен обеспечивать:

- TLS termination;
- redirect HTTP → HTTPS;
- проксирование web и API;
- request size limits;
- базовые security headers;
- health checks;
- graceful shutdown;
- корректную передачу request ID.

Можно использовать Caddy, Nginx, Traefik или managed ingress. Выбор не должен менять API-контракт и контейнерную модель.

### 14.4. Выбор облачного провайдера

Для российской аудитории можно рассматривать:

- Yandex Cloud;
- VK Cloud;
- Selectel;
- другой провайдер с managed PostgreSQL и S3-compatible storage.

Для международной аудитории можно рассматривать любой провайдер с:

- managed PostgreSQL;
- container hosting или VM;
- object storage;
- secret manager;
- backup/PITR;
- приемлемой юрисдикцией и SLA.

Критерии выбора:

1. Регион хранения данных.
2. Применимые требования к персональным данным.
3. Доступность PostgreSQL 18 либо прозрачная стратегия PostgreSQL 17 → 18.
4. PITR и срок хранения резервных копий.
5. SLA и зоны доступности.
6. Стоимость на этапе v1 и при росте.
7. Доступность managed secrets и object storage.
8. Возможность переноса контейнеров без переписывания приложения.
9. Доступность платежей и поддержки для целевой юрисдикции.
10. Скорость и стабильность сетевого доступа.

Провайдер и тариф выбираются отдельным операционным решением после оценки целевого рынка. Основной production-домен зафиксирован как `HarmoFin.ru`, но не должен зашиваться в код: адреса web/API задаются конфигурацией для каждой среды.

### 14.5. Среды

Обязательны:

```text
local       разработка
staging     приемка и интеграционные проверки
production  реальные данные
```

Правила:

- отдельная БД на каждую среду;
- отдельные credentials;
- отдельные bucket/prefix;
- отдельные ключи мониторинга;
- production secrets не доступны PR pipeline;
- production данные не копируются в staging без обезличивания;
- staging должен иметь возможность полностью пересоздаваться.

### 14.6. Docker

Каждый процесс имеет свой production image либо отдельный target multi-stage Dockerfile:

- `web`;
- `api`;
- `worker`.

Образы должны:

- запускаться от non-root пользователя;
- не содержать исходные секреты;
- иметь фиксированный base image digest либо управляемую политику обновления;
- иметь health endpoint/check;
- корректно обрабатывать SIGTERM;
- иметь минимальный runtime-слой;
- проходить сканирование уязвимостей.

Для production Compose должны быть заданы:

- restart policies;
- resource limits;
- health checks;
- отдельные volumes только для нужных ephemeral данных;
- сеть с минимально необходимыми связями;
- production override-конфигурация.

### 14.7. Бэкапы и восстановление

Целевые показатели v1:

- RPO — не более 1 часа;
- RTO — не более 4 часов.

Необходимы:

- автоматические backup;
- point-in-time recovery;
- копия резервных данных в отдельном failure domain, если поддерживается;
- шифрование;
- политика retention;
- documented restore runbook;
- регулярная практическая проверка восстановления.

Бэкап считается пригодным только после успешного восстановления тестовой среды и проверки целостности данных.

### 14.8. Деплой без простоя

Для одного host в v1 допустима короткая controlled restart, если она укладывается в согласованный SLA. При росте перейти к:

- нескольким API-репликам;
- rolling/blue-green deploy;
- managed load balancer;
- отдельному worker pool.

Миграции должны быть совместимы с версией приложения до и после переключения.

## 15. Наблюдаемость и эксплуатация

### 15.1. Логи

Логи должны быть структурированными и содержать:

- timestamp;
- level;
- service;
- environment;
- request ID;
- user ID — только если допустимо политикой приватности;
- budget ID — только в обезличенном/контролируемом виде;
- duration;
- error code.

Не логировать:

- пароли;
- cookies;
- session secrets;
- полные финансовые payload;
- платежные реквизиты;
- содержимое пользовательских комментариев без необходимости.

### 15.2. Метрики

Минимальные метрики:

- HTTP request count/latency/error rate;
- database query latency;
- connection pool usage;
- worker queue depth;
- failed/retried jobs;
- notification creation failures;
- export failures;
- login failures;
- resource usage контейнеров;
- backup status.

### 15.3. Tracing и ошибки

Использовать OpenTelemetry-compatible instrumentation там, где это доступно.

Sentry или аналог должен получать:

- stack trace;
- release/version;
- environment;
- request/correlation ID;
- безопасный контекст.

Перед отправкой ошибки удалять финансовые payload и секреты.

### 15.4. Health endpoints

API должен иметь отдельные проверки:

```text
/live   процесс запущен
/ready  процесс готов принимать запросы и имеет нужные зависимости
```

Readiness должен учитывать доступность базы данных и обязательных runtime-зависимостей, но не должен раскрывать секреты или внутреннюю конфигурацию.

### 15.5. Runbooks

До production подготовить инструкции:

- deploy;
- rollback;
- восстановление БД;
- ротация секретов;
- сбой worker;
- недоступность PostgreSQL;
- рост ошибок API;
- очистка зависших jobs;
- реагирование на подозрительную активность;
- удаление аккаунта и выгрузка данных.

## 17. Будущие интеграции

### 17.1. Совместный доступ

Текущие сервисы должны принимать `workspace_id`, `budget_id`, `actor_id` и роль из request context, даже если v1 использует только владельца.

Добавление редактора и наблюдателя должно расширять policies, а не требовать переписывания контроллеров и таблиц.

### 17.2. Импорт выписок

Импорт CSV/XLSX не входит в v1.

Техническая подготовка:

- источник операции должен быть расширяемым;
- внешний идентификатор операции должен быть необязательным полем;
- endpoint создания операции должен поддерживать idempotency;
- staged/imported статус не должен попадать в финансовые расчеты до подтверждения;
- deduplication не должна быть реализована частично в ручном вводе.

### 17.3. Telegram

Уведомления должны создаваться независимо от канала доставки.

Будущий канал Telegram подключается через:

```text
Notification rule
→ Notification record
→ Delivery channel adapter
→ Delivery attempt/status
```

Правила бюджета не должны напрямую зависеть от Telegram SDK.

### 17.4. ИИ

ИИ не получает прямой доступ к PostgreSQL.

Будущая интеграция использует ограниченный аналитический слой:

```text
Budget analytics service
→ minimized structured context
→ AI provider adapter
→ answer with source period and confidence/limitations
```

ИИ:

- не может сам изменять операции;
- не получает пароли и платежные реквизиты;
- получает только разрешенные бюджеты;
- не должен получать лишние персональные данные;
- все действия изменения проходят обычный API и подтверждение пользователя;
- provider-specific SDK скрывается за adapter.

### 17.5. Мультивалютность

В v1 поддерживается RUB. Поля валюты присутствуют в денежных сущностях.

Полноценная мультивалютность потребует отдельного решения по:

- курсам;
- дате курса;
- конверсиям;
- базовой валюте отчета;
- переоценке;
- округлению;
- историческим значениям.

Она не должна быть включена простым снятием ограничения `RUB`.

## 18. Архитектурные запреты и анти-паттерны

Запрещается:

1. хранить денежные суммы как float;
2. рассчитывать баланс только в браузере;
3. хранить auth-секреты в localStorage;
4. создавать микросервисы до появления потребности;
5. размещать единственную production-базу на том же host без backup/PITR;
6. дублировать бизнес-правила в каждом контроллере;
7. создавать фиктивные операции при распределении дохода;
8. считать перевод доходом или расходом;
9. удалять финансовые записи физически без отдельного согласованного процесса;
10. применять migration с необратительным удалением данных без backup и плана восстановления;
11. использовать in-memory cron как единственный планировщик в multi-instance окружении;
12. отправлять в мониторинг полные пользовательские финансовые payload;
13. передавать ИИ прямой доступ к базе;
14. добавлять Redis/Kubernetes только «на будущее»;
15. смешивать server-only код с клиентским bundle.

## 21. Инфраструктурные критерии приемки

### Локальная среда

- новый разработчик запускает проект по README;
- локальная БД создается одной документированной командой;
- seed создает демонстрационный бюджет;
- тесты запускаются без production secrets.

### CI

- Pull Request блокируется при ошибке typecheck, lint, test, build или contract check;
- Docker images собираются без ручного изменения кода;
- миграции проверяются на чистой и существующей схеме;
- артефакт содержит commit SHA.

### Staging

- deploy выполняется воспроизводимо;
- health-check проходит;
- smoke-тест создает и удаляет тестовые данные безопасным способом;
- staging не имеет доступа к production базе.

### Production

- web, API и worker перезапускаются отдельно;
- приложение не запускается с отсутствующими обязательными настройками;
- backup настроен;
- восстановление документировано и проверено;
- доступ к БД ограничен;
- TLS включен;
- мониторинг ошибок активен;
- rollback-процедура проверена.

## 25. Итог

- идемпотентность;
- резервное копирование;
- наблюдаемость;

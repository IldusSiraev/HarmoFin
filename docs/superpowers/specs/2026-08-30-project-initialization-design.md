# Дизайн инициализации репозитория HarmoFin

**Дата:** 30.08.2026
**Статус:** согласовано
**Область:** только репозиторная метаинформация; scaffold приложений, зависимости, Docker и CI не входят в эту работу

## 1. Цель

Подготовить чистую и воспроизводимую основу репозитория HarmoFin перед созданием monorepo. Основа должна фиксировать назначение продукта, источники требований, правила работы с кодовой базой и базовые настройки Git и редакторов.

## 2. Результат

В корне проекта создаются:

- `README.md`;
- `CLAUDE.md`;
- `.gitignore`;
- `.gitattributes`;
- `.editorconfig`.

Каталог инициализируется как Git-репозиторий с основной веткой `main`.

В репозиторий включаются:

- функциональное ТЗ `docs/superpowers/specs/2026-08-30-family-budget-app-spec.md`;
- спецификация разработки `docs/superpowers/specs/2026-08-30-family-budget-development-spec.md`;
- этот документ;
- `categories.txt`.

Удалённый Excel-план не восстанавливается и не включается в репозиторий.

## 3. README

`README.md` должен содержать:

- краткое описание HarmoFin;
- текущий статус проекта: проектирование завершено, приложения ещё не созданы;
- границы MVP;
- утверждённый технологический стек;
- целевую структуру monorepo;
- ссылки на функциональное ТЗ и спецификацию разработки;
- этапы разработки;
- честное указание, что команды установки и запуска пока отсутствуют;
- краткие правила безопасности;
- указание, что права на использование не предоставлены, пока файл `LICENSE` отсутствует.

README не должен документировать команды, которых ещё нет в проекте.

## 4. CLAUDE.md

`CLAUDE.md` должен давать агентам краткий, достаточный контекст без копирования полного ТЗ. Документ фиксирует:

- приоритет функционального ТЗ для поведения продукта и спецификации разработки для технической реализации;
- границы MVP;
- архитектуру модульного монолита;
- основные финансовые инварианты;
- требования к точности денежных расчётов;
- изоляцию данных по бюджету;
- требования безопасности;
- правила TypeScript, API, PostgreSQL, миграций и тестирования;
- запрет использовать или описывать несуществующие команды;
- обязанность обновить README после появления реальных команд;
- русский язык для документации и пользовательского интерфейса, английский для идентификаторов кода, API и схемы БД;
- ссылки на исходные документы вместо их полного дублирования.

## 5. Репозиторные настройки

### `.gitignore`

Игнорируются:

- локальные файлы `.superpowers/`;
- настройки IDE и ОС;
- зависимости Node.js;
- результаты сборки Nuxt, NestJS и TypeScript;
- coverage, временные файлы и логи;
- локальные базы и runtime-данные;
- `.env` и производные файлы с секретами.

Будущий `.env.example` не игнорируется.

### `.gitattributes`

Текстовые файлы нормализуются в LF. Бинарные форматы помечаются как бинарные. Настройка должна предотвращать случайные массовые изменения строк между Windows и Linux.

### `.editorconfig`

Базовые правила: UTF-8, LF, финальная новая строка, удаление хвостовых пробелов и отступ в 2 пробела для будущего TypeScript/JSON/YAML/Markdown, кроме случаев, где формат требует иного.

## 6. Git

Репозиторий создаётся командой, эквивалентной `git init -b main`. Remote не настраивается.

После создания и проверки файлов формируется первый commit:

```text
chore: initialize HarmoFin repository
```

Если локальная идентификация автора Git не настроена, файлы и индекс подготавливаются, но фиктивные значения `user.name` или `user.email` не задаются. Блокировка commit явно сообщается пользователю.

## 7. Проверка

Перед завершением необходимо проверить:

1. текущая ветка называется `main`;
2. ожидаемые файлы существуют;
3. удалённый Excel-план отсутствует;
4. `.superpowers/`, секреты, IDE-файлы и build outputs не попадают в индекс;
5. ссылки README и CLAUDE указывают на существующие документы;
6. tracked-файлы соответствуют согласованному объёму;
7. рабочее дерево чистое после первого commit.

## 8. Вне области работы

Не создаются:

- `apps/`, `packages/`, Prisma schema и инфраструктурные каталоги;
- `package.json`, workspace-конфигурация и lock-файл;
- зависимости;
- Docker и Docker Compose;
- GitHub Actions;
- application code и тесты;
- remote repository;
- LICENSE, CONTRIBUTING, SECURITY и GitHub-шаблоны.

Эти элементы добавляются отдельными этапами после согласования соответствующего плана.

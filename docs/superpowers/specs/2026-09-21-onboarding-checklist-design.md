# Дизайн: чек-лист первого запуска (онбординг)

Дата: 2026-09-21

## 1. Контекст и проблема

HarmoFin в проде, реальных пользователей пока нет — владелец продукта первый тестировщик. При прогоне сценария «начинаю пользоваться приложением с нуля» выяснилось: новому пользователю нужно вручную и в правильном порядке дойти до `/app/settings` (шаблон категорий/конвертов + финансовый цикл), `/app/accounts`, `/app/envelopes` и создать первую операцию дохода с распределением — без какой-либо подсказки о порядке или смысле шагов. Часть шагов физически существует (кнопка «Создать базовый шаблон» и настройки цикла в `apps/web/app/pages/app/settings/index.vue`), но ничем не выделена среди прочих настроек.

Важное расхождение с изначальной постановкой задачи: создание бюджета **не** сеет базовые категории/конверты автоматически (`apps/api/src/budgets/budget.application.service.ts:31-41` создаёт только голую запись `Budget`). Заполнение шаблоном — отдельное идемпотентное действие `POST /budgets/:budgetId/reference-template` (`apps/api/src/budgets/budget.controller.ts:104-120`), которое сегодня доступно только через кнопку в `/app/settings`. Поэтому шагов в чек-листе пять, а не четыре.

## 2. Цели / не цели

Цели:
- Дать новому пользователю единую точку входа на дашборде, которая по порядку ведёт через 5 шагов первоначальной настройки, объясняя каждый простыми словами на русском.
- Не дублировать финансовую логику на фронтенде — весь расчёт готовности шага и агрегатов остаётся на сервере.
- Не создавать новые страницы/маршруты — чек-лист только показывает статус и ссылается на уже существующие страницы.

Не цели:
- Не переписываем существующие страницы accounts/envelopes/operations и их формы.
- Не делаем модальный wizard, блокирующий дашборд.
- Не добавляем хранение «пользователь закрыл подсказку навсегда» — статус шагов целиком выводится из реальных данных бюджета.

## 3. Изменение дефолта финансового цикла

Текущий дефолт (`prisma/schema.prisma:228-231`, продублирован в функциональной спецификации `docs/superpowers/specs/2026-08-30-family-budget-app-spec.md:227-228`) — `cycleStartDay = 10`, `periodBoundaryOffset = 15`. Это осмысленное значение только для конкретного сценария автора спеки (аванс 25-го, расчёт 10-го), но приложение рассчитано на разных пользователей.

Новый дефолт: `cycleStartDay = 1`, `periodBoundaryOffset = 15` — календарный месяц, разбитый на два периода: 1–15 и 16–конец месяца. Это привычнее для пользователей, не привязанных к схеме «аванс/зарплата 10/25», и даёт чёткий сигнал «настройки цикла ещё не трогали» (см. §5).

Требуются правки (выполняются в рамках плана реализации, не в этом документе):
- `prisma/schema.prisma` — новые `@default` для `cycleStartDay`/`periodBoundaryOffset` + миграция (только смена дефолта колонки, без изменений существующих строк).
- Функциональная спецификация `docs/superpowers/specs/2026-08-30-family-budget-app-spec.md`:
  - строки 227–228 — новый дефолт;
  - раздел 9.1 (строки 435–440) и 9.2 (строки 446–449) сейчас поданы как «для текущего бюджета» = 10/15; переформулировать как иллюстративный пример настройки («например, если аванс 25-го, а расчёт 10-го, можно настроить цикл с началом 10-го и границей 15 дней»), а не как описание дефолта;
  - таблица примеров 9.3 (строки 453–463) не описывает дефолт напрямую (это иллюстрация алгоритма), можно оставить как есть или продублировать вторым примером для 1/15 — решить в плане реализации.
- Тесты в `apps/api/src/budgets/**` и `apps/api/src/dashboard/**`, которые сейчас полагаются на дефолт 10/15 (список — в плане реализации).

Шаблонные ключи конвертов (`envelope-current-10-24`, `envelope-current-25-9` в `apps/api/src/budgets/budget.repository.ts:824-831`) — это внутренние идентификаторы, отображаемые названия конвертов общие («Первый период», «Второй период»), дат в UI нет — переименование ключей не требуется.

## 4. Backend: расширение `GET /dashboard/summary`

Новый объект `onboarding` в `DashboardSummaryResponse` (`apps/api/src/dashboard/dashboard.dto.ts`), вычисляется в `dashboard.repository.ts`/`dashboard.application.service.ts` — тот же паттерн, что уже применён для `unassignedStartingBalanceMinor` (коммит 07809e5).

```
onboarding: {
  categoriesSeeded: boolean;          // есть активная категория ИЛИ конверт
  cycleConfigured: boolean;           // cycleStartDay !== 1 || periodBoundaryOffset !== 15
  hasAccounts: boolean;               // есть неархивный счёт
  hasEnvelopeStartingBalances: boolean; // сумма startingBalance неархивных конвертов ≠ 0
  hasAllocatedIncome: boolean;        // есть CONFIRMED операция дохода хотя бы с одним распределением
}
```

Правила вычисления:
- `categoriesSeeded` намеренно не привязан к факту нажатия кнопки шаблона — считается выполненным, если у бюджета вообще есть базовые данные (шаблон или созданные вручную категории/конверты). Это соответствует принципу «статус выводится из реальных данных, а не из истории действий».
- `cycleConfigured` — простая проверка отличия текущих значений от нового дефолта (1/15). Так как единственный способ изменить эти поля — `PATCH /budgets/:id`, который создаёт `AuditEvent` (`apps/api/src/budgets/budget.repository.ts:157-169`), достаточно сравнить текущие значения с дефолтом — не нужен отдельный запрос к журналу аудита. Известное ограничение: если пользователь осознанно оставит дефолт 1/15, шаг будет вечно показывать «не подтверждено» — это некритично, шаг не блокирующий.
- `hasAllocatedIncome` — требует join операций (`type = INCOME`, `status = CONFIRMED`) и распределений (`IncomeAllocation`, `amountMinor > 0`) в рамках бюджета.

OpenAPI-спека и её снэпшот (`pnpm --filter api openapi` / соответствующая команда генерации) обновляются вместе с DTO — версия `/api/v1` не ломается, поле аддитивное.

## 5. Frontend: компонент чек-листа

Новый компонент `apps/web/app/components/dashboard/OnboardingChecklist.vue`, подключается в `apps/web/app/pages/app/index.vue` рядом с `DashboardWarnings.vue`, получает данные из того же вызова dashboard summary (`useBudgetReferenceData`/аналогичный composable, расширить типы `DashboardSummaryResponse`).

Карточка (оформление по `docs/superpowers/specs/2026-09-17-calm-fintech-visual-guidelines.md`: `UiCard`, токены `--hf-color-*`, иконки только из `@lucide/vue`) со списком из 5 строк-шагов. Каждая строка:
- иконка статуса (заполненный кружок с галочкой / пустой контур) — дублируется текстом («Готово» / «Не начато»), не только цветом, по требованию доступности CLAUDE.md;
- заголовок шага;
- короткое пояснение на русском (1–2 предложения, всегда видимое текстом, не в тултипе — тултип на hover хуже для клавиатуры/скринридеров/тач-устройств);
- кнопка-ссылка (`UiButton` variant="tertiary" size="sm", как существующая кнопка шаблона в `settings/index.vue:157-165`) на нужную страницу.

Тексты шагов:

1. **Базовые категории и конверты** — «Создайте набор стандартных категорий и конвертов одним нажатием — их можно будет менять позже.» → `/app/settings`
2. **Финансовый цикл** — «Финансовый месяц не обязан начинаться 1-го числа — настройте день, который соответствует вашему графику доходов.» → `/app/settings`
3. **Счета** — «Добавьte счета, на которых реально лежат деньги, с их текущим остатком.» → `/app/accounts`
4. **Начальные остатки конвертов** — «Разнесите деньги со счетов по конвертам — так вы увидите, что уже распределено, а что нет.» → `/app/envelopes`
5. **Первый доход и распределение** — «Добавьте операцию дохода и распределите её по конвертам — это включит расчёт доступного лимита периода.» → страница операций (открытие `OperationDrawer` с типом «Доход»)

Поведение карточки:
- Пока не все 5 шагов выполнены — карточка видна вверху дашборда.
- Кнопка «Свернуть» сворачивает карточку в компактный пилл «Начало работы: N/5»; повторный клик разворачивает обратно. Состояние свёрнуто/развёрнуто хранится в `localStorage` — это чисто UI-предпочтение, не связано с готовностью шагов и не блокирует их пересчёт.
- Когда все 5 полей `onboarding.*` истинны — карточка и пилл полностью исчезают, без ручного дизмисса.

Доступность: все интерактивные элементы — обычные фокусируемые кнопки/ссылки, видимый фокус по токенам темы, `aria-live` для изменения статуса шага не требуется (статус меняется при переходе на другую страницу и обратно, а не в реальном времени на этой же странице).

## 6. Тестирование

- Backend: unit-тесты на новые поля `onboarding.*` в `dashboard.repository.spec.ts` / `dashboard.application.service.spec.ts` (все 5 полей, включая граничные случаи — ноль счетов, ноль конвертов, доход без распределения); unit-тесты на новый дефолт цикла в `apps/api/src/budgets/*.spec.ts`.
- Frontend: component-тест `OnboardingChecklist.vue` (рендер 5 строк, статус текстом и иконкой, скрытие при всех true, сворачивание/разворачивание).
- Playwright e2e: новый сценарий — регистрация нового пользователя → чек-лист показывает 5/5 невыполненных → последовательное прохождение всех шагов через реальные страницы → чек-лист исчезает. Выполняется только в CI, локально не гоняем (см. правило [Playwright CI only]).

## 7. Риски / ограничения

- Смена дефолта цикла — поведенческое изменение для новых бюджетов, требует синхронной правки функциональной спецификации, иначе документ разойдётся с кодом.
- Шаг «финансовый цикл» может вечно висеть невыполненным для пользователей, сознательно оставляющих дефолт 1/15 — принято как допустимый компромисс (шаг не блокирующий).
- `hasAllocatedIncome` требует join двух таблиц в уже существующем dashboard-запросе — держать запрос в пределах текущего бюджета (`budgetId`), без утечки данных других бюджетов.

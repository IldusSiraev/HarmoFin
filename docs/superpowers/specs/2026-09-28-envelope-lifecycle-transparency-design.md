# Прозрачность жизненного цикла конвертов — дизайн

- Дата: 2026-09-28 (снимок данных пользователя 26.09.2026, домен v1)
- Статус: дизайн, согласовать с владельцем продукта; реализация — отдельным планом
- Источник боли: реальный бюджет «Семейный бюджет» (workspace owner `i_siraev@mail.ru`), снимок 2026-09-26:
  - в архивных конвертах заморожено **139 738,76 ₽** (пустой дубль «Обязательные» 89 000,00 + остаток «Обязательные» 50 738,76), пользователь не может их найти и вернуть;
  - три конверта «Обязательные» (архив → архив → активный), каждый перенос остатка делался вручную с пересчётами;
  - «Второй период» создавался с отрицательным стартовым балансом (−53 115,00 ₽) — домашний бухгалтерский трюк ради сходимости сумм;
  - 14 842,00 ₽ распределены в конверт, архивированный через пару минут;
  - счёт «Промежуточный конверт» (20 035,56 ₽) не привязан ни к одному конверту.
- Формула баланса конверта не меняется: `starting_balance + Σ подтверждённые распределения доходов − Σ подтверждённые расходы − переводы (в конверт − из конверта) + реаллокации (входящие − исходящие)`.

## 1. Проблемы (что чиним)

| № | Проблема | Факт |
|---|---|---|
| P1 | Архивация конверта с остатком = деньги выпадают из всех активных балансов | 139 738,76 ₽ в двух архивных конвертах |
| P2 | Нет операции «заменить конверт», только ручной пересчёт | три «Обязательные» |
| P3 | Состав баланса конверта невидим | вопрос «куда деть 37 130,62» неотвечаем в UI |
| P4 | Нет предупреждений о судьбе денег при распределении/переводе | 14 842,00 в обречённый конверт |
| P5 | Переход между «Первый/Второй период» — ручная магия | отрицательный старт −53 115,00; «Первый период» вручную обнулён |

## 2. Границы

**В скоупе этого дизайна:** API + UI операции над конвертами (архив, замена, переносы), валидации, видимость замороженных остатков, предпросмотр последствий операций.

**Не в скоупе:** новые правила расчёта денег; новые статусы операций; мультивалютность; интеграции; изменение `envelope_reallocations` как примитива; изменение изоляции по `workspace_id`/`budget_id`.

Все новые операции — обычные подтверждения уровня `CONFIRMED`, идемпотентные (Idempotency-Key по существующей схеме), с проверкой `budget_id` в репозитариях и аудитом (`AuditLog`, источник `API`).

## 3. Функции

### F1. Безопасное архивирование конверта (P1) — приоритет P0

- `PATCH budgets/:budgetId/envelopes/:id/archived` (существующий) возвращает **409** `ENVELOPE_HAS_UNMOVED_BALANCE` (точный код зафиксировать в OpenAPI при реализации), если текущий баланс ≠ 0, с body:
  - `balanceMinor`, список активных конвертов того же типа/бюджета как кандидаты на перенос остатка;
- UI: модалка «В конверте N осталось. Куда перенести?: [конверт X] [Свободные] [Создать новый]» → создаёт `envelope_reallocations` + архивацию в одной транзакции (см. F2 механика) или просто реаллокацию.
- Архивация пустого конверта — без изменений.
- Архивные конверты с балансом остаются допустимыми (исторические данные), но попадают в F5.

### F2. Операция «Заменить конверт» (P2) — приоритет P0

- `POST budgets/:budgetId/envelopes/:id/replacement` (идемпотентный), тело: `{ name, targetEnvelopeId?|createSpec }` — создаёт новый конверт (тот же тип/валюту/цикловый слот, `monthly_planned`/`target` копируются), в той же транзакции:
  1. реаллокация всего текущего баланса старого → нового (0, если пусто);
  2. архивация старого (гарантированно пустого после шага 1);
  3. запись lineage: новый конверт получает `replaces_envelope_id` (новая колонка, nullable, FK на тот же бюджет) — UI показывает «заменил: … → (дата)»;
- Ошибки: 409 если у старого есть активные (не завершённые) привязки, препятствующие переносу (список приводится); 422 `INSUFFICIENT_BALANCE` не срабатывает — переносит ровно текущий баланс независимо от знака (бюджет с `allow_negative_balance=false` → перенос только положительной части не поддерживается; при `false` и отрицательном балансе — 409 с объяснением).
- Аудит: три записи (создание, реаллокация, архивация) с общим `request_id`.

### F3. Состав баланса конверта (P3) — приоритет P1

- API: существующий `.../envelopes/:id/balance-summary` уже возвращает разбивку (старт, распределения, расходы, переводы, реаллокации + списки до 100 строк). Расширяем:
  - курсорная пагинация списков (сейчас `LIMIT 100` без курсора);
  - для каждой строки распределения/реаллокации: `counterpartId`/`counterpartName` (у распределения — доход/счёт, у реаллокации — другой конверт);
- UI: таблица «Состав» с строками и кнопкой «Переместить в…» на строках распределения и реаллокаций, создающей целенаправленную `envelope_reallocations` (сумма = строке). Общий баланс — без изменений (это та же операция, что и F2/F1 механика).
- Не вводит новых сущностей в БД.

### F4. Валидации и предпросмотр (P4) — приоритет P1

- При `POST income_allocations` / `transfer_parts` / `envelope_reallocations` ответ 201 получает дополнительный опциональный блок `warnings[]` (текст на русском, код + детали), если:
  - объект-приёмник архивен или был архивирован менее 30 дней назад;
  - операция ухудшает покрытие подтверждённых планов ближайшего периода (покрытие считается так же, как на dashboard): например, «После этого план "Алименты" (20 000,00) останется не покрыт на 21 000,00».
- Принудительные ошибки (409/422) не добавляются: это предупреждения, а не блокировки (пользователь может знать, что делает — как в реальном случае, когда в «Обязательные» намеренно оставили 20 000,00).
- Расчёт покрытия — read-only, выполняется **до** записи мутации (по данным на момент запроса) и не влияет на её успешность; при расхождении данных предупреждение может опоздать, — допустимо, так как это предостережение, а не контроль.

### F5. Замороженные остатки (P1) — приоритет P0

- Dashboard: новый блок «Деньги вне активных конвертов» = сумма балансов архивных конвертов (≠0). Клик → список таких конвертов с действиями «Перенести в…» (та же механика F2-реаллокации) или «Архив оставить как есть» (список не блокирует, но блок dashboard остаётся видимым).
- Отдельно подсвечиваются (не блокируются) архивные конверты с балансом, архивированные за последние 14 дней.
- API: `GET budgets/:budgetId/envelopes?archived=true` (существующий фильтр, если есть, иначе добавить) + сумма в ответ dashboard-эндпоинта `archivedBalanceMinor`.

### F6. Закрытие цикла между периодами (P5) — приоритет P1

- UI-операция «Перенести остаток периода» (кнопка на карточках «Первый период»/«Второй период»): открывает форму реаллокации со ссылкой на активный конверт того же `period_slot`-пары; создаёт **обычную** `envelope_reallocations`, никакой новой сущности.
- Правило-помощник: при `allow_negative_balance=false` остаток < 0 не переносится (нечего переносить).
- Не вводит автоматического carry-over (автоматические финансовые движения без подтверждения владельца не создаём).

### F7. Основной конверт счёта — приоритет P2 (не в этом релизе, зарезервировано)

- Ссылка `account.default_envelope_id` (nullable), по умолчанию операции со счёта без явно указанного конверта идут в него; «сиротские» счета (с ненулевым балансом и без операций в последние 90 дней) подсвечиваются в списке счетов.
- В v1-регресс: не менять текущее поведение (счёт → конверт привязан только операциями); только UI-подсветка.

## 4. Изменения данных

| Объект | Изменение | Миграция |
|---|---|---|
| `envelopes.replaces_envelope_id` (новый, nullable Uuid, FK→`envelopes.id`+`@@unique` пары с тем же `budget_id`, `ON DELETE SET NULL`) | lineage для F2 | добавляющая, без данных |
| `audit_log` | нет изменений | — |
| `envelope_reallocations` | нет изменений | — |

Все существующие инварианты сохраняются; никаких пересчётов `starting_balance` при этой фазе.

## 5. OpenAPI и контракты

- Новые: `POST budgets/:budgetId/envelopes/:id/replacement` (201/400/401/403/404/409), расширение 409 у архивации (новый код + детали), `archivedBalanceMinor` в dashboard, `warnings[]` в ответах мутаций.
- Все тексты ошибок/предупреждений — на русском; коды ошибок — ASCII-идентификаторы (по существующим конвенциям).
- Breaking changes по `/api/v1` не планируются.

## 6. Приёмка (кратко, подробно — в плане)

1. Архив конверта с балансом невозможен без указания, куда уйти деньгам; после — архив = 0, сумма по бюджету не меняется.
2. «Заменить» создаёт нового → старый пуст и архивен, сумма по бюджету не меняется, lineage виден.
3. В «Состав» видно каждую строку, из которой сформировался баланс; «Переместить в…» на любой строке корректно переносит только её сумму.
4. При операции, ухудшающей покрытие планов, приходит `warnings[]` с суммой дефицита (пример: «Алименты» 20 000,00 → 21 000,00).
5. Блок «Деньги вне активных конвертов» на реальном бюджете показывает 139 738,76 ₽ до и 0,00 ₽ после действий (F5-перенос вручную).
6. Перенос периода создаёт обычную реаллокацию; отрицательный/нулевой остаток — без операции.
7. Инварианты: активные конверты = счета, бюджет A не видит объекты B (теги по `budget_id` во всех новых/изменённых запросах).
8. Идемпотентность: повтор `replacement`/архивации с тем же ключом — тот же результат без дублей.

## 7. Тесты

- Модульные: приложение-сервисы (новые ветки: баланс ≠ 0 на архив, replacement с lineage, warning-расчёт, carry-zero).
- Интеграционные (Supertest + Postgres): транзакционность replacement (crash на шаге 2 откатывает всё), идемпотентность, изоляция бюджетов, авторизация (401/403/404), OpenAPI-схемы.
- E2E (Playwright): сценарий пользователя «архив с остатком → выбрать конверт → остаток переехал, в архиве пусто»; «заменить конверт»; перенос «Первый → Второй период».
- Money-тесты: все суммы — bigint minor; децималы — только на границе API.

## 8. Риски и ограничения

- F4-покрытие планов: расчёт приближённый (не учитывает будущие доходы) — это предупреждение, не гарантия.
- Исторические архивные остатки (139 738,76 ₽) возвращаются вручную через F5; автосоздание реаллокаций в миграции не делаем (fintech-правило: миграция не двигает деньги).
- Отрицательный баланс при `allow_negative_balance=false`: F2 переносит только при балансе ≥ 0 (иначе 409) — такое поведение зафиксировано в контракте.
- UI-тексты: доступность (фокус, контраст, иконка-пометка на предупреждениях) по гайдлайну Calm Fintech.

## 9. Приоритизация

- **П0 (баг-фича, в ближайший релиз):** F1 + F2 + F5 + миграция `replaces_envelope_id` + блок dashboard.
- **П1 (следующий релиз):** F3 (курсор + counterparty), F4, F6.
- **П2 (потом / после v1):** F7 (основной конверт счёта).

По функциональной спецификации v1 — это расширения уже выпущенного v1, не новые продуктовые возможности v1; roadmap «После v1» (§18) не расширять без согласия владельца.

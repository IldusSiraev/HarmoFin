# Конверты как планы (Envelope Plan Model) — дизайн

- Дата: 2026-09-28
- Статус: дизайн v2. **Замещает** предыдущий дизайн `2026-09-28-envelope-lifecycle-transparency-design.md` (точечный подход F1–F7 снят с реализации; старый документ оставляем как исторический).
- Решения владельца (2026-09-28):
  1. Конверты **не хранят деньги** — только планы/назначения; деньги живут на счетах.
  2. Доход уходит на счёт; конвертам он не «принадлежит» по умолчанию.
  3. Перевод между счетами — чистая операция без «назначений».
  4. Существующие бюджеты — **live-миграция** на новую модель.
  5. Автозаполнение планов конвертов (`funding rules`); правила применяются через **черновик → подтверждение владельца**.

## 1. Контекст

Факты с бюджета «Семейный бюджет» (снимок 2026-09-26) — все они следуют из старой модели, где конверты вели себя как физические хранилища, а инвариант «активные конверты = счета» порождал:

- замороженные деньги в архивных конвертах (139 738,76 ₽);
- отрицательный старт конверта (−53 115,00 ₽) ради «схождения балансов»;
- ручные «замены» конверта и переносы остатков (три «Обязательные» за цикл);
- `INSUFFICIENT_MANDATORY_OBLIGATIONS`, где фактические расходы и «деньги в конверте» сравнивались в одном числе.

Вывод: 139 738,76 ₽ не потеряны — всё на счетах (681 134,70 ₽ = 681 134,70 ₽). Потеряна **понятность**. Смысловое лечение — смена модели, а не точечные фиксы.

## 2. Новая модель (кратко)

**Деньги живут на счетах. Конверты живут в планах.**

- Единственный жёсткий инвариант: `баланс(счёт) = стартовый + Σ подтверждённых доходов − Σ подтверждённых расходов ± переводы`. Никакой другой «сходимости» в системе нет.
- Конверт = назначение на период. На каждом конверте: `получено (allocated)`, `потрачено (spent)`, `осталось`. Это **план**, а не кошелёк: недо- или перераспределение — нормальное состояние, а не ошибка.
- Расход в конверт тратит его **план**, а не деньги «из конверта». Расход без конверта — легален, идёт в «без назначения».
- Специальный конверт «Свободные» больше не нужен: «не размещено» — это состояние счёта, которое всегда видно.

Снимается (и исчезает как категория):

| Было (старая модель) | Станет |
|---|---|
| физический баланс конверта, реаллокации денег между конвертами | редактирование плана/разметки (с записью в аудит) |
| переводы `preserve purpose` / `transfer_parts` | чистый перевод между счетами |
| отрицательный/нулевой `starting_balance` как трюк | у конверта нет физического старта |
| «замороженные» деньги в архиве | архив конверта = не использовать в новых периодах; деньги на счетах, ничего не «замораживается» |
| операция «заменить конверт» | смена названия/правил конверта (история планов сохраняется) |

## 3. Доходы

- Подтверждённый доход → на счёт (как сейчас), баланс счёта только растёт.
- **Автоматическая разметка** на источники плана (см. правила) + **ручная разметка** по желанию: существующие `income_allocations` остаются инструментом разметки, но теперь это «этот доход кормит этот план», а не «деньги перелиты в конверт».
- Блокировок, если доход «без разметки», нет: деньги на счёте, и их всегда видно в блоке «Не размещено».

## 4. Правила формирования плана (`funding rules`) — ядро автозаполнения

Одна сущность `envelope_funding_rule` на конверт (переключается на лету, хранится в настройках конверта):

| Тип | Поведение | Пример (данные пользователя) |
|---|---|---|
| `manual` (по умолчанию) | план на период вводится вручную, как сегодня | «Ремонт», «Инвестиции» |
| `sum_of_plans` | план конверта = **сумма подтверждённых планов расходных операций на периоде** | «Обязательные» = алименты 20 000 + интернет/связь + садик + аренда… — конверт считает сам, ручного расчёта «91 644» больше не нужно |
| `fixed_monthly` | план = фиксированная сумма каждый период (integer minor) | «Связь — 6 000/мес» |
| `percent_of_income` | план += X% каждого подтверждённого дохода (X редактируется) | «Инвестиции — 30% дохода» |

Правила и безопасность:

- Правило **никогда** само не подтверждает: при наступлении события (смена периода, подтверждение дохода) система создаёт **черновик** плана/разметки; владелец одним тапом подтверждает, правит или отклоняет. Финансово-значимые записи без подтверждения владельца не создаются.
- Правило действует на **будущие** периоды и будущие доходы; текущий период не перезаписывается.
- Правила в сумме могут дать >100% или <100% плана — это предупреждение/подсветка, не ошибка (планы, а не деньги).
- Движок правил — отдельный модуль; **AI/ML-правило** (предсказание %/суммы по истории) — «после v1» по функциональной спеке, в этой фазе не реализуем; точка расширения закладывается заранее (новый тип правила, интерфейс `rule → draft`).
- До v1 только мажорная валюта бюджета; суммы — integer minor.

## 5. Периоды

- Границы периода не меняются: `cycle_start_day=10`, `period_boundary_offset=15` (существующий механизм).
- Начало периода: система по правилам конвертов создаёт **черновик плана нового периода** → экран «Подтвердить план периода» (одно действие на период).
- Конверт `sum_of_plans` пересчитывается при изменении подтверждённых планов периода; до подтверждения плана результат держится в черновике, после — меняется только явной кнопкой «изменить план».
- Остаток плана предыдущего периода при смене **не переносится** (планы — не деньги). Если владелец хочет продолжить финансирование — задаёт новый план вручную или правилом. carry-over по умолчанию нет.

## 6. Карточка конверта (UX)

```
[Алименты]                        Правило: фикс. 20 000/мес
получено    30 000,00  [разметка с доходов: З/П 20.09]
потрачено   20 000,00  [оплата 25.09]
осталось    10 000,00  [подсветка, если план < 0]
```

- Строка «получено» = сумма разметки доходов (источники плана); кликабельна → «Состав источников» (существующий `balance-summary` переосмысливается: источники и траты плана, а не «состав кошелька»).
- «Переместить источник» = перенос разметки дохода с одного конверта на другой (запись в аудит).
- На дашборде вместо «замороженных денег» — блок **«Не размещено»**: сумма на счетах без разметки на источники плана + подсветка периодов с покрытием плана <100%.
- «Обязательные» (конверт `sum_of_plans`): карточка-суммаризатор по подтверждённым планам; у каждого плана — статус «покрыто / не покрыто на N».

## 7. Переводы и операции

- Переводы — чистая операция счёт→счёт, без `transfer_parts` (существующие — только в истории).
- Расход — как сегодня: оплата в конверт = трата плана конверта.
- Расход без конверта или в архивный конверт — легален (запись в аудит); на карточке счёта — подсветка «траты без назначения».
- `envelope_reallocations`, `starting_balance` (конверта), `period_slot` — не используются в новой модели; сущности остаются в схеме read-only до решения о чистке (§9).

## 8. Миграция (live)

Разовая идемпотентная миграция — переезд **семантики**, а не денег:

1. Текущие физические остатки конвертов → `allocated` плана **ближайшего** периода; создается черновик, первый вход пользователя — «Проверить и подтвердить план».
2. `starting_balance` конвертов (в том числе отрицательные значения) — переносятся в метаданные истории; новый план считается без них.
3. Реаллокации, переводы, расходы, доходы — без изменений (история), только переинтерпретируются новыми экранами.
4. Замороженные 139 738,76 ₽ — остаются как «не размещено» (деньги физически на счетах); никаких движений не создаётся.
5. Старые архивные конверты остаются в архиве; их «остатки» → «не размещено».
6. Миграция — один атомарный шаг на бюджет + откатная копия (снапшот плановых таблиц) до первого подтверждения.

## 9. Контракт API и версионность

- Новая модель — смена мажорной версии домена конвертов: смысл `/api/v1/envelopes/*` меняется. По правилам репо breaking change допустим только с миграционным планом — он в §8 + секция релиза в плане.
- Пока бюджет не мигрирован — он работает по старой модели (флаг в бюджете `plan_model_version = 1|2`); API отвечает по версии бюджета. В одном запуске системы два «продукта» не смешиваются.
- OpenAPI: новые типы правил, `period_plans`, новая карточка конверта; endpoint v1 (без изменений) живёт только до завершения миграции всех бюджетов — срок фиксируется в плане.

## 10. Что не меняется (финансовое ядро)

- Инвариант и формулы **счетов** — без изменений; CONFIRMED-only; идемпотентность мутаций; логическое удаление; аудит; изоляция `workspace_id`/`budget_id` (каждая новая сущность несёт `budget_id`); сессии/CSRF/rate-limit; OpenAPI-дисциплина; UI-тексты — на русском.
- Исключения v1 (функциональная спека, «После v1») остаются исключениями: импорт из банков, мультивалютность, кредит/долг, AI-анализ, биллинг, Telegram.

## 11. Приёмка (кратко, подробно — в план)

1. Новый бюджет: доход на счёт; правило `sum_of_plans` на «Обязательные» → в следующем периоде черновик = сумме подтверждённых планов; один тап — подтверждён. Дефицит показан как «не покрыто на N», а не как «мало денег в конверте».
2. Расход > плана → конверт уходит в отрицательный план: предупреждение, без блокировки (опция `allow_negative_plan` — включена по умолчанию).
3. Перевод ТБанк → Копилка на 50 000: баланс счетов сходится, конверты не изменились.
4. Миграция: после «подтверждения плана» баланс счетов 681 134,70 не меняется ни на копейку; «Не размещено» = 139 738,76 ₽ видно и доступно для разметки/расходов.
5. Правило `percent_of_income` меняют на лету → действует с следующего дохода; текущие черновики не перезаписаны.
6. Изоляция: бюджет A не видит правила/планы/черновики бюджета B (тесты по `budget_id` в каждом запросе).
7. Черновик без подтверждения не влияет ни на один баланс и ни на один отчёт.

## 12. Тесты

- Модульные: движок правил (каждый тип; границы: 0%, >100%, отрицательные значения); черновик-подтверждение (идемпотентность, отклонение); пересчёт `sum_of_plans`.
- Интеграционные: миграция (снапшот/откат, идемпотентность, 681 134,70 не меняется), изоляция, авторизация (401/403/404), OpenAPI-схемы.
- E2E (Playwright): «смена периода → черновик → подтверждение → расход → дефицит плана».

## 13. Риски

- **Продуктовый**: «каждая копейка размещена» перестаёт быть инвариантом — осознанный переход к «деньги всегда на счетах, планы — на конвертах». Согласовано с владельцем; блок «Не размещено» — главный ответ на этот вопрос.
- **Миграция**: live-данные во время миграции — снапшот + откат + краткое окно «без записи» (maintenance); никакого «движения денег» миграцией.
- **Правила**: `sum_of_plans` считает по **подтверждённым** планам, не по черновикам — иначе правило «подглядывает» за намерениями.
- Старая семантика `balance-summary`/`envelope_reallocations` для бюджетов `version=1` поддерживается до завершения миграции; срок — в плане.

## 14. Открытые вопросы (решить на этапе плана)

1. Ретроакция: правила действуют только на будущее (предварительное решение — да, прошлые периоды не пересчитывать).
2. Лимит: одно правило на конверт (предварительное решение — да).
3. `allow_negative_balance` переименовать в `allow_negative_plan` — смысл точнее; совместимость — через `plan_model_version`.
4. Срок поддержки v1-endpoint без изменений после завершения миграции (кандидаты: 1 релиз / 6 месяцев — в плане).

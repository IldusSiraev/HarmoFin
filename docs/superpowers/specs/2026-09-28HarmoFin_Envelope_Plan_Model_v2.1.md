# HarmoFin Envelope Plan Model v2.1

- **Дата:** 2026-09-29
- **Статус:** проектная спецификация, подготовленная к реализации
- **Основание:** `2026-09-28-envelope-plan-model-design.md`
- **Исторический контекст:** `2026-09-28-envelope-lifecycle-transparency-design.md`
- **Функциональная основа:** `2026-08-30-family-budget-app-spec.md`
- **Назначение:** зафиксировать окончательную доменную семантику, поведение продукта, UX-flow, API-контрактные требования и критерии приёмки для модели `Envelope Plan Model v2.1`.

## 1. Решения владельца

1. Конверты **не хранят деньги** — только планы/назначения; деньги живут на счетах.
2. Доход уходит на счёт; конвертам он не «принадлежит» по умолчанию.
3. Перевод между счетами — чистая операция без назначений.
4. Расход может быть привязан к плану конверта или оставаться **без назначения**.
5. Автозаполнение планов и разметки работает через **черновик → подтверждение владельца**.
6. План является планом на период, а не денежным балансом.
7. Предыдущая модель физического хранения денег в конвертах больше не используется.
8. Пользовательская live-миграция для будущих пользователей **не является частью продукта**.
9. Для текущего бюджета владельца выполняется **одна разовая миграция данных** при переходе на v2.1.
10. После выхода v2.1 новый пользователь сразу работает только с новой моделью.

## 2. Контекст

Старая модель конвертов пыталась использовать конверт как физическое хранилище денег. Это приводило к:

- замороженным остаткам в архивных конвертах;
- отрицательным `starting_balance` ради сходимости;
- ручным заменам конвертов;
- реаллокациям между конвертами;
- смешению фактического движения денег и их назначения;
- сложным сценариям перехода между периодами.

Основная проблема — не отсутствие отдельных операций, а сама семантика.

**Новая модель:**

> **Деньги живут на счетах. Конверты живут в планах.**

Поэтому v2.1 не пытается исправить старую модель точечными операциями. Она меняет смысл конверта и оставляет финансовым источником истины только реальные движения денег по счетам.

## 3. Новая модель

### 3.1. Финансовый инвариант

Единственный жёсткий финансовый инвариант:

```text
баланс(счёта)
=
начальный баланс
+ подтверждённые доходы
- подтверждённые расходы
± подтверждённые переводы
```

Планы, разметка доходов и конверты **не меняют баланс счёта**.

Никакой дополнительной «сходимости» между счетами и конвертами нет.

### 3.2. Конверт

Конверт — это назначение денег и контейнер планов.

Для конкретного периода у конверта есть:

```text
allocated
spent
remaining
```

где:

- `allocated` — сумма подтверждённых разметок доходов на этот план;
- `spent` — сумма подтверждённых расходов, привязанных к плану;
- `remaining` — `allocated - spent`.

Это не денежный баланс.

`remaining < 0` означает, что фактические расходы превысили сумму назначений. Это предупреждение, а не ошибка.

### 3.3. План

План отвечает на вопрос:

> Сколько мы собираемся направить на это назначение в конкретном периоде?

План не перемещает деньги.

Пример:

```text
Ремонт
План:       50 000 ₽
Назначено:  40 000 ₽
Потрачено:  12 000 ₽
Осталось:   28 000 ₽
```

Здесь физически все 28 000 ₽, как и остальные деньги, находятся на счетах.

### 3.4. Разметка дохода

`income_allocation` отвечает на вопрос:

> Какая часть конкретного подтверждённого дохода предназначена для конкретного плана?

Разметка:

- не переводит деньги;
- не меняет баланс счёта;
- может быть изменена с записью в аудит;
- может быть создана вручную или предложена правилом.

### 3.5. Расход

Расход отвечает на вопрос:

> Сколько денег фактически потрачено и на что?

Расход:

- уменьшает баланс счёта;
- уменьшает `remaining` соответствующего плана, если план указан;
- может быть создан без назначения.

Расход без назначения является допустимым состоянием.

## 4. Семантика основных сущностей

| Сущность | Пользовательский смысл | Меняет реальные деньги |
|---|---|---:|
| Счёт | Где находятся деньги | Да |
| Доход | Деньги фактически поступили | Да |
| Расход | Деньги фактически потрачены | Да |
| Перевод | Деньги перемещены между счетами | Да, но общий объём денег не меняется |
| Конверт | Для чего предназначены деньги | Нет |
| План периода | Сколько хотим направить на назначение | Нет |
| Разметка дохода | Какая часть дохода предназначена плану | Нет |
| Категория | На что фактически потрачены деньги | Нет |
| Запланированный платёж | Ожидаемая будущая операция | Нет |
| Черновик | Предложение системы | Нет |

## 5. Связь сущностей

```text
                    ┌──────────────────┐
                    │  Регулярный план │
                    │  (шаблон цели)   │
                    └────────┬─────────┘
                             │
                             ▼
                    ┌──────────────────┐
                    │      Правило     │
                    │  формирования    │
                    └────────┬─────────┘
                             │
                             ▼
                    ┌──────────────────┐
                    │   План периода   │
                    │   (snapshot)     │
                    └────────┬─────────┘
                             │
                ┌────────────┴────────────┐
                ▼                         ▼
       ┌────────────────┐       ┌────────────────┐
       │ Разметка дохода│       │ Фактический    │
       │   allocation   │       │ расход         │
       └────────────────┘       └────────────────┘
```

Важно:

- регулярный план описывает повторяющееся намерение;
- правило определяет способ формирования;
- план периода — подтверждённый snapshot;
- разметка дохода связывает реальные поступления с назначением;
- расход отражает факт.

## 6. Правила формирования плана (`funding rules`)

На один конверт действует одно активное правило.

### 6.1. `manual`

План периода задаётся вручную.

Примеры:

- Ремонт;
- Инвестиции;
- Резерв.

При создании нового периода система не создаёт финансовый факт автоматически. Пользователь задаёт план сам.

### 6.2. `sum_of_plans`

План конверта равен сумме подтверждённых планов связанных расходных операций периода.

Пример:

```text
Обязательные
├── Алименты       20 000
├── Интернет        3 000
├── Садик          15 000
└── Аренда         40 000
                  ────────
                   78 000
```

Конверт «Обязательные» показывает `78 000 ₽`.

Правило использует только **подтверждённые планы**, а не черновики.

### 6.3. `fixed_monthly`

План равен фиксированной сумме на каждый будущий период.

Пример:

```text
Связь
20 000 ₽ / период
```

При создании нового периода система создаёт черновик плана `20 000 ₽`.

### 6.4. `percent_of_income`

План/назначение формируется из заданного процента каждого подтверждённого дохода.

Пример:

```text
Инвестиции
30% от каждого подтверждённого дохода
```

Если подтверждён доход:

```text
100 000 ₽
```

правило предлагает:

```text
30 000 ₽ → Инвестиции
```

Разметка является черновиком и требует подтверждения.

### 6.5. Общие правила безопасности

- Правило никогда не создаёт финансово значимую запись без подтверждения владельца.
- Правило создаёт черновик плана и/или разметки.
- Черновик не влияет на балансы и отчёты.
- Правила применяются только к будущим событиям.
- Изменение правила не переписывает историю.
- Правило не изменяет уже подтверждённый план периода молча.
- Сумма правил может быть меньше или больше 100% дохода/плана — это предупреждение, а не ошибка.
- AI/ML-правило в v2.1 не реализуется.

## 7. Периоды

Границы финансового цикла сохраняются:

```text
cycle_start_day = 10
period_boundary_offset = 15
```

Пример:

```text
Финансовый месяц
10 сентября → 9 октября

Период 1
10 → 24 сентября

Период 2
25 сентября → 9 октября
```

### 7.1. Создание нового периода

```text
Новый период
    ↓
Применить активные правила
    ↓
Создать черновик планов
    ↓
Показать «Подтвердить план периода»
    ↓
Пользователь подтверждает / редактирует / отклоняет
```

### 7.2. Изменение подтверждённого плана

После подтверждения:

- автоматический пересчёт не выполняется;
- изменения происходят только через явное действие пользователя;
- история изменения записывается в аудит.

Для `sum_of_plans` изменение подтверждённых связанных планов может сформировать предложение изменить суммарный план, но не изменяет его молча.

### 7.3. Перенос между периодами

Carry-over планов отсутствует по умолчанию.

План предыдущего периода не переносится, потому что план — не деньги.

## 8. Дополнительный доход внутри периода

Это отдельный важный сценарий v2.1.

### 8.1. Общий принцип

Дополнительный доход — это обычный подтверждённый доход.

Он:

1. увеличивает баланс выбранного счёта;
2. попадает в текущий финансовый период;
3. не изменяет уже подтверждённые планы сам по себе;
4. запускает правила, которые зависят от дохода;
5. создаёт черновик предложений там, где это необходимо.

### 8.2. Доход без процентных правил

Пример:

```text
План периода:

Обязательные    80 000
Текущие         40 000
Ремонт          20 000
```

Пользователь получает дополнительный доход:

```text
+50 000 ₽
```

Система:

```text
Баланс счёта     +50 000 ₽
Планы периода     без изменений
```

На главной:

```text
Получено +50 000 ₽

Есть новые деньги, которые ещё не размещены.
[Распределить]
```

Пользователь самостоятельно решает, куда направить доход.

### 8.3. Доход при `percent_of_income`

Если есть правило:

```text
Инвестиции = 30% каждого дохода
```

и приходит:

```text
+50 000 ₽
```

система создаёт черновик:

```text
Новый доход
50 000 ₽

HarmoFin предлагает:

Инвестиции
15 000 ₽

Оставить не размещёнными
35 000 ₽
```

После подтверждения:

```text
income
  +50 000 ₽ на счёт

allocation
  15 000 ₽ → Инвестиции
```

Баланс счёта остаётся увеличенным на полные `50 000 ₽`.

### 8.4. Если текущий план уже подтверждён

Если процентное правило должно увеличить план текущего периода, система не изменяет подтверждённый snapshot молча.

Вместо этого создаётся предложение:

```text
Инвестиции

Текущий план      30 000 ₽
Новый доход        50 000 ₽
Правило             30%

HarmoFin предлагает:
увеличить план до 45 000 ₽
и назначить 15 000 ₽ из нового дохода.
```

Действия:

```text
[Принять]
[Изменить]
[Оставить план без изменений]
```

Факт дохода создаётся независимо; изменение плана и разметки требует подтверждения.

### 8.5. `fixed_monthly` и `sum_of_plans`

Дополнительный доход **не увеличивает**:

- `fixed_monthly` план;
- `sum_of_plans` план.

Эти правила зависят не от размера дохода, а от периода/связанных планов.

Дополнительный доход при этом становится доступен для ручной разметки.

### 8.6. Несколько дополнительных доходов

Каждый подтверждённый доход обрабатывается независимо.

```text
Income confirmed
      ↓
Rules evaluated
      ↓
Draft proposal
      ↓
Owner confirms
```

Система не объединяет несколько доходов задним числом в один источник.

### 8.7. Редактирование дохода

Если доход был изменён после подтверждения:

- баланс счёта пересчитывается по фактической операции;
- связанные разметки не изменяются автоматически;
- если разметки больше доступной суммы, система создаёт предупреждение/задачу на исправление;
- пользователь явно подтверждает изменение разметки.

### 8.8. Удаление/отмена дохода

При логическом удалении подтверждённого дохода:

- операция исключается из расчёта баланса счёта;
- связанные разметки не превращаются в самостоятельные деньги;
- если после удаления разметки становятся некорректными, пользователь получает предупреждение/задачу на исправление;
- автоматического перераспределения на другие конверты нет.

## 9. Разметка дохода и «Не размещено»

### 9.1. Основной принцип

```text
Фактические деньги
        ↓
Баланс счетов

Назначение этих денег
        ↓
Разметка доходов / планы
```

`Не размещено` не является отдельным счётом и не является отдельным конвертом.

### 9.2. Пользовательский смысл

В UI:

> **Не размещено**

означает:

> Есть подтверждённые деньги, для которых пользователь ещё не указал назначение в рамках текущей модели планирования.

Это состояние, а не место хранения денег.

### 9.3. Dashboard

```text
Не размещено
35 000 ₽

[Распределить]
```

Блок отображается, если есть подтверждённые доходы без назначения.

│ Правило: 20 000 ₽ / период         │
│                                     │

│                                     │

В UI предпочтительно:

- `План`
- `Назначено`
- `Потрачено`
- `Осталось`
- `Покрыт`
- `Не хватает`
- `Превышение`

Не использовать без необходимости:

- `allocation`;
- `reallocation`;
- `starting_balance`;
- `funding rule`;
- `balance convergence`.

## 11. Суммаризатор «Обязательные»

Если «Обязательные» использует `sum_of_plans`:

```text
Обязательные

План          78 000 ₽
Назначено     65 000 ₽
Потрачено     32 000 ₽
Не хватает    13 000 ₽
```

Внутри:

```text
Алименты       20 000   ✓ покрыто
Садик           15 000   ✓ покрыто
Интернет         3 000   ✓ покрыто
Аренда          40 000   × не хватает 13 000
```

Статус считается по подтверждённым планам.

## 12. Расходы без назначения

Расход без конверта допустим.

```text
Продукты
−4 820 ₽
Основная карта
Без назначения
```

Система:

- уменьшает баланс счёта;
- не уменьшает `remaining` конкретного плана;
- показывает расход в блоке/фильтре «Без назначения»;
- при необходимости предупреждает пользователя, но не блокирует операцию.

Расход в архивный конверт также не должен блокироваться автоматически, но должен быть видим и аудируем.

## 13. Переводы

Перевод — чистая операция:

```text
Счёт A
   ↓
Счёт B
```

Пример:

```text
50 000 ₽
ТБанк → Копилка
```

После операции:

```text
ТБанк       -50 000
Копилка     +50 000
Общий баланс  без изменений
Планы         без изменений
```

Старые `transfer_parts` не используются как механизм новой модели.

## 14. Архивация конверта

Архивный конверт:

- не используется для новых периодов;
- не получает новые автоматические планы;
- сохраняет историю;
- не хранит деньги.

При архивации:

```text
Текущие планы → сохраняются в истории
Будущие планы → больше не создаются
Деньги         → остаются на счетах
```

Операции прошлого не переписываются.

## 15. Замена конверта

Отдельная операция «Заменить конверт» больше не нужна.

Если пользователь хочет изменить название:

```text
Ремонт
→ Ремонт квартиры
```

достаточно изменить название.

Если нужно другое назначение:

- пользователь меняет правило;
- при необходимости создаёт новый конверт;
- старый архивирует.

История планов и расходов сохраняется.

## 17. Быстрый ввод операций

Добавление обычного расхода должно занимать несколько секунд.

Приоритеты:

- сумма — главный элемент;
- дата = сегодня;
- счёт = последний использованный/наиболее вероятный;
- категория = недавно использованная/подходящая;
- конверт = предложенный автоматически, но легко изменяемый;
- необязательные поля скрыты за progressive disclosure.

Mobile flow:

```text
+ Расход
   ↓
Сумма
   ↓
Категория
   ↓
Счёт / назначение
   ↓
Сохранить
```

## 21. «Можно потратить»

`Можно потратить` — пользовательский агрегат фактической доступности денег в текущем периоде.

Ключевой принцип:

> Плановый доход сам по себе не делает деньги доступными.

Учитываются фактические подтверждённые доходы и расходы согласно действующей финансовой модели.

При этом:

- планы не перемещают деньги;
- разметка доходов не уменьшает баланс счетов;
- переводы не меняют общий объём денег;
- расходы уменьшают реальные деньги.

## 23. API и доменная версия

Новая модель является breaking change по смыслу домена конвертов.

Используется:

```text
plan_model_version = 2
```

После перехода приложения на v2.1 новые бюджеты создаются сразу с новой моделью.

API должен:

- явно возвращать версию модели;
- использовать новые `period_plans`;
- возвращать тип активного `funding_rule`;
- разделять draft и confirmed;
- не возвращать старую семантику физического баланса конверта в новых endpoint'ах.

Основные API-концепции:

```text
GET    /budgets/:budgetId/envelopes
GET    /budgets/:budgetId/period-plans
POST   /budgets/:budgetId/period-plans/drafts
POST   /budgets/:budgetId/period-plans/:id/confirm
PATCH  /budgets/:budgetId/period-plans/:id

GET    /budgets/:budgetId/funding-rules
PUT    /budgets/:budgetId/envelopes/:id/funding-rule

GET    /budgets/:budgetId/income-allocations
POST   /budgets/:budgetId/income-allocations
PATCH  /budgets/:budgetId/income-allocations/:id

GET    /budgets/:budgetId/dashboard
```

Точные endpoint names должны соответствовать существующим OpenAPI-конвенциям репозитория.

## 24. Данные и ограничения

- Основная валюта бюджета — одна.
- Денежные значения внутри домена — integer minor units.
- Каждая новая сущность содержит `budget_id`.
- Все финансово значимые мутации идемпотентны.
- Используется `CONFIRMED` как состояние финансового факта.
- Логическое удаление сохраняет историю.
- Изменения назначений и планов аудируются.
- Черновики не участвуют в балансах и отчётах.
- Изоляция `workspace_id`/`budget_id` обязательна.

## 25. Разовая миграция текущего бюджета

Пользовательская миграция как продуктовая возможность **не реализуется**.

Нужна только одна техническая миграция текущего бюджета владельца перед публикацией v2.1.

Цель:

> перенести текущую семантику в новую модель без движения реальных денег.

Требования:

1. Сделать backup/snapshot текущих плановых данных.
2. Выполнить миграцию один раз.
3. Не создавать финансовых движений.
4. Не менять подтверждённые доходы, расходы и переводы.
5. Не менять итоговые балансы счетов.
6. Перенести актуальные назначения в планы текущего периода.
7. Старые `starting_balance` не использовать как физический баланс нового плана.
8. Старые реаллокации не переносить как операции движения денег.
9. Остаток старой модели, который не имеет однозначного назначения, показать как `Не размещено`.
10. После проверки legacy-данные, которые больше не используются приложением, вывести из новой доменной логики.

Контрольный инвариант текущего бюджета:

```text
Баланс счетов: 681 134,70 ₽
```

Ранее выявленный старой моделью остаток:

```text
139 738,76 ₽
```

должен после миграции быть виден как `Не размещено`, если актуальный snapshot подтверждает эту сумму.

Никаких операций перемещения на эту сумму создавать нельзя.

### Rollback

```text
migration failed
      ↓
rollback snapshot
      ↓
verify account balances
      ↓
abort release
```

## 26. Что удаляется из новой модели

Не использовать для новых финансовых операций:

- физический `envelope balance`;
- `starting_balance` конверта;
- `envelope_reallocations` как движение денег;
- `transfer_parts` как механизм сохранения назначения;
- `preserve purpose`;
- операцию `replacement`;
- автоматический carry-over плана;
- специальный конверт `Свободные`.

Legacy-поля могут временно сохраняться read-only для миграции/истории, но не должны использоваться новой доменной логикой.

## 27. Что не меняется

Без изменений остаются:

- финансовые циклы;
- периоды;
- счета;
- категории;
- фактические доходы;
- фактические расходы;
- переводы;
- CONFIRMED-only финансовые факты;
- idempotency;
- audit;
- logical delete;
- `workspace_id` / `budget_id` isolation;
- CSRF / rate limit;
- OpenAPI discipline;

## 28. Приёмка

### 28.1. Новый бюджет

Создать бюджет → счёт → доход → подтвердить доход → проверить баланс счёта → создать план → убедиться, что баланс счёта не изменился.

### 28.2. `sum_of_plans`

Для периода:

```text
Алименты 20 000
Интернет  3 000
Садик    15 000
```

`Обязательные` должен показать:

```text
План = 38 000
```

### 28.3. Расход больше плана

План:

```text
20 000
```

Расход:

```text
25 000
```

Результат:

```text
Потрачено 25 000
Осталось -5 000
Статус: Превышение 5 000
```

Расход не блокируется по умолчанию.

### 28.4. Перевод

```text
ТБанк → Копилка
50 000 ₽
```

Планы не изменяются.

### 28.5. Дополнительный доход

Текущий период:

```text
+50 000 ₽
```

Без `percent_of_income`:

```text
баланс счёта +50 000
планы без изменений
50 000 доступны для разметки
```

С правилом:

```text
30% → Инвестиции
```

система создаёт предложение:

```text
15 000 → Инвестиции
35 000 → Не размещено
```

Без подтверждения allocation не создаётся.

### 28.6. Изменение правила

Изменение:

```text
30% → 40%
```

не переписывает историю.

Новое правило действует на следующие подходящие события.

### 28.7. Черновик

Черновик:

- не изменяет баланс;
- не попадает в финансовые отчёты;
- не считается подтверждённым планом;
- может быть изменён;
- может быть отклонён;
- повторная обработка события не создаёт дублей.

### 28.8. Миграция

После разовой миграции:

```text
Баланс счетов до = Баланс счетов после
```

и ни одного финансового движения миграцией не создано.

### 28.9. Изоляция

Бюджет A не видит:

- планы B;
- правила B;
- доходы B;
- allocations B;
- drafts B.

Каждый запрос проверяет `budget_id`.

## 30. Риски и ограничения

### 30.1. Семантика «Не размещено»

Нельзя интерпретировать «Не размещено» как физическую сумму денег, лежащую отдельно от остальных денег.

Это состояние назначения.

### 30.2. Фунгибельность денег

Деньги на счетах являются взаимозаменяемыми.

Поэтому UI должен показывать отдельно:

```text
где деньги
```

и:

```text
для чего они предназначены
```

### 30.3. Изменение подтверждённого плана

Автоматические изменения подтверждённого snapshot создают недоверие к истории.

Поэтому:

> **автоматизация создаёт предложение, а не скрыто меняет подтверждённый факт.**

### 30.4. Дополнительный доход

Каждый дополнительный доход должен быть отдельным событием.

Нельзя автоматически считать его «свободными деньгами» только потому, что он превышает ожидаемый доход.

### 30.5. Legacy

Старые сущности не должны просачиваться в новую UI-семантику.

Пользователь не должен видеть:

- реаллокации;
- starting balance;
- физический баланс конверта;
- replacement;
- transfer parts.

## 31. Open questions

На этапе v2.1 открытых продуктовых вопросов, блокирующих реализацию, не остаётся.

Зафиксированные решения:

1. Правило действует на будущее.
2. На конверт действует одно активное правило.
3. `allow_negative_balance` в новой модели переименовывается в `allow_negative_plan`.
4. Подтверждённый план периода является snapshot.
5. Дополнительный доход обрабатывается как отдельное событие.
6. `percent_of_income` применяется к каждому подтверждённому доходу.
7. Изменение подтверждённого плана требует явного действия пользователя.
8. Пользовательская миграция не входит в продукт.
9. Текущий бюджет мигрируется один раз перед релизом.
10. Новые пользователи сразу создаются в модели v2.

## 32. Финальная доменная формула

HarmoFin v2.1 должен объясняться пользователю следующей последовательностью:

```text
Где деньги?
        ↓
Счета

Сколько денег фактически пришло?
        ↓
Доход

Для чего мы хотим их использовать?
        ↓
План / Конверт

Какая часть полученного дохода уже имеет назначение?
        ↓
Распределение

На что фактически потратили?
        ↓
Расход / Категория

Сколько осталось в плане?
        ↓
План − расходы

Что можно сделать прямо сейчас?
        ↓
Можно потратить
```

Главный принцип модели:

> **Деньги находятся на счетах. Планы находятся в конвертах. Доходы и расходы — факты. Разметка и планы — назначения.**

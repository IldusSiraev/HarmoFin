# Планы v2: форма «Создать план» — дизайн

- **Дата:** 2026-10-04
- **Статус:** проект дизайна; ожидает проверки владельцем перед планом реализации ([план](../plans/2026-10-04-plan-create-form.md)).
- **Источники:** [модель Envelope Plan v2.2](2026-09-29%20HarmoFin_Envelope_Plan_Model_v2.2.md) §6, §8, §11; [Calm Fintech](2026-09-17-calm-fintech-visual-guidelines.md); журнал [UX-15, UX-16, UX-17](../../ux/newcomer-walkthrough.md); [открытые решения](../plans/2026-10-03-envelope-v2.2-open-decisions.md) §1.3.
- **Область:** только веб (`apps/web`). Сервер и OpenAPI не меняются.

## 1. Цель

Дать пользователю способ завести обязательный платёж и плановый доход. Сейчас страница «Планы» в модели v2 показывает только пустые списки: форма создания, календарь и список планов были частью модели v1 и удалены (коммит `bbf25c5`), новый интерфейс не писался. Из-за этого шаг 5 чек-листа «Обязательные платежи» невозможно выполнить, а «Можно потратить» не защищает аренду и кредиты.

## 2. Что входит и что нет

Входит:

- диалог «Создать план» с двумя вкладками: **Платёж** (обязательный платёж) и **Доход** (плановый доход);
- кнопки открытия диалога на странице «Планы» (шапка и пустые состояния);
- обновление списков после сохранения, статусное сообщение, возврат фокуса;
- исправление текста про ожидаемый доход (UX-16): строка-предупреждение понятным языком и только когда есть плановые доходы.

Не входит (отдельные задачи):

- календарь по дням, плитки «Плановые доходы / Расходы / Баланс / Всего планов», список «Ближайшие / Все» (UX-17, промпт [plans-calendar-v2.md](../prompts/plans-calendar-v2.md));
- правка и остановка существующего плана;
- вкладка «Накопление» (плана-накопления в v2 нет: взнос задаётся правилом пополнения конверта, спецификация §7.3);
- счёт или конверт в плане (решение владельца: вариант A — счёт выбирается при оплате).

## 3. Что делает план (важно для текстов)

- Сохранение плана — «явное подтверждение намерения», не расход (§6). Операция не создаётся, деньги не списываются.
- Реальный расход создаётся кнопкой «Оплатить» на странице «Планы»: счёт, категория, сумма и дата выбираются там, расход идёт из конверта «Обязательные» (`POST /obligations/{id}/pay`).
- Плановый доход создаёт операцию только кнопкой «Записать доход» (`POST /income-plans/occurrences/{id}/record`).
- Категория нужна в плане: она подставляется при оплате или записи дохода.

## 4. Размещение и компоненты

Центральный диалог на базе `UiModal`, как окно базового шаблона и форма операции (`AppOperationEntryDialog.vue`): это принятое направление для быстрых действий (open-decisions §1.1). Новый компонент `components/plans/PlanCreateDialog.vue`; чистая логика формы и сборки запроса — `components/plans/plan-form.ts`.

Переиспользуем без копирования стилей:

| Нужно | Компонент |
| --- | --- |
| Диалог, заголовок с вкладками, крестик | `UiModal` + разметка вкладок как в `AppOperationEntryDialog.vue` (классы `entry-dialog__tabs`, акцент `danger` для платежа и `success` для дохода) |
| Крупная сумма | `OperationAmountField`; нужен новый необязательный параметр `hideStepper` (по умолчанию `false`, существующий диалог не меняется): степпер считает через `Number.parseFloat`, это вещественная арифметика над деньгами |
| Название, число месяцев, комментарий | `UiInput` |
| Дата и дата окончания | `UiDatePicker` (`quick-dates` только для даты начала) |
| Повторение, категория | `UiPillSelect` |
| Подсказки | `UiInfoTooltip` |
| Дополнительные настройки | нативный `<details>` с понятной подписью |

## 5. Поля и поведение

Вкладки: **Платёж** (акцент danger), **Доход** (акцент success). Переключение вкладки сбрасывает категорию (у типов разные категории), остальные введённые значения сохраняются.

| Поле | Платёж | Доход | Правила |
| --- | --- | --- | --- |
| Сумма* | да | да | текст; шаблон `^\d+([.,]\d{1,2})?$`, больше нуля; запятая → точка при отправке; без степпера |
| Название* | да | да | 1–120 символов после обрезки пробелов; подсказка `Например: аренда` / `Например: зарплата` |
| Дата* | «Ближайший платёж» | «Первое поступление» | по умолчанию сегодня (локальная дата браузера, как в оплате) |
| Повторение* | разово / каждый месяц / раз в несколько месяцев / раз в год | то же | по умолчанию «Каждый месяц» |
| Каждые N мес.* | при «раз в несколько месяцев» | то же | целое 2–120 |
| Категория* | категории расходов | категории доходов | только активные; поиск и пилюли как в форме операции, до 15 вариантов без запроса |
| Дополнительно | дата окончания (кроме «разово»), комментарий | то же | окончание не раньше даты начала; комментарий до 500 символов |

Подсказка под формой (всегда видна, `UiInfoTooltip` не нужен):

- Платёж: «План ничего не списывает. Когда придёт срок, нажмите «Оплатить» и выберите счёт.»
- Доход: «План ничего не добавляет на счёт. Когда деньги придут, нажмите «Записать доход».»

Кнопка отправки: «Добавить платёж» / «Добавить доход», на всю ширину, неактивна, пока нет суммы, названия и категории, и при отправке.

## 6. Данные и запросы

- Категории: страница уже загружает `useBudgetReferenceData().listCategories` (список активных). Форма получает их пропсом и фильтрует по типу (`EXPENSE` / `INCOME`) локально. Если категорий нужного типа нет (бюджет без шаблона), вместо выбора показывается подсказка «Нет категорий расходов. Сначала создайте базовый шаблон: чек-лист на главной» (для дохода — «доходов») со ссылкой на `/app`.
- Создание: `useEnvelopePlanV2().createObligationPlan(budgetId, request, key)` для платежа и `createIncomePlan(...)` для дохода. Тело `CreatePlanRequest`: `name`, `amount` (десятичная строка), `scheduledOn`, `categoryId`, `recurrence`, `intervalMonths` (только для `EVERY_N_MONTHS`), `endOn`, `comment` (пустые необязательные поля не отправляются).
- Idempotency-Key: один ключ на попытку; повтор той же заявки использует тот же ключ, любое изменение полей — новый ключ (как в `TemplatePreviewSheet.vue` и `FundingEntryHost.vue`).
- Браузер не считает деньги: сумма только проверяется по шаблону и отправляется текстом.
- После успеха: диалог закрывается, страница перечитывает списки (`GET obligations/occurrences`, `GET income-plans/occurrences`), показывает `role="status"`: «Платёж «Аренда» добавлен.» / «Доход «Зарплата» добавлен.», фокус возвращается на список. Шаг 5 чек-листа закрывается при следующем чтении дашборда.

## 7. Ошибки

- Полевые ошибки (422 `VALIDATION_FAILED` с `fieldErrors`) показываются у полей через `error` компонентов, фокус на первом ошибочном поле.
- Локальная проверка до отправки (пустое название, сумма, категория, интервал, дата окончания раньше начала) использует те же тексты, что и сервер: «Укажите название», «Введите сумму больше нуля, не более двух знаков после запятой», «Выберите категорию», «Укажите интервал от 2 до 120 месяцев», «Дата окончания не может быть раньше даты начала».
- Остальные ошибки (сеть, 403 для не-владельца, 409) — общая строка `role="alert"` вверху диалога через `v2ErrorMessage(error, 'Не удалось сохранить план. Попробуйте ещё раз.')`; диалог остаётся открытым, введённое сохраняется.
- Для роли без права управления (VIEWER) кнопки «Добавить» не показываются, если роль доступна на клиенте; иначе сервер отвечает 403, и показывается общая ошибка.

## 8. Страница «Планы» (изменения `plans.vue`)

- Кнопка «Добавить платёж» (primary) в шапке страницы через уже существующий слот `actions` компонента `ReferencePageLayout`.
- Пустой список обязательных платежей: «Обязательных платежей пока нет. Добавьте аренду, коммунальные платежи, кредиты — «Можно потратить» учтёт их заранее.» и кнопка «Добавить платёж».
- Блок «Ожидаемые доходы» (UX-16, вариант 1): строка «Это прогноз: пока деньги не пришли и вы не записали их как доход, они не входят в «На счетах» и не увеличивают «Можно потратить»» показывается только при непустом списке плановых доходов; пустое состояние: «Здесь будут ожидаемые поступления.» и кнопка «Добавить доход». Кнопка открывает тот же диалог на вкладке «Доход».
- Диалог монтируется постоянно (`open`), как `ObligationPaySheet`, чтобы возвращать фокус на вызвавший элемент.

## 9. Доступность и адаптивность

- Диалог — `role="dialog"`/фокус-ловушка из `UiModal`; вкладки как в форме операции (`role="tab"`, `aria-selected`), крестик с `aria-label="Закрыть"`.
- Все поля с подписями, ошибки связаны через `aria-describedby`/`error`, статусы не только цветом.
- Кнопки и поля — зона касания ≥44px; диалог пригоден на ширине 390px (прокрутка внутри, кнопка отправки видна).
- Акцент цветом только для состояния и типа (расход/доход), по Calm Fintech.

## 10. Тесты

Юнит-тесты (Vitest) по TDD:

- `plan-form.test.ts`: проверка суммы, названия, интервала, окончания; сборка тела запроса для каждого повторения (ONE_TIME без `endOn`, EVERY_N_MONTHS с `intervalMonths`, остальные без); запятая → точка; пустые необязательные поля не отправляются.
- `PlanCreateDialog.test.ts`: вкладки и подписи, сброс категории при смене вкладки, подсказка «ничего не списывает», пилюли категорий и фильтрация по типу, отправка платежа и дохода с правильным методом и телом, один ключ при повторе и новый при изменении, полевые ошибки с сервера, общая ошибка и сохранение ввода, блокировка при отправке, пустые категории.
- `OperationAmountField` (существующий тест): `hideStepper` скрывает кнопки, по умолчанию они есть.
- `plans.v2.test.ts` (страница): кнопки открытия, пустые состояния, текст про прогноз только при непустом списке, после сохранения списки перечитываются и показывается статус.

Playwright: сценарий для CI (владелец запускает `pnpm test:e2e`): чек-лист → «Перейти» → «Добавить платёж» → заполнить → список содержит платёж, шаг 5 выполнен. Локально браузер не запускается без прямой просьбы.

## 11. Ревью и риски

- Ревью по `.claude/rules/workflow.md`: UI/UX, QA, финальное; дополнительно API-контракт (типы клиента совпадают с `CreateObligationPlanInput` / `CreateIncomePlanInput`) и финансовое (форма создаёт план обязательств, влияющий на защиту «Можно потратить»; суммы не считаются в браузере; идемпотентность).
- Риск: `OperationAmountField` использует фиксированный `id`; диалог открывается один, дубль не возникает.
- Риск: список категорий большой; поиск и ограничение до 15 вариантов (как в форме операции).
- Зависимость: календарь (отдельная сессия) переиспользует `PlanCreateDialog`: компонент принимает необязательные `initialType` и `initialDate`, которые календарь подставит из панели дня.

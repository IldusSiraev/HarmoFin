# Порядок шагов «Начало работы» — дизайн

Дата: 2026-10-16. Область: `apps/web` (чек-лист онбординга, страница «Счета»), `apps/api` (дашборд v2, новый маршрут онбординга), Prisma (одна additive-колонка).

Документ уточняет [дизайн чек-листа онбординга](2026-09-21-onboarding-checklist-design.md) и раздел о базовом шаблоне в [Envelope Plan Model v2.2](2026-09-29%20HarmoFin_Envelope_Plan_Model_v2.2.md). Финансовые правила и формулы не меняются.

## 1. Проблема

Сейчас мастер «Начало работы» (`apps/web/app/components/dashboard/OnboardingChecklist.vue`) идёт так:

1. Базовые категории и конверты.
2. Лимит на текущий период.
3. Счета.
4. Назначить имеющиеся деньги.
5. Обязательные платежи.

Недостатки:

- Предпросмотр распределения начальных денег (`funding-preview`) сначала закрывает потребность «Обязательных». Эта потребность считается по плановым платежам. Пока платежей нет (шаг 5), «Обязательные» получают 0 ₽, и всё уходит в обычные траты. Распределение на шаге 4 заведомо неверное.
- После создания счёта с положительным остатком страница «Счета» сразу открывает окно распределения (`apps/web/app/pages/app/accounts.vue`, вызов `funding.offer({ sourceKind: 'OPENING' })`). Это дублирует шаг 4 и происходит ещё раньше, на шаге 3.
- Лимит периода подтверждается до того, как пользователь видит свои деньги и обязательные расходы, поэтому сумму приходится угадывать.
- Шаг «Обязательные платежи» засчитывается только при наличии хотя бы одного активного планового расхода из «Обязательных». У пользователя без обязательных платежей мастер не завершается никогда.

## 2. Решение

### 2.1. Новый порядок шагов

1. **Базовые категории и конверты** — без изменений.
2. **Счета** — без изменений: `done = hasAccounts`.
3. **Обязательные платежи** — `done = hasMandatoryPlans || mandatoryPlansDeclined`.
4. **План (лимит) периода** — текущая логика `periodStep()` без изменений: подтверждение или отклонение черновика шаблона либо ссылка «Задать лимит».
5. **Назначить имеющиеся деньги** — без изменений: `done = hasAccounts && !needsOpeningAssignment`.

Меняются только порядок, условие `done` шага 3 и тексты, перечисленные ниже. Счётчик «Начало работы: N/5» и сворачивание работают как раньше.

### 2.2. Шаг 3: «У меня их нет»

- Описание: «Добавьте регулярные обязательные платежи: аренду, коммунальные услуги, кредиты. Из них складывается сумма, которую нужно отложить в «Обязательные».»
- Действия невыполненного шага: ссылка «Добавить платёж» (`/app/plans`) и вторичная кнопка «У меня их нет».
- Нажатие «У меня их нет» вызывает `POST /api/v2/budgets/:budgetId/onboarding/no-mandatory-plans`. На время запроса кнопка недоступна; `Idempotency-Key` создаётся на попытку и переиспользуется при повторе после ошибки, как у решения по плану периода. После успеха мастер перечитывает статус дашборда, а `role="status"` объявляет «Шаг «Обязательные платежи» пропущен.». При ошибке текст из `v2ErrorMessage` выводится рядом с кнопкой, шаг остаётся невыполненным.
- Выполненный шаг при `mandatoryPlansDeclined && !hasMandatoryPlans` показывает: «Обязательных платежей нет. Если появятся, добавьте их в «Планах».» Отменять отказ не нужно: добавленный позже платёж всё равно оставляет шаг выполненным.

### 2.3. Шаги 4 и 5 без жёсткой блокировки

Порядок задаёт рекомендацию, а не запрет. Если шаг 5 не выполнен и шаг 3 тоже не выполнен, описание шага 5 добавляет: «Сначала добавьте обязательные платежи — иначе на них ничего не будет отложено.» Кнопка «Распределить» остаётся доступной: пользователь вправе распределить деньги осознанно (принцип v2.2 — не прятать отклонение от рекомендации за предупреждениями без выхода).

Текст шага 4 в выполненном состоянии («Деньги появятся в нём, когда вы назначите их конвертам: это шаг «Назначить имеющиеся деньги».») остаётся, ссылка на следующий шаг теперь корректна.

### 2.4. Страница «Счета»: без автоматического окна во время первичной настройки

После успешного создания счёта с положительным начальным остатком:

1. Страница перечитывает `onboarding` через `useEnvelopePlanV2().getDashboard(budgetId)`.
2. Если `onboarding.needsOpeningAssignment === false`, то есть назначения уже есть и первичная настройка позади, окно распределения открывается, как сейчас.
3. Если `needsOpeningAssignment === true`, окно не открывается. Уведомление об успехе получает описание: «Распределить деньги по конвертам можно на шаге «Назначить имеющиеся деньги» на главной.»
4. Если запрос дашборда не удался, окно не открывается (безопасный вариант по умолчанию), счёт уже сохранён, сообщение «Счёт создан.» показывается как обычно.

Браузер ничего не вычисляет: решение принимается только по серверному полю. Создание счёта и его остаток от этого не зависят.

## 3. API и данные

### 3.1. Схема

Additive-миграция в `prisma/schema.prisma`, модель `Budget`:

```prisma
onboardingNoMandatoryPlansAt DateTime? @map("onboarding_no_mandatory_plans_at") @db.Timestamptz(3)
```

Nullable, без значения по умолчанию, существующие строки не меняются. Миграция совместима с текущей стратегией развёртывания: старый код колонку игнорирует.

### 3.2. Маршрут

`POST /api/v2/budgets/:budgetId/onboarding/no-mandatory-plans`

- Тело запроса пустое. Ответ `204 No Content`.
- Аутентифицированная сессия, CSRF как у остальных v2-мутаций.
- Авторизация: активное членство в workspace бюджета и роль `OWNER` (`RolePolicy.canManage`, как у остальных настроек бюджета v2: шаблон, цели периодов, правила пополнения). Бюджет ищется через `PlanModelPolicy.requireModel(userId, budgetId, 2)` — запрос с фильтром по членству; чужой или несуществующий бюджет — `404 RESOURCE_NOT_FOUND`, бюджет v1 — `409 MODEL_VERSION_MISMATCH`, `EDITOR`/`VIEWER` — `403 FORBIDDEN`.
- Обязательный заголовок `Idempotency-Key`, как у всех v2-мутаций (это проверяет `apps/api/test/v2-openapi.integration.test.ts`); операция `DECLINE_MANDATORY_PLANS` через `IdempotencyService`. Повтор с тем же ключом воспроизводит `204`. Кроме того, идемпотентность по состоянию: если `onboarding_no_mandatory_plans_at` уже задано, значение не перезаписывается, audit не пишется, ответ `204`.
- В одной транзакции: условный `UPDATE ... WHERE onboarding_no_mandatory_plans_at IS NULL` и, если строка обновлена, audit-событие `entityType: 'budget_onboarding'`, `entityId: budgetId`, `action: 'MANDATORY_PLANS_DECLINED'`, `source: 'API'`, `newValues: { declinedAt }`.
- Слои: controller переводит HTTP, application service проверяет доступ и вызывает repository, repository делает обновление и пишет audit.
- Размещение: модуль `v2-dashboard` (рядом с блоком onboarding) — новый controller `onboarding-v2.controller.ts` с `@Controller({ path: 'budgets/:budgetId/onboarding', version: '2' })`.

### 3.3. Дашборд

В `DashboardV2OnboardingResponse` добавляется обязательное поле `mandatoryPlansDeclined: boolean` = `onboarding_no_mandatory_plans_at IS NOT NULL`. Остальные поля не меняются. Изменение additive; web-тип в `useEnvelopePlanV2` обновляется вместе с ним.

OpenAPI: новое поле, новый маршрут, ответы `204`, `400` (ключ или `budgetId`), `401`, `403`, `404`, `409`; маршрут вносится в `EXPECTED_V2` теста v2 OpenAPI.

## 4. Вне области

- Изменение `suggestedTarget` и расчёта черновика лимита: он по-прежнему берётся из шаблона.
- Перерасчёт лимита по обязательным платежам и деньгам на счетах.
- Отмена отказа от обязательных платежей.
- Изменения в предпросмотре распределения (`funding-preview`) и в финансовых формулах.

## 5. Тесты

- **Web unit, `OnboardingChecklist.test.ts`:** порядок заголовков пяти шагов; шаг 3 выполнен при `hasMandatoryPlans` и при `mandatoryPlansDeclined`; кнопка «У меня их нет» вызывает маршрут и перечитывает статус; ошибка маршрута показывается, шаг не выполнен; предупреждение в шаге 5, пока шаг 3 не выполнен, и его отсутствие после.
- **Web unit, страница «Счета»:** при `needsOpeningAssignment: true` окно не открывается и показывается подсказка; при `false` окно открывается; при ошибке дашборда окно не открывается; нулевой остаток — окна нет, как раньше.
- **API integration:** `204` и запись колонки с audit-событием; повторный вызов — `204` без второго audit-события; чужой бюджет — `404`; `EDITOR` и `VIEWER` — `403`; без CSRF — `403`; бюджет v1 — `409`; без сессии — `401`; `mandatoryPlansDeclined` в дашборде до и после.
- **OpenAPI:** проверка схемы включает новое поле и маршрут.
- **E2E (выполняет CI):** новый пользователь применяет шаблон → создаёт счёт с остатком — окно распределения не открылось → нажимает «У меня их нет» → подтверждает лимит → распределяет деньги → мастер скрывается. Существующие E2E, опирающиеся на старый порядок или на авто-окно после создания счёта, обновляются в том же изменении.

## 6. Ревью

По матрице маршрутизации: API review (маршрут, DTO, OpenAPI), Security review (доступ к данным бюджета), Backend review (миграция), UI/UX review (чек-лист, страница «Счета»), QA и final review. Денежных мутаций нет, financial review не требуется.

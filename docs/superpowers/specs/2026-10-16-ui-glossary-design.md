# Понятные термины в интерфейсе — дизайн

Дата: 2026-10-16. Область: тексты интерфейса `apps/web`, тексты `apps/api`, которые видит пользователь, и глоссарий функциональной спецификации. Поведение, API-контракт, имена в коде и финансовые правила не меняются.

## 1. Проблема

Интерфейс говорит языком модели Envelope Plan v2.2, а не языком пользователя:

- «Назначить», «Назначено», «Свободно для назначения», «Переназначить» — канцелярские слова. Новому пользователю непонятно, что «назначить деньги» — это разложить их по конвертам.
- У одного числа два названия: «Свободно для назначения» на карточке и «Не назначено» в списке конвертов на главной.
- У одного понятия два названия: «План периода» и «Лимит периода».
- Сумма к оплате называется «Обязательства», а конверт и шаг мастера — «Обязательные платежи».
- Типы конвертов «Периодная», «Накопительная», «Пользовательская» и слова «горизонт», «защищено», «границы цикла закреплены» — внутренние термины.

## 2. Решение

Ввести единый пользовательский словарь (раздел 3) и заменить им тексты во всём интерфейсе за одно изменение. Частичная замена недопустима: шаг мастера «Распределить» рядом с кнопкой «Назначить» хуже, чем сейчас.

### 2.1. Что входит

- Тексты `apps/web`: шаблоны, `aria-label`, `title`, `tooltip`, уведомления, ошибки (`useV2Error`, `FundingEntryHost`, локальные словари ошибок), справка `/app/help`, лендинг (`data/landing.ts`, `components/landing`), страница входа.
- Тексты `apps/api`, которые доходят до пользователя:
  - `message` предупреждений дашборда (`dashboard-v2.application.service.ts`);
  - `detail` problem details: web показывает его, когда кода нет в словаре ошибок;
  - `message` предупреждений операций и оплат («Назначение конверта меньше расхода…»);
  - заголовки CSV-выгрузок (`csv-export-v2.application.service.ts`).
- `example` в DTO, которые повторяют изменённые сообщения, обновляются вместе с ними (`openapi.json` перегенерируется).
- Глоссарий в функциональной спецификации: новый подраздел «7.7. Термины интерфейса» после «7.6. Расчет остатка конверта» — таблицы раздела 3 в виде «внутренний термин → текст в интерфейсе». Раздел «7.5. Нераспределенные деньги» уже использует нужное слово и не меняется.
- Unit-, integration- и E2E-тесты, которые проверяют эти тексты.

### 2.2. Что не входит

- Имена в коде, API, БД, коды ошибок, `data-testid`, маршруты: `assignment`, `funding`, `freeToAssignMinor`, `OBLIGATION` и т. п.
- `summary` и `description` OpenAPI — это документация для разработчиков.
- Доменные документы (`Envelope Plan Model v2.2`, дизайны стадий): там «назначение» остаётся внутренним термином. Связь задаёт таблица в функциональной спецификации.
- «Цикл» и «период»: термины нужны, подсказка уже объясняет их. Меняется только формулировка о закреплённых границах цикла.
- «Цель периода» (`targetAmountMinor` конверта), «Правило пополнения», «Перерасход», «Перенос».
- Слово «назначение» в смысле «цель, предназначение денег» («Назначение — под контролем», «по назначению»): оно понятно. Заменяется только смысл «действие или факт раскладывания денег по конвертам».

## 3. Глоссарий

### 3.1. Распределение денег

| Внутренний термин | Сейчас | В интерфейсе |
|---|---|---|
| assign (глагол) | назначить, назначьте | распределить, распределите |
| assignment (запись) | назначение, назначения | распределение, распределения |
| funded | Назначено | Отложено |
| free to assign | Свободно для назначения, Не назначено | Не распределено |
| opening assignment | Назначить имеющиеся деньги | Распределить деньги по конвертам |
| move between envelopes | Переназначить | Переложить |
| need to fund (подсветка) | Нужно назначить | Нужно пополнить |
| remaining in preview | Осталось назначить | Осталось распределить |
| accept preview | Назначить предложенное | Распределить как предложено |
| expense without envelope | Без назначения | Без конверта |

Правило согласования: везде, где встречается сочетание «назначить в конверт / конверту», пишем «распределить в конверт» или «отложить в конверт» — по смыслу фразы, без новых терминов.

### 3.2. Лимит периода

| Сейчас | В интерфейсе |
|---|---|
| План периода, план | Лимит на период, лимит |
| Подтвердите план периода | Подтвердите лимит на период |
| Предложенный план периода | Предложенный лимит на период |
| Принять план периода | Принять лимит на период |
| План периода подтверждён / отклонён | Лимит на период подтверждён / отклонён |
| Лимит периода, Настройте лимит периода | Лимит на период, Настройте лимит на период |

### 3.3. Обязательные платежи

| Сейчас | В интерфейсе |
|---|---|
| Обязательства (раздел, список) | Обязательные платежи |
| обязательство (один экземпляр) | платёж |
| Оплатить обязательство | Оплатить платёж |
| Пропустить обязательство? | Пропустить платёж? |
| Обязательство будет пропущено и перестанет защищать деньги на счетах. | Платёж будет пропущен, и деньги под него больше не будут удерживаться. |
| Ближайших обязательств нет. | Ближайших обязательных платежей нет. |
| К оплате по обязательствам {срок} | К оплате {срок} |
| Не хватает на обязательства | Не хватает на обязательные платежи |
| Назначено на обязательства | Отложено на обязательные платежи |

### 3.4. Типы конвертов

| Тип | Сейчас | В интерфейсе | Пояснение (`planScopeNote`) |
|---|---|---|---|
| `CURRENT_EXPENSES` | Периодная | На текущие траты | Остаток прошлого периода переносится только по вашему решению |
| `SAVINGS_GOAL` | Накопительная | Накопления | Остаток не сбрасывается при смене периода |
| `RESERVE` | Резерв | Резерв | Остаток не сбрасывается при смене периода |
| `MANDATORY_EXPENSES` | Обязательная | Обязательные платежи | Аренда, кредиты, коммунальные и другие регулярные платежи |
| `CUSTOM` | Пользовательская | Свой конверт | Деньги на любую цель без привязки к периоду |

Подсказка типов в форме конверта (`EnvelopesPlanView.vue`) переписывается теми же названиями.

### 3.5. Прочие формулировки

| Сейчас | В интерфейсе |
|---|---|
| К оплате может быть неполным: часть обязательств за горизонтом ещё не видна. | Сумма может быть неполной: более поздние платежи пока не учтены. |
| Защищено обязательствами и накоплениями | Уже отложено на платежи и накопления |
| Учитываются обязательства в пределах горизонта… (справка) | Учитываются ближайшие обязательные платежи. Более поздние появятся по мере приближения. |
| …не защищает обязательства… (справка) | …не покрывает обязательные платежи… |
| Границы цикла уже закреплены операциями и назначениями. | Даты цикла здесь изменить нельзя: в бюджете уже есть операции или распределённые деньги. |
| Пока лимит не задан, безопасный остаток не показываем: это не ноль, а отсутствие плана. | Пока лимит не задан, сумму «Можно потратить» не показываем: это не ноль, а отсутствие лимита. |

Тексты, которых нет в таблицах, переписываются по словарю 3.1–3.4 с сохранением смысла. Если фраза становится длиннее или теряет точность, исполнитель оставляет комментарий в отчёте задачи, а не придумывает новый термин.

## 4. Исполнение

- Правка механическая, но не слепая: автозамена по корню «назнач» запрещена из-за падежей и из-за смысла «предназначение» (раздел 2.2). Каждая строка правится вручную.
- Порядок: сначала словарь в функциональной спецификации, затем web, затем API-тексты и `openapi.json`, затем E2E.
- Проверка полноты: после правок поиск по `apps/web/app` и пользовательским строкам `apps/api/src` на `[Нн]азнач`, `[Пп]ереназнач`, `План периода`, `Обязательств`, `горизонт`, `Периодн`, `Пользовательск`. Каждое оставшееся вхождение должно быть комментарием, описанием OpenAPI или смыслом «предназначение».

## 5. Тесты

- Web unit: все ассерты на старые тексты обновляются на новые; в `help.test.ts` проверяется новый список четырёх чисел («На счетах», «Отложено», «Не распределено», «Можно потратить»).
- API integration: тесты, которые проверяют `detail`, `message` предупреждений и заголовки CSV, обновляются.
- OpenAPI: `openapi.json` перегенерирован, тест контракта проходит.
- E2E (выполняет CI): селекторы по тексту в `e2e/*.spec.ts` обновлены, `data-testid` не меняются.
- Проверки: `pnpm format:check`, `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm test:integration`.

## 6. Ревью

По матрице маршрутизации: UI/UX review (тексты, `aria-label`, понятность), API review (`example` DTO и `openapi.json`, коды и схемы не меняются), QA и final review. Денежных мутаций, доступа к данным и миграций нет: financial, security и backend review не требуются.

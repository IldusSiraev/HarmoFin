# Дизайн: удаление аккаунта

**Версия:** 1.1
**Дата:** 18.10.2026
**Статус:** утверждён владельцем, реализовано (расхождения с v1.0 см. ниже)

## Контекст

Функциональная спецификация (§14, «Настройки пользователя») требует пункт «удаление аккаунта», а §19 (безопасность) — «корректное удаление и выгрузка пользовательских данных». Development spec (§15, runbooks) упоминает runbook «удаление аккаунта и выгрузка данных». В коде этого нет: `apps/web/app/pages/app/settings/` содержит только `general`, `password`, `sessions`; в `auth.controller.ts` нет эндпоинта удаления. Это расхождение со спецификацией v1, а не новая функция.

Дополнительный мотив — доверие нового пользователя: возможность гарантированно уйти и стереть данные снимает барьер «не введу ничего реального».

Что уже есть и переиспользуется:

- `UserStatus` содержит `ACTIVE | LOCKED | DELETED`.
- `auth.application.service.ts` пропускает вход, recovery, смену пароля и `me` только при `status === 'ACTIVE'`; сессии проверяются через пользователя.
- Worker (`notification.handler.ts`, `plan-occurrence.handler.ts`) обрабатывает только `workspace.status = 'ACTIVE'` и `budget.status = 'ACTIVE'`.
- Механика одноразовых токенов с хешем (`RecoveryToken`, `token.service.ts`) и отправка писем (`email-sender.ts`, `smtp-email.sender.ts`).
- Периодические задания worker (`job.repository.ts`, `recurringJobs`).
- Все FK в схеме — `onDelete: Restrict`, поэтому физическое удаление выполняется явно, в порядке зависимостей.

## Решения владельца

1. **Отложенная очистка.** Сразу после запроса аккаунт недоступен, данные скрыты и не обрабатываются; через 30 дней worker физически стирает данные.
2. **Отмена — по одноразовой ссылке из письма.** Знание пароля само по себе не возвращает аккаунт.

## Цели

- Пользователь может удалить свой аккаунт из настроек, подтвердив паролем.
- В течение 30 дней удаление отменяется по ссылке из письма.
- Через 30 дней все финансовые и персональные данные пользователя физически удалены из основной БД.
- Удаление не затрагивает данные других бюджетов и пользователей.

## Не-цели

- Удаление отдельного бюджета без удаления аккаунта.
- Передача владения рабочим пространством другому участнику (в v1 нет совместного доступа).
- Стирание данных из резервных копий: копии удаляются по своему сроку хранения (фиксируется в runbook).
- Юридические тексты (политика конфиденциальности) — отдельная задача.
- Новые форматы экспорта: используется существующий экспорт.

## Модель состояний

```
ACTIVE --(POST /me/deletion)--> PENDING_DELETION --(purge_after наступил, worker)--> DELETED
                                      |
                                      +--(POST /auth/deletion/cancel, токен)--> ACTIVE
```

- Новое значение `UserStatus.PENDING_DELETION`. Существующие проверки `status !== 'ACTIVE'` автоматически закрывают вход, recovery и сессии.
- `DELETED` — конечное состояние после очистки.
- При переходе в `PENDING_DELETION` рабочие пространства, где пользователь — `OWNER`, и их бюджеты переводятся в `ARCHIVED`; при отмене — обратно в `ACTIVE`. Чтобы при отмене не активировать то, что было архивировано до удаления, `account_deletions` хранит список id, которые были `ACTIVE` на момент запроса (`archived_workspace_ids`, `archived_budget_ids`), и восстанавливаются только они.
- Членства пользователя в чужих рабочих пространствах (задел на будущее; в v1 их нет) деактивируются (`is_active = false`, `removed_at`) и при отмене восстанавливаются по тому же принципу (`deactivated_membership_ids`).
- Email остаётся занятым до очистки: повторная регистрация на этот адрес возможна только после перехода в `DELETED`.

## Данные

### Миграция (только добавление)

- `ALTER TYPE "UserStatus" ADD VALUE 'PENDING_DELETION'`.
- `ALTER TYPE "SessionRevokeReason" ADD VALUE 'ACCOUNT_DELETED'`.
- `ALTER TYPE "WorkerJobType" ADD VALUE 'PURGE_DELETED_ACCOUNTS'`.
- Новая таблица `account_deletions`:

| Поле | Тип | Назначение |
|---|---|---|
| `id` | uuid PK | |
| `user_id` | uuid, **без FK** | переживает очистку |
| `requested_at` | timestamptz | |
| `purge_after` | timestamptz | `requested_at + 30 дней` |
| `restore_token_hash` | char(64), unique | SHA-256 одноразового токена |
| `archived_workspace_ids` | uuid[] | что вернуть при отмене |
| `archived_budget_ids` | uuid[] | что вернуть при отмене |
| `deactivated_membership_ids` | uuid[] | что вернуть при отмене |
| `restored_at` | timestamptz null | |
| `purged_at` | timestamptz null | |

Индексы: `(purged_at, restored_at, purge_after)` для выборки worker.

Инвариант «не больше одного активного запроса на пользователя» реализован не частичным уникальным индексом, а атомарным переходом статуса: `UPDATE users SET status = 'PENDING_DELETION' WHERE id = … AND status = 'ACTIVE'` — вторая одновременная заявка не находит строку для обновления и завершается ошибкой до создания второй `account_deletions`.

Таблица не содержит email, имени или финансовых данных и остаётся после очистки как неперсональный след факта удаления.

## API (`/api/v1`, OpenAPI)

### `POST /me/deletion`

- Требует сессию и CSRF. Rate limit как у смены пароля.
- Тело: `{ password: string }`.
- В одной транзакции:
  1. Загрузить пользователя по сессии; `status` должен быть `ACTIVE`.
  2. Проверить пароль (Argon2id). Неверный → `422 CURRENT_PASSWORD_INVALID` с `fieldErrors.password` (как в смене пароля).
  3. Если в рабочих пространствах, где пользователь `OWNER`, есть другие активные участники → `409 ACCOUNT_DELETION_HAS_MEMBERS`. В v1 недостижимо, но защищает от стирания чужого доступа в будущем.
  4. Перевести пользователя в `PENDING_DELETION`; рабочие пространства и бюджеты — в `ARCHIVED`; деактивировать членства в чужих рабочих пространствах.
  5. Отозвать все сессии пользователя (`revoked_reason = ACCOUNT_DELETED`); погасить непогашенные recovery-токены (`consumed_at = now`).
  6. Создать `account_deletions` с хешем нового токена.
  7. Записать `AuditEvent` (`entityType = 'auth'`, `action = 'ACCOUNT_DELETION_REQUESTED'`, без персональных данных в `old/newValues`, только `purgeAfter`).
- После коммита отправить письмо со ссылкой `/restore-account?token=…` от `config.mail.webBaseUrl` (как ссылка сброса пароля) и датой очистки. Ошибка отправки логируется без токена и не откатывает удаление; повторно письмо можно получить только через поддержку (см. runbook).
- Ответ `202` `{ purgeAfter: string }`, cookie сессии очищается.
- Повторная отправка: после шага 1 повтор невозможен (пользователь уже не `ACTIVE`, сессия отозвана), поэтому дублирования не возникает; отдельный idempotency-ключ не нужен.

### `POST /auth/deletion/cancel`

- Без сессии. Без CSRF-токена, как `auth/recovery/confirm`; глобальный `OriginGuard` проверяет `Origin`. Rate limit как у recovery.
- Тело: `{ token: string }`.
- В одной транзакции:
  1. Найти `account_deletions` по хешу, где `restored_at` и `purged_at` пусты и `purge_after > now`; пользователь в `PENDING_DELETION`. Иначе → `422 ACCOUNT_RESTORE_TOKEN_INVALID` (одна общая ошибка, без раскрытия причины).
  2. Вернуть пользователя в `ACTIVE`; восстановить сохранённые workspace, бюджеты и членства, если они всё ещё `ARCHIVED`/неактивны.
  3. Поставить `restored_at`; токен становится непригодным.
  4. `AuditEvent` (`entityType = 'auth'`, `action = 'ACCOUNT_DELETION_CANCELLED'`).
- Ответ `204`. Сессию не создаёт: пользователь входит обычным способом.

### Не меняются

- `login`, `recovery/request`, `recovery/confirm`, `me`, проверка сессии — уже отсекают не-`ACTIVE`.
- `register` с email пользователя в `PENDING_DELETION` ведёт себя как с любым занятым email.

## Очистка (worker)

- Новое периодическое задание `PURGE_DELETED_ACCOUNTS` (`jobKey = 'accounts:purge-deleted-v1'`) в `recurringJobs`, раз в сутки.
- Выборка: `account_deletions` с `purge_after <= now`, `restored_at IS NULL`, `purged_at IS NULL`, пользователь в `PENDING_DELETION`; пачками по 20.
- Каждый аккаунт — отдельная транзакция с повторной проверкой условий под блокировкой строки `account_deletions` (`FOR UPDATE`), чтобы гонка с отменой была невозможна.
- Запуск задания ограничен бюджетом времени 200 секунд: по истечении этого окна запуск не берёт в обработку новые аккаунты (уже начатая транзакция аккаунта доводится до конца), оставшиеся обрабатываются следующим запуском.
- Изоляция сбоев: ошибка очистки одного аккаунта (`AccountPurgeCoverageError` или иная) откатывает только его транзакцию, логируется структурированным событием `purgeFailure` (`deletionId`, имя класса ошибки, без финансовых значений) и репортится в error reporter; задание продолжает обработку остальных аккаунтов пачки и следующих пачек.
- Порядок удаления (FK `Restrict`):
  1. Для каждого бюджета из рабочих пространств, где пользователь `OWNER`: все таблицы со ссылкой на бюджет, от листьев к корням — платежи по планам, распределения, части переводов, переводы, движения/назначения/периоды/правила конвертов, перераспределения, вхождения и уведомления, планы, операции, ревизии цикла, idempotency, события аудита бюджета, счета, конверты, категории (сначала дочерние), затем сам бюджет. В список входят и legacy-таблицы, оставленные после перехода на модель конвертов v2.
  2. События аудита и уведомления рабочего пространства, членства, рабочее пространство.
  3. Данные пользователя в собственном (аккаунтном) скоупе: сессии, recovery-токены, собственные членства пользователя и его события аудита уровня аккаунта (`actor = user AND workspace_id IS NULL AND budget_id IS NULL`). Строки, где пользователь — актор в чужом/другом workspace или budget скоупе, этим шагом не трогаются (они уже удалены в рамках шага 1–2 для его собственных бюджетов/workspace либо принадлежат данным, не затрагиваемым этим удалением) — остаются как часть истории соответствующего скоупа.
  4. Анонимизация строки `users`: `email = 'deleted-<id>@invalid'`, `password_hash = ''`, `display_name = null`, `email_verified_at = null`, `status = 'DELETED'`. Строка не удаляется, чтобы не затрагивать возможные будущие ссылки и чтобы `account_deletions` можно было сопоставить.
  5. `purged_at = now`.
- Идемпотентность: каждый шаг — «удалить, если есть»; прерванная транзакция откатывается целиком и повторяется в следующем запуске.
- Защита покрытия таблиц реализована двумя уровнями: во время выполнения задание проверяет актуальный список таблиц с `budget_id`/`workspace_id` через `information_schema` и бросает `AccountPurgeCoverageError`, если находит таблицу вне `BUDGET_TABLES_IN_DELETE_ORDER`; отдельный unit-тест сверяет тот же список со схемой через Prisma DMMF на этапе CI, до того как недостающая таблица попадёт в продакшен.
- Логи: нет отдельного успешного лога с количеством строк и длительностью на каждую очистку; только сбои логируются событием `purgeFailure` (`deletionId`, имя класса ошибки), без email и финансовых значений.

### Исключение из правила логического удаления

Правило «логическое удаление финансовых записей» сохраняется для всех обычных сценариев. Очистка аккаунта — единственное явное исключение: по требованию владельца после 30-дневного окна отмены данные стираются физически. Исключение фиксируется в development spec (раздел о логическом удалении) и в runbook.

## UI

### Настройки — страница «Удаление аккаунта»

- В `/app/settings` (страница-хаб) — строка «Удаление аккаунта», ведущая на отдельную страницу `/app/settings/delete-account` (не диалог — тот же паттерн, что у «Пароль»/«Сессии»).
- На странице:
  - что произойдёт: вход закрыт сразу, данные удаляются безвозвратно через 30 дней, отмена — по ссылке из письма;
  - ссылка «Сначала выгрузите данные» на существующий экспорт;
  - поле «Текущий пароль» с ошибкой поля;
  - чекбокс «Понимаю, что данные удалятся безвозвратно через 30 дней»;
  - кнопка «Удалить аккаунт» в danger-стиле по Calm Fintech guidelines (активна при заполненном пароле и отмеченном чекбоксе).
- После `202` — переход на публичную страницу `/account-deleted?until=<дата>` с заголовком «Аккаунт удаляется» и текстом с датой очистки; письмо со ссылкой отмены уже отправлено.

### Страница `/restore-account?token=…`

- По образцу `reset-password.vue`: заголовок, пояснение, кнопка «Отменить удаление».
- Успех — сообщение «Удаление отменено», та же кнопка меняет подпись на «Перейти ко входу» (переход на `/login`); в футере также есть ссылка «Войти». Ошибка — «Ссылка недействительна или устарела» и контакт поддержки.
- Токен не попадает в логи и аналитику; после отправки удаляется из адресной строки (`history.replaceState`).

### Доступность

Клавиатурное управление диалогом, видимый фокус, подпись и ошибка поля пароля, предупреждение не только цветом (иконка + текст), touch-friendly кнопки.

## Письмо

Тема: «Аккаунт HarmoFin будет удалён». Содержит дату очистки, ссылку отмены, предупреждение «Если это были не вы — отмените удаление и смените пароль». Новый метод `sendAccountDeletionScheduled` в `EmailSender`.

## Тесты

- **API unit/integration:** неверный пароль → `422` поля; без CSRF → отказ; `409` при других участниках; после удаления сессии отозваны, вход и `me` отклонены; письмо отправлено после коммита и его сбой не откатывает удаление; отмена: валидный, повторный и просроченный токены; при отмене не активируется то, что было архивировано до запроса; аудит запроса на удаление записан без персональных данных.
  - Отложено (не реализовано в этой итерации): тест транзакционности запроса на удаление (ошибка на середине — ничего не изменилось); тест отмены с чужим токеном (не принадлежащим вызывающему); отдельный тест восстановления членств при отмене; тест, что аудит отмены записан без персональных данных; тест откат транзакции на середине отмены.
- **Worker:** очищает только просроченные; пропускает восстановленные и уже очищенные; гонка с отменой (блокировка); идемпотентный повтор; данные другого пользователя и бюджета не затронуты; защитный тест покрытия таблиц по схеме Prisma.
- **OpenAPI:** оба эндпоинта описаны с запросами, ответами и ошибками.
- **Web unit:** карточка и диалог в настройках (ошибка поля, блокировка кнопки, переход после успеха); страница восстановления (успех, ошибка, очистка токена из URL).
- **E2E (CI):** сценарий «удалить аккаунт → вход отклонён → отмена по токену из Mailpit → вход успешен». Локально Playwright не запускается.

## Изменения в версии 1.1 (приведение к реализации)

- Код ошибок API — `422` (не `400`) для неверного пароля (`CURRENT_PASSWORD_INVALID`, `fieldErrors.password`) и для недействительного токена восстановления (`ACCOUNT_RESTORE_TOKEN_INVALID`).
- `AuditEvent.entityType = 'auth'`, действия — `ACCOUNT_DELETION_REQUESTED` / `ACCOUNT_DELETION_CANCELLED`.
- Инвариант «не больше одного активного запроса на пользователя» держит не частичный уникальный индекс, а атомарный `UPDATE … WHERE status = 'ACTIVE'`.
- UI подтверждения — отдельная страница настроек `/app/settings/delete-account`, а не диалог; страница восстановления переиспользует одну кнопку, меняющую подпись на «Перейти ко входу» после успеха.
- Шаг очистки 3 ограничен собственным скоупом пользователя: сессии, recovery-токены, его членства и события аудита уровня аккаунта (`actor = user AND workspace_id IS NULL AND budget_id IS NULL`); строки-актёр в чужих/других workspace- или budget-скоупах этим шагом не трогаются.
- Добавлены бюджет времени на запуск задания (200 секунд, без захвата новых аккаунтов по истечении) и изоляция сбоя по аккаунту (`purgeFailure`, задание продолжает остальные аккаунты).
- Защита покрытия таблиц — двухуровневая: runtime-проверка `information_schema` (`AccountPurgeCoverageError`) плюс unit-тест на Prisma DMMF.

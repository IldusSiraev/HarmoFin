# Страница «Правила пополнения» — дизайн

Дата: 2026-10-20. Статус: утверждён владельцем, ждёт плана реализации.

## Проблема

Правило пополнения конверта настраивается в диалоге `RuleSettingsSheet` по одному конверту. Текущее правило нигде не видно (API не отдаёт его на чтение, диалог пишет «Текущее правило здесь не показывается»). Порядок распределения задаётся числом «Приоритет», хотя на деле это очередь: `FundingPreviewApplicationService` сортирует правила по `priority` (при равенстве — по `envelopeId`) и раздаёт доход сверху вниз, пропуская `MANUAL` и архивные конверты. Пользователь не видит ни очередь, ни правило конкретного конверта.

## Цель

Отдельная страница, где все конверты бюджета показаны карточками: очередь распределения в явном порядке со стрелками, перестановка перетаскиванием и кнопками, правило задаётся прямо в карточке, всё сохраняется одной кнопкой. Текущее правило видно и на странице, и в деталях конверта.

## Не входит

- Изменение модели данных правил и предложения для дохода (по-прежнему одно предложение «категория дохода → конверт» на бюджет).
- Изменение алгоритма preview/confirm распределения.
- Удаление одиночных эндпоинтов `PUT envelopes/:envelopeId/funding-rule` и `PUT income-category-suggestion` (остаются для совместимости).

## 1. API (`/api/v2/budgets/:budgetId`, контроллер `envelope-plan.controller.ts`)

### `GET funding-rules`

Ответ:

```json
{
  "items": [
    {
      "id": "uuid",
      "envelopeId": "uuid",
      "type": "PERCENT_OF_INCOME",
      "priority": 30,
      "fixedAmountMinor": null,
      "percentBasisPoints": 1000
    }
  ]
}
```

- Форма элемента совпадает с существующим `FundingRuleResponse`.
- Отбор по `budget_id` в самом запросе репозитория; доступ — участник бюджета с правом чтения (та же политика, что у `GET envelopes`).
- Порядок: `priority`, затем `envelopeId`, — ровно как сортирует preview.
- Конверты без строки в `envelope_funding_rules` в ответ не попадают.

### `PUT funding-rules`

Только OWNER (та же `requireManageRole`, что в одиночном PUT), `CsrfGuard`, обязательный `Idempotency-Key`.

Тело:

```json
{
  "queue": [
    { "envelopeId": "uuid", "type": "SUM_OF_PLANS" },
    { "envelopeId": "uuid", "type": "FIXED_PER_PERIOD", "fixedAmount": "15000" },
    { "envelopeId": "uuid", "type": "PERCENT_OF_INCOME", "percentBasisPoints": 1000 }
  ],
  "outside": [{ "envelopeId": "uuid", "type": "MANUAL" }],
  "incomeSuggestion": {
    "enabled": true,
    "sourceCategoryId": "uuid",
    "targetEnvelopeId": "uuid"
  }
}
```

Правила:

- `queue` — правила с типом не `MANUAL`; порядок массива = порядок распределения. Сервер сам присваивает `priority = (index + 1) * 10`. Клиент `priority` не передаёт.
- `outside` — только `type: "MANUAL"`, сервер ставит `priority = 0`.
- Поля по типу — как в `putFundingRuleSchema`: `fixedAmount` (десятичная строка рублей, больше нуля) только для `FIXED_PER_PERIOD` и `SUGGESTED_FIXED`; `percentBasisPoints` (целое 0..10000) только для `PERCENT_OF_INCOME`.
- Один `envelopeId` встречается во всём теле не больше одного раза.
- Каждый конверт принадлежит бюджету и не архивирован; `SUM_OF_PLANS` — только у конверта `MANDATORY_EXPENSES`. Те же коды ошибок, что в одиночном PUT (`ENVELOPE_ARCHIVED`, `FUNDING_RULE_TYPE_NOT_ALLOWED`, 404 для чужого/несуществующего конверта).
- `incomeSuggestion` — та же валидация, что у `PUT income-category-suggestion` (категория `INCOME`, не архивная; конверт не архивный; при `enabled: true` оба id обязательны; при `false` оба `null`). Поле обязательное: клиент всегда передаёт текущее состояние.
- Конверты, отсутствующие в теле, не изменяются (их правила остаются как есть).
- Всё выполняется в одной транзакции под `lockBudget`: любая ошибка — ничего не сохранено.
- Строка правила, у которой тип, суммы и `priority` не изменились, не перезаписывается и не получает audit. Изменённые правила и изменённое предложение пишут audit тем же способом, что одиночные эндпоинты.
- Идемпотентность: новая операция `PUT_FUNDING_RULES_BATCH`, `requestHash` — sha256 от нормализованного тела (минорные единицы вместо строк сумм). Повтор с тем же ключом и телом возвращает сохранённый ответ; с тем же ключом и другим телом — 409, как в существующих мутациях.
- Ошибки полей в `fieldErrors` с путём: `queue.2.fixedAmount`, `outside.0.type`, `incomeSuggestion.sourceCategoryId`. Для ошибок уровня конверта (архив, тип не допустим) — `queue.N.envelopeId` / `queue.N.type`.

Ответ 200:

```json
{
  "items": [ /* как GET funding-rules */ ],
  "incomeSuggestion": { "enabled": true, "sourceCategoryId": "uuid", "targetEnvelopeId": "uuid" }
}
```

OpenAPI: request/response DTO, заголовок `Idempotency-Key`, ответы 400/401/403/404/409/422 с `ProblemDetailsResponse`, по образцу соседних эндпоинтов. `openapi.json` перегенерируется.

### Слои

- Контроллер только переводит HTTP.
- Новый метод прикладного сервиса (рядом с `putFundingRule` в `period-target.application.service.ts` или отдельный `funding-rules-batch.application.service.ts`, если файл перерастает разумный размер) выполняет проверки и вызывает `FundingRuleRepository.saveRule` и `IncomeCategorySuggestionRepository.save` в одной транзакции.
- Чтение — метод `FundingRuleRepository.listRules(budgetId)` с фильтром по бюджету в запросе.
- Миграция БД не нужна.

## 2. Страница `/app/envelopes/rules`

### Маршрут

`apps/web/app/pages/app/envelopes.vue` переезжает в `pages/app/envelopes/index.vue` (и тест рядом), новая страница — `pages/app/envelopes/rules.vue`. URL `/app/envelopes` не меняется.

Кнопка «Задать правила» (secondary) стоит рядом с «Создать конверт» в `EnvelopesPlanView` и ведёт на страницу. На странице заголовок «Правила пополнения» и ссылка «Назад к конвертам».

### Загрузка

Параллельно: список конвертов (`listEnvelopes`, без архивных), `GET funding-rules`, бюджет (поля `incomeAllocation*`) и активные категории дохода. Пока грузится — скелетоны; при ошибке — сообщение и «Повторить».

### Блок «Предложение для дохода»

Переключатель «Включено», затем строка «Доход категории [select] предлагать в конверт [select]» и `InfoTooltip`: «Когда приходит доход этой категории, сервер предложит направить его в выбранный конверт. Деньги не распределяются сами — распределение вы подтверждаете отдельно.» Когда переключатель выключен, селекты неактивны. В карточке выбранного конверта появляется метка «Доход: <категория>» (текст и иконка, не только цвет).

### Блок «Очередь распределения»

Заголовок с `InfoTooltip`: «Доход распределяется сверху вниз: сначала первый конверт, потом следующий, пока хватает денег.»

Список `<ol>`, между карточками декоративная стрелка вниз (`aria-hidden`). Карточка:

- ручка перетаскивания (иконка `GripVertical`, `aria-hidden`; кнопки ↑/↓ — доступная альтернатива);
- номер позиции и название конверта;
- метка «Доход: …», если конверт получает предложение;
- селект «Тип правила» с `InfoTooltip`, тексты подсказок — текущие `TYPE_HINTS`; `SUM_OF_PLANS` доступен только у обязательного конверта;
- поле «Сумма на период, ₽» / «Предлагаемая сумма, ₽» / «Процент от дохода, %» по типу, с подсказкой формата и ошибкой у поля;
- icon-only кнопки «Выше» / «Ниже» (`ChevronUp`/`ChevronDown`, `aria-label` «Переместить выше: <название>», тултип); у крайних позиций неактивны.

### Блок «Вне очереди»

Заголовок с `InfoTooltip`: «Для этих конвертов сервер не предлагает сумму — их пополняете вручную при распределении.» Карточки без ручки и без кнопок ↑/↓, отсортированы по названию. Конверт без правила — пометка «Правило не задано» и пустой селект типа.

### Зона определяется типом

- Тип «Вручную» → карточка переходит в «Вне очереди».
- Любой другой тип у карточки вне очереди → карточка встаёт в конец очереди.
- Перетаскивание и ↑/↓ работают только внутри очереди.
- Конверт без правила, которому тип так и не выбран, в тело PUT не попадает.

### Перестановка

- Composable `useSortableList` на pointer events (мышь и касание, без новой зависимости): захват за ручку, вертикальное перемещение, вставка по середине соседней карточки, `touch-action: none` на ручке, автопрокрутка у краёв окна.
- После перемещения (pointer или кнопки) — объявление в `aria-live="polite"`: «<Название>: позиция 3 из 7». Фокус после кнопки ↑/↓ остаётся на той же кнопке перемещённой карточки (или на соседней, если крайняя стала неактивной).

### Сохранение

- Нижняя панель, прилипающая к низу экрана: «Сохранить» (primary) и «Отменить изменения» (tertiary). Обе неактивны, пока состояние совпадает с загруженным.
- Перед отправкой — проверка формы ввода (как в текущем `RuleSettingsSheet`): ошибки показываются у поля, фокус на первое неверное поле. Сервер остаётся источником истины.
- Один `Idempotency-Key` на попытку с одинаковым телом (тот же приём `attemptKey`, что сейчас).
- Успех: тост «Правила сохранены. Распределения и остатки не изменились.», состояние перечитывается из ответа.
- `fieldErrors` с путём `queue.N.*` / `outside.N.*` / `incomeSuggestion.*` сопоставляются с карточкой по индексу отправленного тела и показываются у поля; прочие ошибки — общим сообщением `v2ErrorMessage` над панелью.
- Уход со страницы с несохранёнными изменениями: `onBeforeRouteLeave` → `UiConfirmDialog` «Есть несохранённые изменения. Уйти без сохранения?»; закрытие вкладки — `beforeunload`.

### Визуал

По Calm Fintech: карточки как остальные поверхности (`UiCard`), icon-only действия в карточке, иконки `@lucide/vue`, светлая и тёмная темы через токены. Мобильная ширина — одна колонка, ручка и кнопки не меньше 44px.

## 3. Детали конверта

- Убираются пункт «Правило пополнения» в `EnvelopePlanDialog.vue` и в меню строки `EnvelopesPlanView.vue`, вместе с подключением `RuleSettingsSheet`.
- В `EnvelopePlanDialog` — строка только для чтения: «Правило: <тип>[, <сумма/процент>] · №N в очереди», «Правило: вручную» или «Правило не задано». Данные — `GET funding-rules`, загружаемый один раз в `EnvelopesPlanView` и перечитываемый после изменений; номер в очереди — позиция среди правил не `MANUAL` в порядке ответа.
- Кнопка «Изменить цель периода» в `EnvelopePlanDialog` открывает новый `PeriodTargetDialog`: блок «Текущая цель периода» из `RuleSettingsSheet` переносится без изменения поведения (предупреждение о последствиях, подтверждение, идемпотентность, недоступность при `periodStart === null`).
- `RuleSettingsSheet.vue`, `RuleSettingsSheet.test.ts` и `EnvelopesPlanView.rules.test.ts` удаляются; покрытие переносится в тесты новой страницы и `PeriodTargetDialog`.

## 4. Тесты

API (интеграционные, `apps/api/test/v2-funding-rules.integration.test.ts` или новый файл рядом):

- GET: только правила своего бюджета; порядок; чужой бюджет — 404/403 как у соседних GET.
- PUT: присвоение `priority` по порядку; `MANUAL` в `outside` с `priority = 0`; конверты вне тела не меняются.
- Атомарность: ошибка в одном элементе — ни правила, ни предложение не изменены.
- Валидация: дубль `envelopeId`, `MANUAL` в `queue`, не-`MANUAL` в `outside`, `SUM_OF_PLANS` у необязательного, архивный конверт, конверт чужого бюджета, лишние поля по типу, некорректное предложение; пути в `fieldErrors`.
- Роли: не-OWNER — 403. CSRF обязателен.
- Идемпотентность: повтор — тот же ответ без второго audit; тот же ключ с другим телом — 409.
- Audit только для реально изменённых правил и предложения.
- Preview после batch-сохранения использует новый порядок.
- OpenAPI содержит оба эндпоинта и схемы.

Web (Vitest):

- Зона меняется по типу; без типа конверт не попадает в тело.
- ↑/↓ и `useSortableList` меняют порядок; объявление `aria-live`; фокус.
- Тело PUT: порядок `queue`, поля по типу, `incomeSuggestion`.
- Ошибки сервера с путём показываются у нужного поля нужной карточки.
- Кнопки сохранения неактивны без изменений; подтверждение ухода.
- Метка «Доход: …» у выбранного конверта.
- `EnvelopePlanDialog` показывает правило и номер в очереди; `PeriodTargetDialog` сохраняет поведение прежнего блока.

E2E (сценарий для CI, локально не запускается): открыть «Конверты» → «Задать правила», переставить два конверта, сменить тип одного на процент, сохранить, открыть детали конверта и увидеть новое правило и номер.

# Окно распределения: все конверты сразу — дизайн

Дата: 23.10.2026. Статус: дизайн одобрен владельцем.

## Проблема

Окно «Распределить деньги» (`FundingReviewSheet`) показывает только строки, которым сервер по очереди правил пополнения предложил сумму больше нуля. Очередь останавливается, как только деньги кончаются, поэтому:

- нельзя направить деньги в конверт, до которого очередь не дошла (пример: 103,05 ₽ свободных денег целиком уходят в «Первый период», «Моя копилка» в окне отсутствует);
- нельзя обнулить предложенную строку: окно требует сумму больше нуля, потому что confirm отклоняет строку с нулём, а без неё пересчитанный `previewHash` не совпадает (`PREVIEW_STALE`).

Обходной путь — «Позже», затем «Переложить → Из свободных сюда» на странице конвертов — неочевиден.

## Решение (одобрено)

Окно показывает **все активные конверты**. Строки, где сработало правило, предзаполнены суммой правила, остальные пусты. Пользователь правит любую сумму; пустое поле или 0 означает «не распределять». Остаток «Осталось распределить» пересчитывает сервер по ходу ввода.

Выбран подход «список строит сервер»: preview сам возвращает строку на каждый конверт с правильным `periodId`. Альтернатива «клиент склеивает preview и список конвертов» отклонена — она дублирует в браузере выбор периода и может разойтись с сервером.

Правила пополнения по-прежнему только предлагают суммы; очередь (`rule-engine.ts`) не меняется. Освобождённая пользователем сумма не перетекает к следующим правилам, а остаётся в «Осталось распределить».

## Сервер

### `POST /api/v1/budgets/{budgetId}/funding/preview`

`lines` содержит строку для каждого неархивного конверта бюджета:

| Конверт | Строки | `periodId` |
|---|---|---|
| Непериодный (кроме обязательного) | одна | `null` |
| Периодный, слот = текущая половина | одна | период текущей половины |
| Периодный, слот = другая половина | одна | ближайший период этого слота (следующая половина) |
| `MANDATORY_EXPENSES` | `…MANDATORY_CURRENT`; плюс `…MANDATORY_NEXT`, если у конверта правило `SUM_OF_PLANS` (как сейчас) | `null` |

- `suggestedMinor` строки = предложение правила или override пользователя; для конверта без предложения — `"0"`. Строки с нулём больше не отфильтровываются.
- Порядок: строки очереди правил в порядке `suggestFunding` (`…MANDATORY_NEXT` с `slotAfterPeriod` — последней в очереди); затем конверты без правила (или с `MANUAL`) по имени.
- Набор строк строится **до** применения overrides, поэтому override по `lineId` всегда находит свою строку (сейчас override по `…MANDATORY_NEXT`, когда очередь до неё не дошла, ошибочно становится строкой `…MANDATORY_CURRENT`). Override с `lineId`, которого нет среди строк, сопоставляется по `envelopeId/periodId`, как override без `lineId`.
- Новые поля строки (аддитивно): `queuePosition` — номер в очереди правил (1, 2, …) или `null` для конвертов без правила; `periodStartsOn` / `periodEndsOn` — даты периода строки (ISO) или `null` для непериодных.
- Период другой половины создаётся тем же идемпотентным `FundingRuleRepository.getOrCreatePeriod`, что уже используется для `FIXED_PER_PERIOD` и для подсказки по категории дохода (структурная запись `envelope_period` со своим аудитом). Период текущей половины для периодного конверта без правила `FIXED_PER_PERIOD` — так же через `getOrCreatePeriod`.
- Подсказка по категории дохода (`categoryOverride`) продолжает задавать предложенную сумму; остальные конверты при ней тоже присутствуют с `"0"`.
- `remainingMinor`, `errors` (`OVERRIDES_EXCEED_SOURCE`), `periodTargetDrafts`, `mandatoryGapMinor` — без изменений.
- `overrides` с суммой `0` разрешены (как и сейчас) и попадают в состояние для `previewHash`.

### `POST /api/v1/budgets/{budgetId}/funding/confirm`

- Строка `lines[]` с `amount` = `0` допустима: она передаётся в пересчёт preview как override (хеш совпадает с preview, который видел пользователь), но **не создаёт** назначение и не участвует в симуляции лимитов.
- Записываются только строки с суммой больше нуля; правила денег прежние: лимит дохода (L03), физически свободные деньги (L02), блокировка бюджета, идемпотентность. Хеш запроса идемпотентности считается по всем строкам, включая нулевые.
- Если положительных строк нет и не выбрана ни одна цель периода — прежний пустой ответ `200` без записи.
- Отрицательные и нечисловые суммы по-прежнему `VALIDATION_FAILED`.

### Контракт и совместимость

Форма запросов не меняется; в ответ preview добавлены необязательные для клиента поля строки (`queuePosition`, `periodStartsOn`, `periodEndsOn`); меняется семантика: в preview появляются строки `"0"`, confirm принимает `amount ≥ 0`. OpenAPI-описания обоих эндпоинтов обновить (описание `lines`, `amount`). Других потребителей, кроме `apps/web`, нет; старый клиент, отправляющий только положительные строки, продолжает работать.

## Окно (`FundingReviewSheet` / `FundingEntryHost`)

- Шапка без изменений: источник, «Можно распределить», плашка «Деньги остаются на ваших счетах», предупреждение о нехватке на обязательные.
- Вводный текст: «Суммы предложены по правилам пополнения. Измените любую или впишите сумму в другой конверт. Деньги со счетов никуда не переводятся.»
- Заголовки колонок: «Конверт» / «Сумма». Строка: номер `queuePosition` (только у строк с правилом), `EnvelopeTypeIcon`, название, подпись (для периодных — даты `periodStartsOn`–`periodEndsOn`; для обязательных слайсов — «текущий период» / «следующий период» в названии, как сейчас), поле суммы. Пустая строка — пустое поле с плейсхолдером «0».
- Пустое поле и `0` валидны и отправляются как `0`. Сообщение «Введите сумму больше нуля…» удаляется. Остаётся проверка формата («Введите сумму числом, не более двух знаков после запятой»).
- Существующие подсказки строки (до цели, «всё оставшееся») сохраняются.
- Пересчёт: после паузы ввода ~400 мс и при уходе из поля/Enter хост запрашивает preview с overrides = все строки. Ответ устаревшего запроса отбрасывается (существующий `generation`). Пока запрос идёт — индикатор у итога; поле, которое пользователь сейчас редактирует, не перезаписывается ответом.
- Итог «Осталось распределить» — в закреплённом футере диалога (`#footer` у `UiModal`) вместе с кнопками; список прокручивается внутри тела. Итог в `aria-live="polite"`. Значение только из `remainingMinor` сервера; клиент деньги не складывает.
- Кнопки: «Позже» и основная «Распределить» (вместо «Распределить как предложено»). «Распределить» неактивна при ожидании ответа, ошибке, перерасходе (`remainingMinor` < 0 / `OVERRIDES_EXCEED_SOURCE`), ошибке строки и когда все суммы нулевые и не выбрана цель периода (проверка строк на `"0"`, без арифметики).
- Confirm отправляет все строки последнего preview, включая нулевые, и его `previewHash`.
- Доступность: у каждого поля `label` с названием конверта (и периодом), видимый фокус, ошибки у поля, порядок табуляции — сверху вниз. На телефоне диалог на весь экран (как сейчас).
- Лендинг (`IncomePreview`, `landing.ts`) не меняется.

## Тесты

- API (integration): preview возвращает строку на каждый неархивный конверт, нули для конвертов без предложения; конверт другой половины получает период следующей половины; архивный конверт отсутствует; confirm с нулевыми строками создаёт назначения только для положительных и хеш совпадает с preview; все строки нулевые — пустой `200`; лимит дохода и свободных денег прежний; изоляция бюджета и роль OWNER — прежние проверки.
- Web (unit): окно показывает все строки, пустое поле = 0 без ошибки, кнопка «Распределить» и её блокировки, итог из ответа сервера; хост — debounce пересчёта, отбрасывание устаревших ответов, confirm со всеми строками.
- E2E: обновить сценарии распределения под новый текст кнопки и полный список; прогон в CI.
- Ревью: финансовое, безопасность и изоляция, API/OpenAPI, UI/UX, QA, финальное.

## Вне объёма

- Изменение очереди правил и автоматическое «перетекание» освобождённых сумм.
- Распределение в архивные конверты и в периоды дальше ближайшего.
- Лендинг и демо-данные.

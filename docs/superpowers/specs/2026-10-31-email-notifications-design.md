# Уведомления на почту: основа доставки и email — дизайн

Дата: 31.10.2026. Статус: согласован владельцем. Продолжает [ленту семьи](2026-10-30-family-activity-feed-design.md) и пункт 18.6 [функциональной спецификации](2026-08-30-family-budget-app-spec.md). Решением владельца от 31.10.2026 доставка уведомлений по email переносится в объём; остальные внешние каналы по-прежнему вне объёма.

## Цель

Участник семьи, который не заходит в приложение каждый день, узнаёт о важном по почте: получает сводку «что нового в семье» и сразу получает письмо о просроченном платеже или напоминание календаря. Заодно появляется общая основа доставки (настройки каналов, очередь отправки, отписка), на которую позже ляжет Telegram.

## Порядок подпроектов внешней доставки

1. Основа доставки и email — этот документ.
2. Уведомления в Telegram — второй канал той же очереди, отдельная спецификация.
3. Ввод операций и событий календаря через Telegram — отдельная спецификация, опирается на привязку из пункта 2.
4. Web push — вместе с установкой как приложение (PWA), отдельная спецификация.

## Объём

- настройки канала email на пользователя: главный переключатель, «срочные письма», дайджест (выключен / ежедневно / еженедельно), показ сумм по согласию;
- срочные письма: просроченный плановый платёж (`PLAN_OVERDUE`) и напоминание календаря (`CALENDAR_REMINDER`);
- дайджест: сводка событий семьи из ленты и плановые платежи на сегодня, в 08:00 по часовому поясу бюджета;
- очередь отправки в воркере с повторами;
- отписка по ссылке из письма без входа и заголовки `List-Unsubscribe`;
- страница настроек `/app/settings/notifications`.

Вне объёма (кандидаты на расширение):

- Telegram, web push и другие каналы (подпроекты 2–4);
- выбор времени отправки дайджеста;
- письма по остальным типам уведомлений (`PLAN_UPCOMING`, `PLAN_TODAY`, состав семьи и т. д.) как отдельные срочные;
- построчное повторение ленты в письме;
- статистика открытий, трекинг-пиксели, картинки в письмах;
- внешние сервисы рассылок.

## Решения владельца

| Вопрос | Решение |
|---|---|
| Первый подпроект | Основа доставки и email; Telegram следующим каналом |
| Что уходит на почту | Дайджест и срочное: просроченный платёж и напоминание календаря |
| Включение по умолчанию | Выключено; пользователь включает сам в настройках |
| Суммы в письмах | По умолчанию без сумм; отдельный переключатель с явным согласием |
| Расписание дайджеста | Ежедневно или еженедельно (понедельник), в 08:00 по часовому поясу бюджета; пустой не отправляется |
| Способ доставки | Очередь отправки (outbox) в воркере, текущий SMTP; без внешних сервисов рассылок |
| Вид дайджеста | Сводный: счётчики по людям и видам событий, ссылка на ленту |
| Подтверждение почты | По запросу при включении канала, не при регистрации; ссылка на 24 часа |

## Доступ и приватность

- Письма уходят только на подтверждённый email (`users.email_verified_at` не пустой). Без подтверждения канал включить нельзя. Подтверждения почты в коде до этой работы не было (поле есть, но не заполнялось), поэтому оно входит в объём — раздел «Подтверждение почты».
- Получатель — активный участник бюджета на момент отправки. Права перепроверяются при каждой отправке; бывший участник писем не получает, его письма в очереди отменяются.
- Дайджест собирается только по бюджету получателя, фильтр `workspace_id` и `budget_id` в запросе. Видимость событий — как у ленты: роль `VIEWER` дайджест тоже получает, срочные письма о платежах — только тем, кому адресовано уведомление в приложении.
- Без согласия текст строится только из имён, названий и дат. С согласием (`includeAmounts`) добавляются суммы. Суммы и текст письма собираются в момент отправки и не хранятся в очереди. Снятие согласия действует на всё, что ещё не отправлено.
- В логах, метриках и аудите нет текста писем, сумм и адресов. `lastError` хранит только код и класс ошибки SMTP.
- Аудит фиксирует изменение настроек канала, выдачу и отзыв согласия на суммы, отписку по ссылке.
- Перед выпуском проверить текст [политики обработки ПД](2026-10-18-legal-documents-design.md): цель «уведомления на почту» и передачу сумм при согласии. Если цели нет — дополнить в той же задаче, что и настройки.

## Данные

Новая миграция, только добавление.

`notification_channel_settings` — одна строка на пользователя и канал:

| Поле | Тип | Смысл |
|---|---|---|
| `user_id` | uuid, FK `users` | владелец настроек |
| `channel` | enum `NotificationChannel` (`EMAIL`) | канал; позже `TELEGRAM`, `PUSH` |
| `enabled` | boolean, default false | главный переключатель |
| `urgent_enabled` | boolean, default true | срочные письма при включённом канале |
| `digest_frequency` | enum `DigestFrequency` (`OFF`, `DAILY`, `WEEKLY`), default `DAILY` | частота дайджеста |
| `include_amounts` | boolean, default false | показывать суммы |
| `amounts_consent_at` | timestamptz, null | когда дано согласие; сбрасывается при отзыве |
| `created_at`, `updated_at` | timestamptz | |

Уникальность `(user_id, channel)`. Настройки общие для пользователя, не для бюджета: в v1 у пользователя один бюджет семьи.

`notification_deliveries` — очередь:

| Поле | Тип | Смысл |
|---|---|---|
| `id` | uuid | |
| `workspace_id`, `budget_id` | uuid, составной FK `budgets` | бюджет события |
| `user_id` | uuid, FK `users` | получатель |
| `channel` | `NotificationChannel` | |
| `kind` | enum `DeliveryKind` (`URGENT`, `DIGEST`) | |
| `notification_id` | uuid, null, FK `notifications` | источник срочного письма |
| `digest_period_start` | timestamptz, null | начало окна дайджеста |
| `digest_period_end` | timestamptz, null | конец окна дайджеста |
| `dedupe_key` | varchar(255) | `urgent:<notificationId>` или `digest:<DAILY|WEEKLY>:<локальная дата>` |
| `status` | enum `DeliveryStatus` (`PENDING`, `SENT`, `FAILED`, `CANCELLED`) | |
| `attempts` | int, default 0 | |
| `next_attempt_at` | timestamptz | |
| `sent_at` | timestamptz, null | |
| `last_error` | varchar(200), null | код ошибки без содержимого |
| `unsubscribe_token_hash` | char(64), null, unique | SHA-256 токена отписки этого письма; ставится при отправке |
| `created_at`, `updated_at` | timestamptz | |

Уникальность `(budget_id, user_id, channel, dedupe_key)`.

`email_verification_tokens` — одноразовые токены подтверждения почты, как `recovery_tokens`: `id`, `user_id` (FK `users`), `token_hash` char(64) unique (HMAC через `TokenService`), `expires_at`, `consumed_at`, `created_at`; индекс `(user_id, consumed_at, expires_at)`. Индекс `(status, next_attempt_at)` для выборки очереди. Строки не удаляются задачей отправки; очистка отправленных старше 90 дней — в задаче дайджеста.

## Срочные письма

- Обработчики `PLAN_OVERDUE` (`EVALUATE_BUDGET_NOTIFICATIONS`) и `CALENDAR_REMINDER` (`EVALUATE_CALENDAR_REMINDERS`) при создании уведомления в той же транзакции вставляют запись в очередь, если у получателя `enabled` и `urgent_enabled`.
- Повторная оценка того же уведомления не создаёт второго письма: `dedupe_key` по `notificationId`, вставка `ON CONFLICT DO NOTHING`.
- Если уведомление закрыто (`resolved_at`) до отправки, письмо отменяется.

## Дайджест

Задача `BUILD_EMAIL_DIGESTS`, раз в 15 минут:

- выбирает пользователей с `enabled` и `digest_frequency <> OFF` и их активные бюджеты;
- считает локальное время по часовому поясу бюджета; дайджест назначен, если локальное время в окне 08:00–11:59 текущего дня (для `WEEKLY` — понедельника) и записи с этим `dedupe_key` ещё нет. Окно не даёт отправить дайджест сразу, если пользователь включил его днём, и покрывает простой воркера до 4 часов;
- окно: от `digest_period_end` прошлого отправленного дайджеста до момента постановки, не длиннее 1 дня для `DAILY` и 7 дней для `WEEKLY`; при первом дайджесте — то же ограничение;
- вставляет запись `DIGEST` с границами окна; само содержимое собирается при отправке;
- при пропуске запуска (воркер был остановлен) отправляется только последний назначенный дайджест; более старые даты не догоняются.

Содержимое при отправке:

- события из `audit_events` за окно по тем же 16 видам, что у ленты, без собственных действий получателя и без строк без автора;
- группировка по автору, счётчики по группам: операции (`TRANSACTION_*`), переводы (`TRANSFER_*`), конверты (`ENVELOPE_*`), планы (`PLAN_*`), календарь (`CALENDAR_EVENT_*`), состав семьи (`MEMBER_*`);
- плановые платежи на сегодня по бюджету: название, при согласии — сумма;
- нет событий и платежей — письмо отменяется (`CANCELLED`), окно всё равно считается обработанным.

Список 16 видов в воркере — копия из `apps/api/src/activity-feed/feed-kinds.ts`. Тест воркера читает файл API и сверяет набор, чтобы списки не разошлись.

## Отправка

Задача `DELIVER_NOTIFICATIONS`, каждую минуту:

- берёт до 20 записей `PENDING` с `next_attempt_at <= now` через `FOR UPDATE SKIP LOCKED`, отмечает попытку;
- перепроверяет: канал включён, нужная опция включена, email подтверждён, участник активен, уведомление не закрыто; иначе `CANCELLED`;
- собирает письмо и отправляет через SMTP (`nodemailer`, та же версия, что в API);
- успех — `SENT`, `sent_at`; ошибка — `attempts + 1`, пауза 1 мин, 5 мин, 30 мин, 2 ч; после 5-й неудачи — `FAILED`;
- метрики по образцу `JobRunnerMetrics`: исходы отправки по каналу и виду, без адресов.

Воркер получает SMTP-переменные (`SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `MAIL_FROM`) и базовый адрес веб-приложения для ссылок — в конфиге, `.env.example`, staging и production compose.

## Письма

- Две части: простой текст и HTML со встроенными стилями, палитра Calm Fintech, без картинок и внешних ресурсов.
- Темы: «HarmoFin: что нового в семье за 31 октября», «HarmoFin: что нового в семье за неделю», «Просрочен платёж «Ипотека»», «Напоминание: «Родительское собрание» сегодня в 18:00».
- Дайджест: строки по людям («Анна: 3 операции, 1 пополнение конверта, 1 событие календаря»), блок «Платежи сегодня», кнопка «Открыть ленту» на `/app/activity`.
- Срочное: одна фраза, дата, кнопка «Открыть» на `actionPath` уведомления.
- Подвал каждого письма: почему пришло письмо, ссылки «Настроить уведомления» (`/app/settings/notifications`) и «Отписаться».
- Заголовок `List-Unsubscribe: <https://…/unsubscribe?token=…>` — ссылка на страницу отписки в вебе. `List-Unsubscribe-Post` (отписка в один клик) не ставится: почтовый клиент шлёт такой `POST` без заголовка `Origin`, а глобальный `OriginGuard` API его отклоняет; ослаблять защиту ради этого не стоит.
- Токен отписки создаётся воркером при отправке каждого письма (32 случайных байта, `base64url`), в строке очереди хранится только SHA-256. Ссылка живёт столько же, сколько строка очереди (90 дней).
- Имена и названия экранируются в HTML.

## API

Все ответы и ошибки описаны в OpenAPI. Эндпоинты относятся к аккаунту, а не к бюджету, поэтому живут в `/api/v1` рядом с `me`, `auth` и `legal` (добавление без изменения существующих путей); инварианты `/api/v2` (путь бюджета, `Idempotency-Key`, обязательные 404/409) к ним не подходят.

- `GET /api/v1/me/notification-settings/email` — настройки, `emailVerified`, маскированный email для показа. Если строки нет — значения по умолчанию.
- `PUT /api/v1/me/notification-settings/email` — CSRF; тело `{enabled, urgentEnabled, digestFrequency, includeAmounts, amountsConsent?}`. Включение `includeAmounts` требует `amountsConsent: true`, иначе 422. `enabled: true` без подтверждённого email — 409 `EMAIL_NOT_VERIFIED`.
- `POST /api/v1/notifications/unsubscribe` — публичный, тело `{token}`, без сессии и CSRF; глобальный `OriginGuard` требует origin веба; ограничение частоты по IP (`AuthRateLimitGuard`). Ищет письмо по SHA-256 токена и выключает канал его получателю; неизвестный токен — тот же ответ 204, чтобы не раскрывать существование.
- Страница `/unsubscribe?token=…` в вебе показывает кнопку «Отписаться» и вызывает `POST`; открытие страницы ничего не меняет (сканеры ссылок не должны отписывать).

## Подтверждение почты

Подтверждение по запросу, не при регистрации:

- на странице настроек уведомлений при неподтверждённой почте — кнопка «Подтвердить почту»;
- `POST /api/v1/me/email-verification` — сессия, CSRF, ограничение частоты; гасит прежние неиспользованные токены, создаёт новый на 24 часа, отправляет письмо со ссылкой `/verify-email?token=…`; если почта уже подтверждена — 204 без письма;
- `POST /api/v1/auth/email-verification/confirm` — публичный, тело `{token}`, ограничение частоты; гасит токен и ставит `email_verified_at`; неверный, использованный или просроченный токен — 422 `EMAIL_VERIFICATION_TOKEN_INVALID`;
- страница `/verify-email?token=…` в вебе подтверждает по кнопке «Подтвердить» и показывает результат;
- аудит: `EMAIL_VERIFICATION_REQUESTED`, `EMAIL_VERIFIED` (`entityType: 'auth'`), без адреса и токена.

## Интерфейс

Пункт настроек «Уведомления на почту» в `/app/settings`, страница `/app/settings/notifications`:

- адрес почты только для чтения; если не подтверждён — подсказка и главный переключатель недоступен;
- переключатель «Присылать уведомления на почту»;
- при включённом канале: «Срочные письма» с пояснением (просроченный платёж, напоминание календаря) и выбор «Дайджест: не присылать / каждый день / раз в неделю», подпись «в 08:00 по времени бюджета»;
- «Показывать суммы в письмах»: при включении диалог с текстом согласия и кнопками «Согласен» / «Отмена»; отказ возвращает переключатель;
- сохранение по кнопке, ошибки у полей.

Calm Fintech: карточка настроек как на соседних страницах, переключатели и радио с подписями, без цветового кодирования. Клавиатура, видимый фокус, подписи у всех полей, текст ошибки не только цветом.

## Тесты

- Юниты воркера: расчёт 08:00 и понедельника по часовому поясу, переход на летнее/зимнее время, окно дайджеста, `dedupe_key`, расписание повторов, текст письма без сумм и с суммами, экранирование HTML, сверка 16 видов с API.
- Интеграция: выборка очереди с `SKIP LOCKED` двумя исполнителями, отмена письма исключённому участнику и при снятом согласии, изоляция бюджетов в дайджесте, пустой дайджест, срочное письмо в одной транзакции с уведомлением, отсутствие дубля при повторной оценке.
- API: настройки (по умолчанию, 409 без подтверждения, 422 без согласия), CSRF, отписка по токену и неизвестный токен, OpenAPI.
- Веб: страница настроек, диалог согласия, страница отписки.
- Интеграция воркера: срочное письмо и дайджест проходят путь «очередь → сборка письма → отправитель» с подменённым отправителем; токен отписки из письма выключает канал через API.
- E2E в CI (воркер там не запущен): подтверждение почты по письму из Mailpit, включение канала, дайджест, диалог согласия на суммы.

## Review

Security (адреса, токены отписки, приватность сумм, доступ при отправке), backend (миграция, очередь, воркер), API, UI/UX, QA, финальный. Financial review не нужен: финансовые данные не изменяются, суммы только читаются.

## Разбивка на PR

1. API и данные: миграция, подтверждение почты, настройки, отписка, OpenAPI.
2. Воркер: очередь, срочные письма, дайджест, письма, конфиг и compose.
3. Веб: страница настроек, диалог согласия, страницы подтверждения и отписки, E2E.

E2E в CI не запускает воркер, поэтому путь «воркер → SMTP» проверяется интеграционным тестом с подменённым отправителем, а E2E проверяет подтверждение почты через Mailpit и настройки.

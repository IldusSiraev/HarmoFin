# Часовой пояс бюджета: выбор при регистрации и безопасная смена

Статус: **черновик на утверждение владельцем**. Код не пишется до одобрения. После одобрения — план по `writing-plans`.

## 1. Проблема

1. Бюджет создаётся при регистрации (`createPersonalWorkspace` из `auth.application.service.ts`) с `NEW_BUDGET_TIMEZONE = 'Europe/Moscow'`. Пользователь пояс не выбирает. Для не-московских семей письма-дайджесты (08:00 по поясу бюджета), напоминания календаря и «сегодня» в дашборде сдвинуты.
2. `V2BudgetSettingsApplicationService.update` отвечает `409 TIMEZONE_CHANGE_REQUIRES_RECONCILIATION`, если `hasConfirmedPlanHistory` (любая подтверждённая операция, любое назначение/перенос, подтверждённая цель или смена цикла). Исправить ошибочный пояс после первой же операции нельзя.

## 2. Обоснование текущего правила

Источники: envelope v2.2 roadmap (стр. 21), план 04b (T02), `reset-unconfirmed-periods.ts`. Довод: «в существующих фактах хранятся календарные даты, а не UTC-инстанты», поэтому смена пояса «потребует отдельного решения о перекладке календарных дат». Сознательно отложено, не обосновано анализом конкретных столбцов.

## 3. Какие данные зависят от пояса

Пояс влияет только на то, как «сейчас» превращается в календарную дату (`todayInTimezone`). Границы периодов и циклов (`cycleAndPeriodFor`) — чистая арифметика над датами, от пояса не зависят.

| Данные | Тип | Откуда дата | Зависит от пояса |
|---|---|---|---|
| `Transaction.occurredOn`, `Transfer`, `IncomeAllocation`, `EnvelopeReallocation` (v1) | DATE | вводит пользователь | нет. Есть проверка «подтверждённый факт не позже сегодня» |
| `EnvelopePeriod.startsOn/endsOn` | DATE | цикл | нет |
| `PlanOccurrence.scheduledOn`, `RegularPlan.*On` | DATE | правило повторения | нет (горизонт материализации считается от «сегодня») |
| `EnvelopeAssignment.effectiveOn`, `EnvelopeMovement.effectiveOn` | DATE | **сервер: сегодня в поясе на момент подтверждения** | **да** |
| `Budget.planModelActivatedOn`, `BudgetCycleRevision.effectiveOn` (если не задан явно) | DATE | сервер: сегодня в поясе | да |
| `CalendarEvent` all-day (`startsOn/endsOn`, `repeatUntil`) | DATE | вводит пользователь | нет |
| `CalendarEvent` timed (`startsAt/endsAt`) | timestamptz | пользователь ввёл время **в поясе бюджета**, сохранён инстант | **да**: при смене пояса инстант тот же, настенное время сдвигается |
| Дайджесты, напоминания, `digestDedupeKey` | вычисляется воркером | локальная дата/время | да, но состояния в данных нет: подхватывается новым поясом сразу |
| Балансы, отчёты, дашборд | вычисляются | `effectiveOn/occurredOn <= today(tz)` | чувствительны только к п. «даты, штампуемые сервером» |

Вывод: правило избыточно. Подтверждённые операции пользовательских дат не «переезжают». Реальный риск один: серверные штампы `effectiveOn` и timed-события календаря.

Граничные случаи при смене пояса на Δ часов:

- Восток (Москва → Екатеринбург, +2 ч). «Сегодня» наступает раньше, ни один сохранённый штамп не оказывается в будущем. Опасности нет.
- Запад (Δ < 0). В течение |Δ| часов после локальной полуночи нового пояса штамп `effectiveOn = «сегодня по старому»` может оказаться **завтрашним** по новому. Балансы фильтруют `effective_on <= today`, и назначение временно «пропало» бы. Это единственная ситуация, где смена пояса может исказить расчёт.

## 4. Варианты

**A. Только выбор при регистрации, правило смены не менять.** Просто, но не решает уже созданные бюджеты (в том числе прод владельца).

**B. Разрешить смену с точной защитой (рекомендация).** Убрать `hasConfirmedPlanHistory` как условие. Вместо него в той же транзакции под `lockBudget`:
1. Проверить: ни один серверный штамп (`assignment/movement.effectiveOn`, `planModelActivatedOn`, `revision.effectiveOn` ≤ границ) и ни один подтверждённый факт не окажется позже `todayInTimezone(now, новый пояс)`. Иначе `409 TIMEZONE_CHANGE_WOULD_FUTURE_DATE_FACTS` с текстом «Повторите после 00:00 по новому поясу». На восток не срабатывает никогда.
2. Историю не трогать: ни одна сохранённая дата не меняется.
3. Timed-события календаря: режим `timedEvents` в теле PATCH — `KEEP_WALL_CLOCK` (сохранить настенное время, сдвинуть инстанты на разницу смещений на дату события; для исправления ошибочного пояса) или `KEEP_INSTANT` (сохранить момент; для переезда). Если timed-событий нет, поле не нужно. Если есть и поле не передано — `422`.
4. `resetUnconfirmedPeriods` оставить: он безвреден.
5. Аудит: старый/новый пояс, режим, число сдвинутых событий. Идемпотентность и `lockBudget` как сейчас.

UI: при смене пояса диалог подтверждения с объяснением («Прошлые операции и даты не изменятся. Письма и напоминания будут приходить по новому времени») и, при наличии timed-событий, выбор режима.

**C. B + явная сверка (preview/confirm по образцу `cycle-change`).** Добавить read-only preview с перечнем затронутых строк и `previewHash`. Надёжнее, но по сути повторяет B: затронутых финансовых данных нет, preview нужен лишь для календаря. Не окупается; вернуться, если появятся пояса-зависимые финансовые данные.

**D. Хранить пояс как ревизии с датой вступления (`BudgetCycleRevision.timezone`).** Схема уже допускает, но все расчёты читают `Budget.timezone`. Потребует переписать чтение на `settingsAt` во всех сервисах. Избыточно для v1.

## 5. Выбор пояса при создании

- Добавить в `RegisterInput` необязательное `timezone` (IANA, та же `isValidTimezone`); отсутствует → `Europe/Moscow` (обратная совместимость `/api/v1`, аддитивно). Передавать в `createPersonalWorkspace` → `Workspace.timezone`, `Budget.timezone`, `newBudgetModelData(now, tz)`.
- Форма регистрации (`register.vue`): поле «Часовой пояс» (тот же поиск по списку, что в настройках) с предзаполнением `Intl.DateTimeFormat().resolvedOptions().timeZone`, если он есть в `Intl.supportedValuesOf('timeZone')`; иначе Москва. Подсказка: «Нужен для писем и напоминаний; позже можно изменить в настройках».
- Другие места вызова `createPersonalWorkspace` (принятие приглашения, восстановление после удаления аккаунта, `workspace.repository`): оставить по умолчанию. Для них пояс подтягивается из явной смены.
- Мягкая подсказка в «Общих настройках»: если пояс браузера ≠ пояс бюджета, показать «Ваш браузер в Asia/Yekaterinburg. Изменить?» (владельцу бюджета). Решает случай прод-бюджета без поиска по списку.

## 6. Обновление документации

Функциональная спека (стр. 1282 «по умолчанию `Europe/Moscow`») и справка/настройки: пояс выбирается при регистрации, меняется владельцем в любой момент; прошлые даты не меняются. Убрать текст ошибки `TIMEZONE_CHANGE_REQUIRES_RECONCILIATION` из `useV2Error.ts` и справки.

## 7. Совместимость и риски

- `PATCH /api/v2/budgets/:id/settings`: код `TIMEZONE_CHANGE_REQUIRES_RECONCILIATION` исчезает, добавляются `TIMEZONE_CHANGE_WOULD_FUTURE_DATE_FACTS` и поле `timedEvents`. Для OpenAPI это расширение, но клиент, ожидавший старый 409, учесть в web-коде (единственный клиент).
- Дубль `Workspace.timezone` и `Budget.timezone`: сейчас PATCH меняет только бюджет. Решить в плане: синхронизировать оба или считать `Workspace.timezone` неиспользуемым (читается лишь для DTO и fallback при удалении аккаунта).
- Один дайджест может прийти повторно или пропасть в день смены (ключ дедупликации — локальная дата). Принимается, документируется.
- Данные владельца не трогаются; миграций схемы нет. Смену пояса прод-бюджета владелец делает уже через UI после релиза.

## 8. Тесты (для плана)

- Интеграционные: смена на восток при подтверждённых операциях и назначениях проходит, история не меняется; смена на запад при штампе «завтра по новому» даёт 409; режимы `timedEvents`; изоляция бюджетов, роль OWNER, идемпотентность, аудит.
- Unit: сдвиг инстантов по смещению на дату события, включая переход DST.
- Register: валидный/невалидный/отсутствующий `timezone`, `planModelActivatedOn` в новом поясе.
- Web: предзаполнение пояса браузера, подсказка в настройках, диалог подтверждения. Playwright только в CI.

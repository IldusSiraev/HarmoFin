# Команды Telegram-бота: дизайн

Дата: 02.11.2026. Статус: согласован владельцем, не реализован.

Это третий подпроект внешнего канала Telegram (пункт 18.3 [функциональной спецификации](2026-08-30-family-budget-app-spec.md)). Он строится поверх [уведомлений в Telegram](2026-10-31-telegram-notifications-design.md): привязка чата, webhook и клиент Bot API уже работают в production. Решением владельца от 02.11.2026 ввод операций и событий календаря из чата, а также команды просмотра переносятся в объём.

## Цель

Участник семьи, у которого привязан личный чат, может прямо в Telegram:

- провести расход, доход или перевод между счетами;
- создать простое событие календаря;
- посмотреть последние операции, ближайшие плановые платежи, события календаря и остатки на счетах.

Всё это работает только после того, как пользователь отдельно включит команды в настройках и подтвердит согласие.

## Объём

- Пошаговые диалоги на inline-кнопках:
  - `/expense` — расход;
  - `/income` — доход;
  - `/transfer` — перевод между счетами;
  - `/event` — событие календаря.
- Команды просмотра: `/last`, `/plans`, `/events`, `/balance`.
- Служебные команды: `/help`, `/cancel`. Меню команд бота задаётся через `setMyCommands`.
- Переключатель «Команды бота» с отдельным согласием на странице `/app/settings/telegram`.
- Таблица `telegram_dialogs` хранит состояние диалога. Worker удаляет устаревшие диалоги.
- Обработка `callback_query`. Бот редактирует одно своё сообщение диалога вместо того, чтобы присылать новые.

### Вне объёма

Эти пункты — кандидаты на будущее расширение:

- ввод одной строкой и разбор свободного текста;
- распределение дохода по конвертам из чата: в ответе только кнопка «Распределить», ведущая в приложение;
- проведение планового платежа из чата: только ссылка в приложение;
- повтор, участники и описание события;
- правка и удаление операций из чата;
- черновики (DRAFT) из чата;
- выбор бюджета в боте;
- Mini App (WebApp) и групповые чаты.

## Решения владельца

| Вопрос | Решение |
|---|---|
| Способ ввода | Пошагово кнопками, без разбора свободного текста |
| Статус операции | Сразу `CONFIRMED`, после сводки и кнопки «Провести» |
| Типы операций | Расход, доход, перевод между счетами (v2 `direct-transfer`, без конвертов) |
| Событие | Простое: название, дата, время или «весь день», напоминание |
| Просмотр | `/last` — 10 операций, `/plans` и `/events` — 7 дней, плюс `/balance` |
| Включение | Отдельный переключатель с согласием, по умолчанию выключен |
| Состояние диалога | Таблица в БД |

## Доступ и безопасность

- Обновления принимаются только из личных чатов (`chat.type = "private"`).
- Пользователя определяет только привязка `telegram_links.chat_id`. Данные профиля Telegram из обновления не используются.
- Каждое обновление проверяется по цепочке:
  1. привязка есть;
  2. `users.status = 'ACTIVE'`;
  3. `telegram_links.commands_enabled_at` не null;
  4. есть активное участие в пространстве.

  Если какая-то проверка не прошла, бот коротко объясняет причину и прикладывает кнопку-ссылку на настройки, если это возможно.
- Бюджет — тот, что пользователь последним выбрал в приложении: участие в пространстве с наибольшим `last_selected_at`, затем самое раннее по `created_at`, его активный бюджет с `planModelVersion = 2`. Название бюджета показывается в сводках.
- Деньги, права и бюджет проверяют существующие application services. Бот вызывает те же методы, что и HTTP-контроллеры:
  - `requireWriter`;
  - `requireAccountOwner`;
  - фильтр по `budget_id`;
  - блокировка бюджета;
  - аудит.

  Своих расчётов сумм и остатков у бота нет.
- Идемпотентность: ключ — `telegram:<id диалога>`. Повторное нажатие «Провести» или повторная доставка того же `callback_query` возвращает уже созданную запись.
- Суммы разбираются строкой: пробелы убираются, запятая заменяется точкой, затем проверка `^\d+(\.\d{1,2})?$` и больше нуля. Дальше сумма уходит строкой в схему API. Float не используется.
- Не попадают в логи, метрики, аудит и `last_error`:
  - `chat_id`;
  - текст сообщений пользователя;
  - суммы;
  - названия.

  Аудит создаваемых записей идёт обычным путём, источник — `TELEGRAM`.
- Ограничение частоты: не больше 30 обновлений в минуту на чат. Обновления сверх лимита отбрасываются без ответа.
- Включение команд требует `{ enabled: true, consent: true }`, иначе 422 `TELEGRAM_COMMANDS_CONSENT_REQUIRED`. Без привязки — 409 `TELEGRAM_NOT_LINKED`. Включение и выключение пишутся в аудит.
- При отвязке (через веб, `/stop` или блокировку бота) строка привязки удаляется, а вместе с ней команды и диалоги. После новой привязки команды нужно включить заново. Если тот же чат привязывается повторно (`refreshLink`), состояние команд сохраняется.

Текст согласия: «Ответы бота с суммами, остатками и названиями остаются в истории чата Telegram. Из чата можно проводить операции от вашего имени. Я согласен включить команды бота».

## Диалоги

### Общие правила

- Новая команда завершает активный диалог чата и начинает новый. `/cancel` завершает диалог явно.
- У чата одна строка `telegram_dialogs`. Диалог живёт 30 минут с последнего шага.
- Бот отправляет одно сообщение и на каждом следующем шаге редактирует его через `editMessageText`. Текстовый ответ пользователя, например сумму или название, бот не удаляет.
- `callback_data` имеет вид `<версия диалога>:<действие>[:<индекс>]`, например `7:acc:2`, и не длиннее 64 байт. UUID в `callback_data` не попадают. Индекс ссылается на список, сохранённый в состоянии шага. Если версия не совпадает или диалога нет, бот отвечает `answerCallbackQuery` с текстом «Диалог устарел, начните заново».
- На каждый `callback_query` бот отвечает `answerCallbackQuery`, чтобы в Telegram пропал индикатор загрузки.
- Списки выбора показываются по 8 кнопок в два столбца. Если вариантов больше, добавляется кнопка «Ещё ›», и список листается по кругу.
- Если сервис вернул ошибку, бот показывает её русский текст из `detail` и остаётся на шаге сводки. Если ошибка не распознана, бот пишет «Не получилось сохранить, попробуйте ещё раз».
- Даты считаются в часовом поясе бюджета. «Сегодня» — это сегодняшняя дата в этом поясе.

### `/expense` и `/income`

1. Бот просит ввести сумму. Неверная сумма — повторная просьба с примером «1250 или 1250,50».
2. Выбор счёта: активные счета пользователя, только свои, потому что этого требует `requireAccountOwner`. Если своих счетов нет, бот пишет «Нет своих счетов» и даёт кнопку-ссылку `/app/accounts`.
3. Выбор категории: активные категории типа операции.
4. Конверт, только у расхода: «Без конверта» и активные конверты бюджета.
5. Дата: «Сегодня», «Вчера» или «Другая». Для «Другой» вводится `ДД.ММ` (текущий год в поясе бюджета) или `ДД.ММ.ГГГГ`.
6. Комментарий: текст до 500 символов или кнопка «Пропустить».
7. Сводка: бюджет, тип, сумма, счёт, категория, конверт, дата, комментарий. Кнопки «Провести», «Изменить сумму», «Отмена».

После «Провести» бот вызывает `TransactionV2ApplicationService.create` со `status: 'CONFIRMED'` и пишет «Записано: −1 250,50 ₽ · Продукты · Карта» с кнопкой «Открыть в приложении». У дохода добавляется кнопка «Распределить», которая ведёт в приложение. Диалог завершается.

### `/transfer`

1. Сумма.
2. Счёт-источник: свои активные счета.
3. Счёт-получатель: активные счета бюджета, кроме источника.
4. Дата.
5. Комментарий.
6. Сводка и «Провести».

Перевод создаёт `DirectTransferApplicationService.create`.

### `/event`

1. Название, от 1 до 200 символов.
2. Дата: «Сегодня», «Завтра» или «Другая».
3. Время: кнопка «Весь день» или текст `ЧЧ:ММ` либо `ЧЧ:ММ-ЧЧ:ММ`. Если указано только начало, конец ставится через час, но не позже `23:59`.
4. Напоминание: «Нет», «За 15 мин», «За 1 час», «За день».
5. Сводка и «Создать».

Событие создаётся через `CalendarApplicationService.createEvent` без повтора и участников. Ответ содержит кнопку «Календарь».

## Команды просмотра

| Команда | Данные | Кнопка |
|---|---|---|
| `/last` | 10 последних проведённых операций и переводов бюджета: дата, сумма со знаком, категория или «Перевод», счёт, автор | «Журнал» |
| `/plans` | Сначала просроченные, затем плановые платежи и доходы на 7 дней: дата, название, сумма | «Планы» |
| `/events` | События календаря на 7 дней с учётом повторов, время в поясе бюджета | «Календарь» |
| `/balance` | Остатки активных счетов, «Всего на счетах», «Доступно до <дата>: <сумма>» из сводки дашборда | «Главная» |

Данные берутся из существующих сервисов чтения, с теми же правами, что у веба: журнал v2, переводы, календарь планов, лента календаря, сводка счетов, сводка дашборда. Суммы форматируются из minor units так же, как в шаблонах уведомлений. Пустой результат — короткая фраза, например «За 7 дней событий нет».

`/help` выдаёт список команд. `/start` без кода и непонятный текст вне диалога тоже получают этот список, а если команды выключены — прежнюю подсказку про настройки.

## Данные

Миграция только добавляет таблицы и поля, бэкфилла нет.

- В `telegram_links` добавляются поля:
  - `commands_enabled_at timestamptz null`;
  - `commands_consent_at timestamptz null`.
- Новая таблица `telegram_dialogs`:
  - `id uuid pk` — UUIDv7, используется в ключе идемпотентности;
  - `chat_id bigint unique`, внешний ключ на `telegram_links.chat_id` с `on delete cascade`;
  - `user_id uuid`;
  - `budget_id uuid`;
  - `kind text` — `EXPENSE`, `INCOME`, `TRANSFER` или `EVENT`;
  - `step text`;
  - `version int`, растёт с каждым шагом;
  - `data jsonb` — собранные поля и список вариантов текущего шага;
  - `message_id int null`;
  - `expires_at timestamptz`;
  - `created_at`, `updated_at`.
- Счётчик частоты хранится в памяти процесса, как в `AuthRateLimitGuard`: окно 60 секунд, ключ — `chat_id`. В production API работает в одном экземпляре, поэтому общий счётчик не нужен.
- Worker раз в сутки удаляет диалоги с `expires_at` старше суток. Удаление аккаунта удаляет диалоги пользователя.

## API

- `GET me/notification-settings/telegram` дополнительно возвращает `commandsEnabled: boolean`.
- `PUT me/notification-settings/telegram/commands`:
  - тело — `{ enabled: boolean, consent?: boolean }`;
  - ответ — те же настройки, что у `GET`;
  - ошибки — 409 `TELEGRAM_NOT_LINKED`, 422 `TELEGRAM_COMMANDS_CONSENT_REQUIRED`, 409 `TELEGRAM_UNAVAILABLE`.
- Webhook не меняется. Новые типы обновлений (`callback_query`, команды) обрабатываются внутри и всегда получают 200.
- В OpenAPI описываются тела, ответы и ошибки. Изменения только добавляют, ничего не ломают.

## Клиент Bot API

`TelegramBotClient` получает новые методы:

- `sendMessage` с клавиатурой из кнопок callback и url в несколько рядов; возвращает `message_id`;
- `editMessageText`;
- `answerCallbackQuery`;
- `setMyCommands`.

Новых зависимостей нет. Как и раньше, URL с токеном не попадает ни в логи, ни в текст ошибок. Если Telegram вернул ошибку `message is not modified`, она игнорируется.

Скрипт `infra/scripts/telegram-webhook.sh` после `setWebhook` вызывает `setMyCommands` и подписывается на типы обновлений `message`, `callback_query` и `my_chat_member`.

## Интерфейс

На странице `/app/settings/telegram`, в блоке привязанного чата, появляется раздел «Команды бота»:

- переключатель;
- при включении — флажок согласия с текстом из раздела «Доступ и безопасность»;
- список команд с короткими пояснениями.

Используются существующие компоненты и токены Calm Fintech. Состояние показывается текстом, а не только цветом.

## Тесты

- Unit-тесты:
  - разбор суммы, даты и времени;
  - кодирование и проверка `callback_data`;
  - машина шагов каждого диалога;
  - форматирование ответов просмотра;
  - разбор новых типов обновлений.
- Integration-тесты API (через webhook с фальшивым клиентом бота):
  - полный `/expense` до операции `CONFIRMED`;
  - повторный «Провести» не создаёт второй записи;
  - `/income`, `/transfer`, `/event`;
  - VIEWER получает отказ при сохранении;
  - чужой счёт в списке не появляется;
  - при выключенных командах бот отказывает;
  - устаревший диалог и устаревшая кнопка;
  - `/last` показывает только данные бюджета пользователя;
  - отвязка удаляет диалог;
  - `PUT .../commands`: согласие, 409 и 422;
  - OpenAPI.
- Worker: очистка диалогов, удаление аккаунта (coverage-тест).
- Web: unit-тест переключателя и согласия.
- E2E: только сценарий включения команд в настройках, запускается в CI.

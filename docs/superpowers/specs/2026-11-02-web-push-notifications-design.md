# Push-уведомления в браузере — дизайн

Дата: 02.11.2026. Статус: согласован владельцем. Третий канал внешней доставки после [уведомлений на почту](2026-10-31-email-notifications-design.md) и [уведомлений в Telegram](2026-10-31-telegram-notifications-design.md). Это пункт «push-уведомления в браузере» в разделе 18.6 [функциональной спецификации](2026-08-30-family-budget-app-spec.md). Решением владельца от 02.11.2026 push переносится в объём v1. Ввод операций через Telegram остаётся вне объёма.

## Цель

Участник семьи включает уведомления на своих устройствах: телефоне, ноутбуке, установленном PWA на iPhone. На эти устройства приходят срочные системные уведомления о просроченном платеже и напоминания календаря. По нажатию на уведомление открывается нужный экран приложения. Устройств может быть несколько. Устройство отключается само, если пользователь вышел из аккаунта или браузер отозвал подписку.

## Объём

- подписка устройства через Push API и service worker из PWA ([план PWA](../plans/2026-10-18-pwa-installability.md));
- VAPID-ключи в env API и воркера, публичный ключ отдаётся клиенту через API во время работы;
- таблица `push_subscriptions`: несколько устройств на пользователя, привязка к сессии, удаление при ответах 404/410/403;
- канал `PUSH` в общей очереди `notification_deliveries`, `PushSender` как ещё одна реализация `ChannelSender`;
- только срочные уведомления `PLAN_OVERDUE` и `CALENDAR_REMINDER`, у каждого типа свой флажок;
- страница `/app/settings/push`: включить на этом устройстве, типы уведомлений, список устройств, отключение;
- iOS и iPadOS: push работает только в PWA, установленном на экран «Домой» (iOS 16.4+), страница объясняет, как установить.

Вне объёма (кандидаты на расширение):

- дайджест событий семьи в push (остаётся в email и Telegram);
- суммы в push (не показываются никогда);
- отдельные настройки типов для каждого устройства;
- тестовое уведомление по кнопке;
- обработчик `pushsubscriptionchange` в service worker (подписка восстанавливается при следующем открытии страницы настроек);
- флажки типов для email и Telegram (колонки общие, но эти каналы их пока не читают);
- другие типы уведомлений.

## Решения владельца

| Вопрос | Решение |
|---|---|
| Состав | Только срочные: просроченный платёж и напоминание календаря |
| Суммы | Никогда, без переключателя и согласия |
| Шифрование и VAPID | Пакет `web-push` в воркере, без своей криптографии |
| Настройки | На пользователя: строка `PUSH` в `notification_channel_settings`; устройства — только список подписок |
| Типы | Два флажка `plan_overdue_enabled` и `calendar_reminder_enabled` в `notification_channel_settings`, пока читает только `PUSH` |
| Очередь | Одна запись на пользователя, отправитель шлёт на все его устройства |
| Выход из аккаунта | Подписка живёт, пока жива сессия, в которой её создали |

## Доступ и приватность

- Push уходит только на устройства, чья сессия активна: не отозвана, `idle_expires_at` и `absolute_expires_at` в будущем. Получатель — активный пользователь и активный участник бюджета на момент отправки. Права перепроверяются при каждой отправке, как у email и Telegram.
- Суммы в push не попадают никогда. Заголовок и текст — те же, что у срочного сообщения в Telegram без сумм: «Просрочен платёж «Ипотека»» и текст уведомления; «Напоминание: «Родительское собрание»» и текст уведомления. Название платежа или события видно на экране блокировки. Об этом предупреждает текст на странице настроек.
- Payload шифруется для устройства по RFC 8291 (`aes128gcm`), поэтому push-сервис браузера (Google FCM, Apple, Mozilla, Microsoft) его не читает. Сервис видит endpoint, время, размер и заголовки `TTL`, `Urgency`, `Topic`. `Topic` — id уведомления без дефисов, он ничего не раскрывает.
- Разрешение браузера — техническое согласие. Страница до запроса разрешения объясняет, что уведомления идут через push-сервис браузера. Отдельного флажка согласия нет: payload зашифрован, третьей стороне передаётся только техническая информация.
- `endpoint`, `p256dh`, `auth` и payload не попадают в логи, метрики, аудит и `last_error`. API не отдаёт endpoint клиенту; в списке устройств только `id`, подпись, даты и признак текущего устройства.
- Подпись устройства («Chrome, Android») вычисляется из `User-Agent` при подписке. Полный `User-Agent` в таблице подписок не хранится.
- Endpoint принимается только по `https` и только для хостов push-сервисов из списка. Иначе воркер можно было бы заставить отправить запрос на произвольный адрес (SSRF).
- Аудит: `PUSH_SUBSCRIBED`; `PUSH_UNSUBSCRIBED` с причиной (`web` — удалено пользователем, `gone` — ответ 404/410/403, `session` — сессия неактивна, `key` — сменился VAPID-ключ, `replaced` — endpoint перешёл к другому пользователю, `limit` — превышено 10 устройств); изменение настроек канала.
- До релиза владелец проверяет [политику обработки ПД](2026-10-18-legal-documents-design.md): цель «push-уведомления» и упоминание push-сервисов браузеров. Это не блокирует разработку, но блокирует релиз.

## Данные

Новая миграция `20261103000000_web_push_notifications`, только добавление.

- `NotificationChannel` получает значение `PUSH` (`ALTER TYPE ... ADD VALUE`).
- `notification_channel_settings` получает колонки `plan_overdue_enabled` и `calendar_reminder_enabled` (`BOOLEAN NOT NULL DEFAULT true`). Строка `PUSH` использует `enabled` как главный переключатель. `urgent_enabled` остаётся `true`, `digest_frequency` записывается как `OFF`, `include_amounts` — `false`.

`push_subscriptions`:

| Поле | Тип | Смысл |
|---|---|---|
| `id` | uuid | |
| `user_id` | uuid, FK `users` (restrict) | владелец |
| `session_id` | uuid, FK `sessions` (cascade) | сессия, в которой подписались |
| `endpoint` | varchar(2048), unique | адрес push-сервиса |
| `p256dh` | varchar(128) | публичный ключ устройства, base64url |
| `auth` | varchar(64) | секрет аутентификации устройства, base64url |
| `application_server_key` | varchar(128) | публичный VAPID-ключ, с которым подписались |
| `label` | varchar(80) | «Chrome, Android» |
| `last_success_at` | timestamptz, null | последняя успешная отправка |
| `created_at`, `updated_at` | timestamptz | |

Индексы: `user_id`, `session_id`. У пользователя не больше 10 подписок: при одиннадцатой удаляется самая старая (причина `limit`).

Удаление строк:

- пользователь отключил устройство на странице настроек (`web`);
- push-сервис ответил 404, 410 или 403 (`gone`);
- сессия отозвана или истекла: ежедневная очистка в задаче дайджеста (`session`);
- VAPID-ключ подписки не совпадает с ключом воркера, проверяется перед отправкой (`key`);
- тот же endpoint подписал другой пользователь (`replaced`);
- удаление аккаунта (вместе с сессиями).

Если у пользователя не осталось подписок, канал `PUSH` выключается (`enabled = false`), неотправленные записи `PUSH` получают `CANCELLED`. Первая подписка включает канал.

## Очередь и отправка

- `enqueueUrgent` получает тип уведомления (`PLAN_OVERDUE` или `CALENDAR_REMINDER`). Для `PUSH` запись ставится, если канал включён, флажок типа включён и у пользователя есть подписка с активной сессией. Для `EMAIL` и `TELEGRAM` правила не меняются.
- `cancelReason` для `PUSH`: дайджест не отправляется (`DIGEST_DISABLED`); тип выключен — `TYPE_DISABLED`. Остальные проверки общие: пользователь, канал, бюджет, участник, уведомление не закрыто.
- Задача дайджеста строит дайджесты только для `EMAIL` и `TELEGRAM`. Она регистрируется, если настроен хотя бы один канал, включая `PUSH`, потому что в ней же идёт очистка подписок.
- `PushSender`:
  1. загружает подписки пользователя с активной сессией;
  2. удаляет подписки с чужим VAPID-ключом;
  3. собирает payload `{title, body, path, tag}` из `loadUrgentContent` без сумм;
  4. отправляет его на каждое устройство через `web-push` с `TTL` 12 часов, `Urgency: high`, `Topic` и таймаутом 10 секунд.

Ответ push-сервиса по каждому устройству:

| Ответ | Действие с устройством |
|---|---|
| `2xx` | успех, `last_success_at` |
| `404`, `410`, `403` | подписка удаляется (`gone`) |
| `429` | ждать `Retry-After` (по умолчанию 60 секунд) |
| `5xx`, сеть, таймаут | временный сбой |
| прочие `4xx` | постоянная ошибка устройства |

Итог записи очереди:

1. хотя бы один временный сбой: обычный повтор (`retryOrFail`: 1 мин, 5 мин, 30 мин, 2 ч, после 5-й неудачи `FAILED`);
2. иначе хотя бы один `429`: `RetryLaterError` к самому позднему `Retry-After`, попытка не тратится;
3. иначе хотя бы одно устройство получило: `SENT`;
4. иначе постоянная ошибка: `PermanentSendError`, `FAILED`;
5. иначе устройств не осталось: `CANCELLED` с причиной `PUSH_NO_DEVICES`.

Повтор уходит на все устройства, в том числе уже получившие уведомление. Service worker показывает уведомление с `tag = notification:<id>`, поэтому повтор заменяет уже показанное без нового звука. `last_error` хранит только `PUSH_<код>` или `PUSH_NETWORK`.

Payload: `title` — заголовок, `body` — текст уведомления (до 200 символов), `path` — `actionPath` уведомления (по умолчанию `/app/notifications`), `tag` — `notification:<id>`. Размер меньше 4 КБ (ограничение Apple).

## API

Все эндпоинты и ошибки описаны в OpenAPI, в `/api/v1` рядом с настройками email и Telegram. Модуль `apps/api/src/push/`.

- `GET /api/v1/me/notification-settings/push` (сессия). Ответ:
  `{available, vapidPublicKey, enabled, planOverdueEnabled, calendarReminderEnabled, devices: [{id, label, createdAt, lastSuccessAt, current}]}`.
  `available` — VAPID настроен на сервере; `vapidPublicKey` — `null`, если не настроен. В `devices` — только подписки с активной сессией; `current` — подписка текущей сессии. Без сохранённых настроек — значения по умолчанию: `enabled: false`, оба типа `true`.
- `PUT /api/v1/me/notification-settings/push` (сессия, CSRF). Тело `{enabled, planOverdueEnabled, calendarReminderEnabled}`. `enabled: true` без активных устройств — 409 `PUSH_NO_DEVICES`.
- `POST /api/v1/me/push/subscriptions` (сессия, CSRF, ограничение частоты как у ссылки Telegram). Тело `{endpoint, keys: {p256dh, auth}}` — результат `PushSubscription.toJSON()` без `expirationTime`. Правила:
  - VAPID не настроен — 409 `PUSH_UNAVAILABLE`;
  - endpoint не `https` или хост не из списка — 422 `PUSH_ENDPOINT_NOT_ALLOWED`;
  - ключи не той длины — 400 `VALIDATION_FAILED`.
  Подписка привязывается к текущей сессии и текущему VAPID-ключу. Если тот же endpoint уже есть у этого пользователя, строка обновляется. Если у другого — строка того пользователя удаляется (`replaced`) и создаётся новая. Канал включается, если строки настроек ещё нет или канал выключен. Ответ 200 — то же, что `GET`.
- `DELETE /api/v1/me/push/subscriptions/:subscriptionId` (сессия, CSRF). Удаляет только свою подписку; 204, в том числе если её нет. Последняя подписка выключает канал.

Список хостов push-сервисов: хост равен одному из суффиксов или оканчивается на `.` + суффикс. Суффиксы: `fcm.googleapis.com`, `push.services.mozilla.com`, `push.apple.com`, `notify.windows.com`. Endpoint не длиннее 2048 символов. `p256dh` — base64url, 65 байт, первый байт `0x04`. `auth` — base64url, 16 байт.

## Конфиг и инфраструктура

- API: `VAPID_PUBLIC_KEY` — необязательный, base64url, 65 байт (87 символов). Без него `available: false`.
- Воркер: `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY` (base64url, 32 байта, 43 символа), `VAPID_SUBJECT` (`mailto:` или `https:`). Задаются вместе или не задаются вовсе. Без них записи `PUSH` остаются в очереди, как письма без SMTP.
- Публичный ключ в API и воркере должен совпадать. Приватный ключ есть только у воркера и никогда не попадает в API, веб и клиентский бандл. Клиент получает публичный ключ из `GET` настроек, а не из `runtimeConfig`.
- Ключи создаются один раз на окружение: `pnpm --filter @harmofin/worker exec web-push generate-vapid-keys --json`. Для staging — отдельная пара. Смена ключа отключает все устройства (причина `key`), пользователи включают push заново.
- Переменные добавляются в `.env.example`, `infra/env/staging.example`, `infra/compose/production.yml` (api: публичный; worker: все три) и в файл окружения из секретов CI/CD (`*_ENV_FILE`). Новых шагов деплоя нет.
- Caddy и CSP: service worker обращается к push-сервису не сам, а через браузер. Правки Caddy не нужны.

## Service worker

В `apps/web/public/sw.js` добавляются два обработчика. Кэширование и офлайн-страница не меняются.

- `push`: читает JSON payload и вызывает `self.registration.showNotification(title, {body, tag, icon: '/icons/icon-192.png', badge: '/icons/icon-192.png', lang: 'ru', data: {path}})`. Если payload пустой или битый, показывается «HarmoFin» с переходом в `/app/notifications`. Показ обязателен (`userVisibleOnly`).
- `notificationclick`: закрывает уведомление и проверяет путь: разрешены только `/app`, `/app/…`, `/app?…`; иначе `/app/notifications`. Затем фокусирует открытую вкладку приложения и переходит в ней по пути, а если вкладки нет — открывает новое окно.

## Интерфейс

Пункт «Push-уведомления» в `/app/settings` после пункта Telegram, страница `/app/settings/push`. Состояния в порядке проверки:

1. Сервер без VAPID: «Push-уведомления пока не настроены на сервере».
2. Браузер без Push API, но это iPhone или iPad не в режиме PWA: «На iPhone и iPad уведомления работают только в приложении, установленном на экран «Домой»: нажмите «Поделиться» → «На экран «Домой»», откройте HarmoFin с экрана «Домой» и вернитесь сюда». Кнопки включения нет.
3. Браузер без Push API: «Этот браузер не поддерживает push-уведомления».
4. Разрешение `denied`: «Уведомления запрещены в настройках браузера. Разрешите их для этого сайта и обновите страницу».
5. Иначе:
   - текст о push-сервисе браузера и экране блокировки;
   - кнопка «Включить на этом устройстве», если текущее устройство не в списке. Если браузерная подписка уже есть, но сервер её не знает (после выхода или истечения сессии), кнопка называется «Включить снова». Нажатие запрашивает разрешение, создаёт подписку и отправляет `POST`. Тихой перепривязки без нажатия нет.

Если устройства есть:

- форма: «Присылать push-уведомления» (главный переключатель); в группе «Что присылать» — «Просроченные платежи» и «Напоминания календаря»; кнопка «Сохранить»;
- список «Устройства»: подпись, отметка «Это устройство», «Подключено <дата>», кнопка «Отключить» с подписью для экранного диктора «Отключить <подпись>». Отключение текущего устройства также снимает подписку в браузере.

При выходе из аккаунта клиент снимает подписку браузера (по возможности, без ожидания ошибок), затем вызывает выход. Даже если это не удалось, сервер не шлёт push на устройство отозванной сессии.

Service worker регистрируется только в production-сборке, поэтому локально push проверяется на собранном приложении (как PWA). Calm Fintech: карточка и поля как на странице Telegram, без новых цветов; клавиатура, видимый фокус, подписи у полей, статус текстом с `aria-live`.

## Тесты

- Юниты API: проверка endpoint (хосты, `https`, длина), проверка ключей, подпись устройства по `User-Agent`, конфиг `VAPID_PUBLIC_KEY`.
- Юниты воркера: конфиг VAPID; payload (обрезка текста, `tag`, путь по умолчанию); итог по нескольким устройствам (успех, 410, 403, 429 с `Retry-After`, 5xx, сеть, прочие 4xx, смесь); `WebPushTransport` с подменённым `web-push`; `cancelReason` для `PUSH`; `enqueueUrgent` с флажками типов.
- Интеграция API: настройки по умолчанию; подписка и включение канала; перепривязка своего endpoint; переход endpoint к другому пользователю; лимит 10; чужой `DELETE` не удаляет; последняя подписка выключает канал; 409 `PUSH_NO_DEVICES`; 409 `PUSH_UNAVAILABLE`; 422 по хосту; CSRF; отозванная сессия скрывает устройство; OpenAPI.
- Интеграция воркера (в `apps/api/test/`, с подменённым транспортом): срочное уходит на два устройства; 410 удаляет подписку и выключает канал; устройство отозванной сессии пропускается; выключенный тип отменяет запись; повтор при 5xx; очистка неактивных подписок; записи `PUSH` не попадают в дайджест.
- Веб: обработчики `push` и `notificationclick` в `sw.js` на подменённом `self`; помощники `pwa/push.ts` (поддержка, iOS, `urlBase64ToUint8Array`, смена ключа); страница во всех состояниях; снятие подписки при выходе.
- E2E в CI: подменённые `Notification` и `PushManager` через `addInitScript`; включение на устройстве, выбор типов, отключение. Настоящий push-сервис не используется. Сборка в CI собирает dev-сервер без service worker, поэтому подменяется и `navigator.serviceWorker.getRegistration`.

## Review

Security (endpoint и SSRF, VAPID-ключи и секреты, привязка к сессии, логи, переход endpoint между пользователями), backend (миграция enum и колонок, очередь), API, UI/UX, QA, финальный. Release review — для env и compose. Financial review не нужен: финансовые данные только читаются, суммы не отправляются.

## Порядок реализации

Одна ветка `feat/web-push`, по коммиту на задачу плана, без промежуточных PR:

1. данные;
2. конфиг и проверки API;
3. эндпоинты API;
4. очередь воркера;
5. `PushSender`;
6. service worker и помощники браузера;
7. страница настроек;
8. инфраструктура, E2E и документы.

# Несколько напоминаний на событие календаря

Дата: 03.11.2026. Статус: согласован владельцем, не реализован.

## Цель

Участник семьи ставит на событие календаря до трёх напоминаний, например «за день» и «за час». Сейчас можно поставить только одно. Выбор времени расширяется. Каждое напоминание приходит в центр уведомлений и во внешние каналы, которые уже доставляют напоминания календаря: email, Telegram и push. Кроме того, в настройках email и Telegram появляются отдельные переключатели «Просроченные платежи» и «Напоминания календаря», как в push. Тогда напоминания можно выключить в канале, не выключая все срочные сообщения.

Пункт 18.7 функциональной спецификации: «несколько напоминаний на событие и внешняя доставка напоминаний». Внешняя доставка уже реализована. Обработчик `EVALUATE_CALENDAR_REMINDERS` для каждого созданного `CALENDAR_REMINDER` вызывает `enqueueUrgent`. Этот дизайн закрывает оставшуюся часть.

## Решения владельца

| Вопрос | Решение |
|---|---|
| Объём | Несколько напоминаний и переключатели по типу для email и Telegram |
| Сколько напоминаний | До 3 на событие |
| Варианты | В момент начала, за 5, 15 и 30 минут, за 1 и 2 часа, за 1 и 2 дня, за 1 неделю |
| Хранение | Массив смещений в строке события, а не отдельная таблица |
| Бот | Не меняется: `/event` по-прежнему ставит одно напоминание |

## Вне объёма

- Произвольное время напоминания (число и единица).
- Разные наборы напоминаний у разных участников: напоминания принадлежат событию, их получают автор и активные участники, как сейчас.
- Выбор канала на конкретное напоминание.
- Изменения в боте и правка или отмена одного повтора серии.

## Данные

Миграция `20261105000000_calendar_multiple_reminders`, только аддитивная.

- Новая колонка `calendar_events.reminder_offsets INTEGER[] DEFAULT ARRAY[]::INTEGER[]` — в той же форме, в какой Prisma создаёт `weekdays`, чтобы `prisma migrate diff` оставался пустым; `NULL` запрещает check-ограничение. Значения — минуты до начала вхождения.
- Backfill: `UPDATE calendar_events SET reminder_offsets = ARRAY[reminder_minutes] WHERE reminder_minutes IS NOT NULL`.
- Check-ограничение `calendar_events_reminder_offsets`:
  - `cardinality(reminder_offsets) <= 3`;
  - `reminder_offsets <@ ARRAY[0, 5, 15, 30, 60, 120, 1440, 2880, 10080]`;
  - без `NULL` в самом массиве и в его элементах;
  - массив строго возрастает, то есть без повторов: при трёх элементах максимум достаточно сравнить соседние пары `[1] < [2]` и `[2] < [3]`, функция не нужна.
- Ограничение `calendar_events_reminder_minutes` пересоздаётся с тем же списком из девяти значений.
- `reminder_minutes` остаётся зеркалом: сервер пишет в неё наименьшее смещение или `NULL`, если смещений нет. Так образ предыдущего релиза при откате продолжает слать ближайшее напоминание. Колонку можно удалить отдельной миграцией в одном из следующих релизов.
- Частичный индекс `calendar_events_reminders_idx` пересоздаётся с условием `cardinality(reminder_offsets) > 0 AND deleted_at IS NULL`.
- В Prisma: `reminderOffsets Int[] @default([]) @map("reminder_offsets")`. Поле `reminderMinutes` остаётся.

Для переключателей по типу схема не меняется. Колонки `plan_overdue_enabled` и `calendar_reminder_enabled` уже есть в `notification_channel_settings` для каждого канала, по умолчанию `true`.

## API

Совместимость API сохраняется: новое поле добавляется, старое помечается `deprecated` и продолжает работать.

### События календаря

`POST /api/v2/budgets/{budgetId}/calendar/events` и `PATCH .../calendar/events/{eventId}`:

- Новое поле `reminders: number[]` — до 3 значений из списка, без повторов, в любом порядке. Сервер сортирует его по возрастанию.
- Старое `reminderMinutes: number | null` остаётся. В OpenAPI оно помечено `deprecated`, допустимые значения те же девять.
- Правило объединения (функция `resolveReminders` в `calendar.schemas.ts`):
  - пришло только `reminders` — берётся оно;
  - пришло только `reminderMinutes` — `[x]` или `[]` для `null`;
  - пришли оба — `reminderMinutes` должно быть равно наименьшему из `reminders` (или `null` при пустом массиве), иначе 400 `VALIDATION_FAILED` с `fieldErrors.reminders` «Напоминания не совпадают с reminderMinutes.»;
  - не пришло ни одно: при создании `[]`, при правке напоминания не меняются.
- Ошибки валидации (400 `VALIDATION_FAILED`, поле `reminders`, у ошибки элемента — `reminders.<индекс>`):
  - «Можно выбрать до трёх напоминаний.»;
  - «Выберите напоминание из списка.»;
  - «Напоминания не должны повторяться.».

Тело `CalendarEventBody` получает `reminders`. Ответ события `CalendarEventResponse` (элементы ленты `CalendarFeedEventItemResponse` напоминаний не содержат и не меняются): `reminders: number[]` по возрастанию и `reminderMinutes: number | null`, то есть наименьшее смещение (`deprecated`).

Бот (`/event`) передаёт `reminderMinutes` и продолжает работать без изменений.

### Настройки email и Telegram

`GET` и `PUT /api/v1/me/notification-settings/email`, `GET` и `PUT /api/v1/me/notification-settings/telegram`:

- В ответ добавляются `planOverdueEnabled: boolean` и `calendarReminderEnabled: boolean`.
- Во входе `PUT` эти поля необязательны: если поле не пришло, значение не меняется. Так старый клиент не сбрасывает их. Пустой профиль по умолчанию даёт `true`.
- Смена значения пишется в аудит так же, как остальные поля настроек канала.

## Worker

`EVALUATE_CALENDAR_REMINDERS` (`calendar-reminder.handler.ts`, `calendar-reminder.ts`):

- Выбираются события с `cardinality(reminder_offsets) > 0`, не удалённые.
- Окно разворота вхождений `reminderWindow` строится по **наибольшему** смещению события.
- Для каждого вхождения и каждого смещения считается `reminderMoment`. Если `isReminderDue`, создаётся уведомление.
- Ключ не меняется: `calendar:<eventId>:<occurrenceDate>:<minutes>`. Уже созданные напоминания после миграции не дублируются. Если добавить смещение, появится новый ключ; если убрать, новых уведомлений по нему не будет.
- Смещение `0` означает момент начала. Для события «весь день» это 09:00 дня события по поясу бюджета, а остальные смещения отсчитываются от того же 09:00.
- Если в одном запуске сработали два смещения одного вхождения (например, после простоя worker), создаются оба уведомления.
- Получатели, правило «простой дольше 30 минут без потока старых уведомлений» и тексты не меняются.

`enqueueUrgent` (`delivery/enqueue.ts`): проверка типа (`planOverdueEnabled` для `PLAN_OVERDUE`, `calendarReminderEnabled` для `CALENDAR_REMINDER`) применяется ко **всем** каналам, а не только к `PUSH`. Повторная проверка при отправке (`delivery/eligibility.ts`, `pushTypeEnabled` → общая `typeEnabled`) тоже начинает работать для всех каналов: если тип выключили после постановки в очередь, доставка отменяется с уже существующей причиной `TYPE_DISABLED`.

## Интерфейс

Перед правкой сверяться с [Calm Fintech visual guidelines](2026-09-17-calm-fintech-visual-guidelines.md).

**Форма события** (`CalendarEventDialog`, `event-form-state.ts`). Поле «Напоминание» (`UiSelect`) заменяется полем «Напоминания» с чипами, тем же компонентом и паттерном, что «Участники» и дни недели в этой форме:

- Чипы по порядку: «В момент начала», «За 5 мин», «За 15 мин», «За 30 мин», «За 1 час», «За 2 часа», «За 1 день», «За 2 дня», «За 1 неделю».
- У каждого чипа `aria-pressed` и галочка у выбранного: состояние передаётся не только цветом.
- Подсказка под полем: «Можно выбрать до трёх». При трёх выбранных остальные чипы `disabled`, подсказка меняется на «Выбрано три — снимите одно, чтобы выбрать другое».
- Для события «весь день» добавляется пояснение «Отсчёт от 09:00 дня события».
- Ошибка сервера `fieldErrors.reminders` показывается под полем. Алиас `reminderMinutes` → `reminders` сохраняется.
- В новом событии ничего не выбрано. При правке выбираются сохранённые `reminders`.
- Форма отправляет только `reminders`.

**Карточка события.** Строка `Bell` показывает выбранные напоминания по убыванию смещения, через запятую с маленькой буквы после первой: «За 1 день, за 1 час, в момент начала». Без напоминаний — «Без напоминания».

**Настройки email** (`/app/settings/notifications`) **и Telegram** (`/app/settings/telegram`). Под включённым переключателем «Срочные письма» или «Срочные сообщения» появляются два вложенных чекбокса с отступом: «Просроченные платежи» и «Напоминания календаря». Формулировки и паттерн те же, что на `/app/settings/push`. Если срочные выключены, вложенные чекбоксы скрыты, а их значения сохраняются.

**Уведомление** в центре уведомлений и тексты во внешних каналах не меняются.

## Тесты

- Unit (worker, `calendar-reminder`): несколько смещений одного вхождения; смещение 0; «весь день» с отсчётом от 09:00; окно по наибольшему смещению; два смещения в одном запуске; ключи совпадают с прежним форматом.
- Unit (api): `resolveReminders` — все ветки правила объединения и тексты ошибок; маппер ответа (`reminders` по возрастанию, `reminderMinutes` — минимум).
- Интеграция (api): создание и правка с `reminders`, только с `reminderMinutes`, с обоими (совпадают и расходятся), правка без полей не меняет напоминания; зеркало `reminder_minutes` в БД; check-ограничение БД отвергает четыре значения, повтор и значение вне списка; бюджетная изоляция события не меняется. Настройки email и Telegram: чтение, частичный `PUT`, аудит.
- Интеграция (БД): оператор backfill из файла миграции копирует `reminder_minutes` в `reminder_offsets`.
- Unit (worker): повторный запуск без дублей при нескольких смещениях; `enqueueUrgent` не ставит EMAIL или TELEGRAM при выключенном типе; `cancelReason` отменяет доставку с `TYPE_DISABLED` в любом канале, если тип выключили после постановки.
- Web unit: чипы, лимит трёх, `disabled` и подсказка, пояснение для «весь день», заполнение при правке, отправка `reminders`; строка карточки; вложенные чекбоксы на страницах email и Telegram.
- E2E (только CI): событие с двумя напоминаниями сохраняется, и карточка показывает обе строки.
